> هذا المستند **خطة إجراء يدوية**، لا سكربت تنفيذ تلقائي. لا يُشغَّل أي ترحيل تلقائي على بيانات إنتاج بموجب هذا المستند أو أي كود مرتبط بـP0.7. **أي سكربت تشخيص يُبنى مستقبلًا استنادًا لهذه الخطة يجب أن يكون قراءة-فقط/تجربة-جافة (dry-run) بشكل افتراضي.**

## 2) الكشف (Detection)

لكل فترة تاريخية مطلوب فحصها:
1. اجلب كل `journalEntries` التي يلمس أحد أسطرها حساب مورد فعلي (`accountCode` يطابق أحد `vendors[].accountId`).
2. لكل قيد كذلك، صنِّف مصدره عبر حقل `source`/`ref`/`type` إن وُجد (`vendor-opening`، `accrued-expense`، `import-expenses`، أو غير مصنَّف/يدوي).
3. اجمع رصيد كل حساب مورد (`buildBalanceMap`) وقارنه بمجموع `openingBalance` + أي `accruedExpenses[].vendor` مطابق بالاسم — أي فرق غير مُفسَّر = **REQUIRES-HUMAN-REVIEW**.

## 3) المطابقة (Mapping) وتجنّب الازدواج

- **لا تُنشئ `vendorBills[]` تلقائيًا من `accruedExpenses[]` قائمة.** إن قرر المحاسب تحويل مصروف مستحق قائم إلى "فاتورة مورد" رسمية، الأسلوب المحاسبي الآمن الوحيد:
  `Dr Accrued Liability (2900) / Cr AP Control (حساب المورد)` — **بلا مصروف جديد** (المصروف مُعترَف به بالفعل) — ثم تُنشأ `vendorBills[]` سجل بقيمة صفرية GL (توثيقي فقط) يشير لقيد التحويل، أو يُترَك الأمر بالكامل لـ`accruedExpenses[]` (بلا تحويل) إن لم يكن هناك حاجة تشغيلية فعلية.
- **مصروفات `payMethod:'accrued'`:** لا تحويل آلي إطلاقًا — كل سجل يتطلب مراجعة بشرية لتحديد حالة السداد الفعلية أولًا (§1).

## 4) مراجعة المحاسب (إلزامية لكل حالة تتضمن قيدًا)
أي إجراء ينشئ أو يُعدِّل قيدًا محاسبيًا بموجب هذه الخطة **يتطلب موافقة محاسب صريحة قبل التنفيذ** — لا استثناء، حتى لو بدت الحالة واضحة آليًا.

## 5) التسوية (Reconciliation) بعد أي ترحيل يدوي
- `GET /api/ap-aging` — `reconciliation.reconciled === true` لكل الموردين المُعاد تصنيفهم.
- `GET /api/vendors/:id/statement` — الرصيد الختامي يطابق `vendorApOutstanding()`.

## 6) الترحيل المُتحكَّم به (Controlled Migration)
1. نسخة احتياطية كاملة قبل أي تعديل (`scripts/backup.js` الموجود مسبقًا).
2. تنفيذ التحويل لمورد واحد فقط أولًا (تجربة محدودة النطاق).
3. تحقق كامل (`ap-aging`, `statement`, ميزان المراجعة) قبل التوسّع لبقية الموردين.
4. تسجيل كل تحويل في سجل تدقيق (`appendAuditEvent`) بوصف واضح يذكر المصدر الأصلي.

## 7) التراجع (Rollback)
كل قيد تحويل هو قيد **إضافي** (لا يحذف أو يُعدِّل أي قيد تاريخي قائم) — التراجع دائمًا عبر قيد عكسي جديد، لا حذف. الاحتفاظ بنسخة احتياطية (§6.1) يسمح بالمقارنة الكاملة قبل/بعد في أي وقت.

## 8) فحوصات ما بعد الترحيل (Post-Migration Checks)
- ميزان المراجعة لا يزال متوازنًا (`isBalanced:true`).
- `GET /api/ap-aging`'s `reconciliation` لكل الفترات المتأثرة.
- لا سجل `vendorBills[]` جديد أُنشئ بلا `journalId` صالح.
- سجل تدقيق كامل لكل خطوة.

## ملخص
**لا بيانات معاملات حقيقية موجودة حاليًا (§0)** — هذه الخطة جاهزة للتفعيل اليدوي، خطوة بخطوة، بموافقة محاسب صريحة لكل حالة، عند ظهور بيانات إنتاج حقيقية. **لم يُشغَّل أي سكربت ترحيل تلقائي بموجب P0.7.**
