# خطة ضبط شجرة الحسابات وإعادة التصنيف — Milestone P0.9

> هذا المستند **خطة إجراء يدوية**، لا سكربت تنفيذ تلقائي. لا يُشغَّل أي إعادة تصنيف تلقائية على بيانات إنتاج بموجب هذا المستند أو أي كود مرتبط بـP0.9. **لم يُعَد كتابة أي قيد يومية تاريخي بموجب هذا الميلستون — كل إصلاح هو تصحيح للمسار البرمجي المستقبلي فقط.**

## 1) تصنيف كل حالة إعادة تصنيف محتملة (Step 38)

| الحالة | الكشف | التصنيف |
|---|---|---|
| قيد مطالبة تأمين تاريخي على حساب 1120 (يُفترض أنه يخص شركة تأمين فعليًا) | `journalEntries` حيث `type` يبدأ بـ`insurance`/`ref` يطابق نمط `IC-####`/`JE-IC-...` وسطر بحساب `1120` | **REQUIRES-HUMAN-REVIEW** — يتطلب تأكيد محاسب أن القيد يخص تأمينًا فعلًا (لا تسوية شبكة حقيقية استخدمت نفس الحساب مصادفة) قبل أي قيد تصحيحي |
| قيد شطب فرق مطالبة تأمين على حساب 5700 | `type==='insurance_received'` وسطر بحساب `5700` | **REQUIRES-HUMAN-REVIEW** — نفس المنطق |
| قيد إيراد تأمين على حساب 4200 بدل 4150 | `type==='insurance'` وسطر دائن بحساب `4200` | **REQUIRES-HUMAN-REVIEW** |
| أي حساب مستخدَم في قيد لكنه محذوف الآن من COA | مقارنة `journalEntries[].lines[].accountCode` مقابل `chartOfAccounts` الحالية | **CAN-MAP-SAFELY** إن وُجد حساب بنفس الاسم بكود مختلف واضح؛ وإلا **REQUIRES-HUMAN-REVIEW** |
| حسابات جديدة تُنشأ بموجب إصلاحات P0.9 (5720 — ديون مشكوك فيها/تأمين) | `ensureAccount()` عند أول استخدام فعلي | **AUTHORITATIVE** — لا حاجة مراجعة، إنشاء تلقائي آمن لحساب جديد لم يوجد من قبل |

## 2) الكشف (Detection)

لكل فترة تاريخية مطلوب فحصها بعد ظهور بيانات حقيقية:
1. اجلب كل `journalEntries` حيث `type` يبدأ بـ`insurance` أو `ref`/`source` يشير لمطالبة تأمين.
2. لكل قيد، افحص أسطره: هل يلمس 1120 (بدل 1130) أو 5700 (بدل 5720) أو 4200 (بدل 4150)؟
3. اجمع القيم لكل حساب متأثر لكل فترة — هذا هو حجم إعادة التصنيف المطلوب فعليًا.

## 3) مراجعة المحاسب (إلزامية لكل حالة تتضمن قيدًا)
أي قيد إعادة تصنيف بموجب هذه الخطة **يتطلب موافقة محاسب صريحة قبل التنفيذ** — لا استثناء.

## 4) قيود إعادة التصنيف المقترحة (لا تُنفَّذ إلا بموافقة)
لكل قيد تاريخي خاطئ الحساب، القيد التصحيحي الآمن الوحيد — **عكس ثم إعادة ترحيل، لا تعديل القيد الأصلي مباشرة**:
```
Dr 1130 (ذمم مدينة — شركات التأمين)   [المبلغ]
    Cr 1120 (K-Net/Visa/Master — مستحقات)   [المبلغ]
```
ونظائرها لـ5700→5720 و4200→4150. كل قيد تصحيحي يحمل مرجعًا صريحًا يشير للقيد الأصلي المصحَّح (`ref: 'RECLASS-<original-ref>'`) في وصفه.

## 5) الموافقة
موافقة محاسب مكتوبة (تعليق/سجل) لكل دفعة إعادة تصنيف قبل الترحيل — لا استثناء حتى لحالة واحدة تبدو واضحة.

## 6) التراجع (Rollback)
كل قيد إعادة تصنيف هو قيد **إضافي عكسي** — لا يُحذف أو يُعدَّل أي قيد تاريخي قائم أبدًا. التراجع دائمًا عبر قيد عكسي جديد آخر، لا حذف.

## 7) التسوية (Reconciliation) بعد أي إعادة تصنيف
- ميزان المراجعة يبقى متوازنًا (`isBalanced:true`) — القيد التصحيحي متوازن بذاته دائمًا.
- `GET /api/financial-statements` — تأكد أن `insReceivable`/`totalAssets` لم يتغيرا (إعادة التصنيف بين 1120/1130 لا تغيّر totalAssets، فقط تصحح أي البندين يظهر فيه المبلغ — تحقَّق من ذلك تحديدًا بعد كل دفعة).
- `GET /api/ar-aging` (مطالبات التأمين) يعكس الحساب الصحيح بعد إعادة التصنيف.

## 8) فحوصات ما بعد إعادة التصنيف (Post-Reclassification Checks)
- عدد قيود إعادة التصنيف = عدد القيود التاريخية الخاطئة المكتشفة بالضبط (لا أكثر ولا أقل).
- سجل تدقيق كامل لكل قيد تصحيحي.
- صفر قيد تاريخي أصلي مُعدَّل أو محذوف.
