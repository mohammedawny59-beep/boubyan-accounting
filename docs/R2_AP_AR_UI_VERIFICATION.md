# R2 — التحقق من واجهات فواتير الموردين (AP) وذمم المرضى (AR) والتخلص من الأصول الثابتة

> ملخّص تحقق شامل لميلستون R2. المرجعية الكاملة للنتائج الخام موجودة في هذا الملف؛ الحالة الحيّة لكل بند فجوة تُقرأ من `ACCOUNTING_GAP_REGISTER.md`.

## 0) السياق والنطاق

R1 اكتشف أن `db.vendorBills[]` (AP، منذ P0.7) و`db.patientReceivables[]` (AR، منذ P0.8) محركان خلفيان كاملان ومختبَران بالفعل — لكن **بلا أي واجهة مستخدم إطلاقًا** (`NEW-R1-AP-AR`)، وأن التخلص من أصل ثابت (`POST /api/assets/:id/dispose`، منذ P0.10) بلا زر واجهة (`NEW-R1-01`). كلا البندين مُصنَّف Tier 0 (حاجز إطلاق).

**هدف R2:** بناء واجهات كاملة، آمنة، جاهزة للمحاسب فوق هذه المحركات المُتحقَّق منها مسبقًا — **بلا** إعادة تصميم المنتج، **بلا** إعادة بناء الخلفية، **بلا** نموذج محاسبي منافس. الخلفية الموجودة هي مصدر الحقيقة الوحيد.

**قاعدة النجاح الصريحة للميلستون:** إن احتاجت AP أو AR لطلب API مباشر أو قيد يدوي خام لدورة حياتها الاعتيادية — R2 غير مكتمل (NOT PASS).

## 2) مسار AP (فواتير الموردين) — التحقق الحي

**دورة الحياة المُتحقَّق منها فعليًا عبر متصفح حي ضد خادم تطوير معزول:**

مورد → فاتورة (متعددة البنود) → مراجعة المتبقي → دفعة جزئية → إشعار دائن → كشف حساب (`GET /api/vendors/:id/statement`) → تقادم الذمم الدائنة (`GET /api/ap-aging`) بمطابقة GL حية.

- إنشاء فاتورة عبر `saveVendorBill()` → `POST /api/vendor-bills` (server.js:5456) — بلا قيد يدوي.
- دفعة جزئية عبر `submitVbPay()` → `POST /api/vendor-bills/:id/pay` (server.js:5513) — حارس `OVERPAYMENT` مربوط بـ`outstandingAmount` المُشتق.
- إشعار دائن عبر `submitVbCredit()` → `POST /api/vendor-bills/:id/credit` (server.js:5739).
- **عكس دفعة مفردة** عبر `reverseVbPayment()` → `POST /api/vendor-bills/:id/payments/:paymentId/reverse` (server.js:5631) — **جديد في هذه الجولة** (انظر §4).
- كشف الحساب مُعاد بناؤه بالكامل ليقرأ من `GET /api/vendors/:id/statement` (server.js:5826) بدل الاشتقاق من `DB.journalEntries` على المتصفح (كان يخالف P6-025).
- تقادم الذمم الدائنة: خلل حرج سابق (`loadAgingAP()` كانت تقرأ `r.buckets.over60` غير الموجود، فتُطلق `TypeError` فور وجود أي رصيد مورد) أُصلح إلى `over90` (المفتاح الحقيقي)، مع بطاقة مطابقة GL.

**دليل رقمي حي:** فاتورة `BILL-1787313235386` مُنشأة عبر الواجهة، دفعة جزئية 300/300 د.ك سُجِّلت بمفتاح تكرار، ثم عُكست عبر `reverseVbPayment()` — `paidAmount` عاد فعليًا لـ0 و`outstandingAmount` استُعيد بالكامل، مع قيد عكسي `JE-BILLPAYREV-*` منفصل يحفظ القيد الأصلي كما هو.

## 3) مسار AR (ذمم المرضى) — التحقق الحي

مريض → ذمة (خدمة آجلة) → مراجعة المتبقي → تحصيل جزئي/كامل → إشعار دائن → شطب دين معدوم → كشف حساب → تقادم ذمم المرضى (`GET /api/patient-ar-aging`، **منفصل تمامًا** عن شاشة تقادم مطالبات التأمين).

- إنشاء ذمة عبر `savePatientReceivable()` → `POST /api/patient-receivables` (server.js:6095) — بحد ذاته له تحذير سلامة صريح في الواجهة: **ممنوع استخدام هذا المسار لنقد مُستلَم فعليًا وقت الخدمة** (يجب أن يمر عبر مسار الدخل اليومي القائم).
- تحصيل عبر `submitPrCollect()` → `POST /api/patient-receivables/:id/collect` (server.js:6150).
- **عكس تحصيل مفرد** عبر `reversePrCollection()` → `POST .../collections/:collectionId/reverse` (server.js:6255) — **جديد في هذه الجولة**.
- **إلغاء ذمة** عبر `submitPrCancel()` → `POST .../cancel` (server.js:6398) — **جديد في هذه الجولة**.
- شطب دين معدوم عبر `submitPrWriteoff()`.

**خلل محاسبي حقيقي اكتُشف ذاتيًا أثناء الاختبار الحي (خارج نطاق R2 الأصلي، مُصلَح بموجب بند "خلل مُتحقَّق منه" في تعليمات الميلستون):** شطب الديون المعدومة كان يُرحِّل إلى حساب `5710` ("هاتف وإنترنت") بدل حساب مصروف "ديون معدومة" مخصَّص. السبب الجذري: `ensureAccount(db, code, name, type, parent)` تُنشئ الحساب فقط إن لم يكن الكود موجودًا مسبقًا — كود `5710` كان مُهيَّأً مسبقًا في `DEFAULT_COA` باسم مختلف تمامًا، فأعاد استخدامه صمتًا تحت اسم "ديون معدومة" في القيد المعروض بينما الحساب الفعلي يبقى "هاتف وإنترنت". **الإصلاح:** كود جديد غير مُصادَم `5920` (server.js:6443). **الاختبارات المُحدَّثة:** `tests/p0-8-ar-lifecycle.test.js` ("Write-off A")، `tests/p0-9-coa-integrity.test.js` ("P6072 D" — أُضيفت تأكيدًا صريحًا أن `5710` لم يعد يظهر في القيد). أُعيد تشغيل المجموعتين + `tests/accounting.test.js`: **98/98 ناجحة.**

**دليل رقمي حي (سيناريو الإلغاء المتسلسل):** ذمة 80 د.ك → تحصيل جزئي 30 د.ك (رُفض الإلغاء بـ`409 RECEIVABLE_HAS_COLLECTIONS` كما هو متوقَّع) → عكس التحصيل عبر الواجهة الجديدة → إلغاء الذمة نجح (`200 OK`) بعدها مباشرة — يُثبت أن سلسلة "تصحيح خطأ ← إلغاء" أصبحت ممكنة بالكامل من الواجهة دون أي طلب API مباشر.

## 4) التخلص من الأصول الثابتة — التحقق الحي

Asset list → زر "📤 تخلص" → معاينة NBV/ربح-خسارة حية → تأكيد → `POST /api/assets/:id/dispose` (server.js موجود منذ P0.10) → حالة "متخلَّص عنه" نهائية (تعذّر التخلص مجددًا، `409 ALREADY_DISPOSED`).

**إصلاحان جانبيان حقيقيان (موجودان مسبقًا، اكتُشفا أثناء بناء R2):**
- `deleteAsset()` كانت `await fetch(...)` بلا أي معالجة للاستجابة — فشل صامت كامل. أُصلحت لتعرض نتيجة الطلب فعليًا (نجاح/فشل `ASSET_HISTORY_LOCKED`).
- قائمة الأصول كانت تعرض القيمة الدفترية القديمة للأصول المتخلَّص عنها بعد التخلص مباشرة (خلل تجميلي بلا أثر محاسبي حقيقي — `buildAndPostAssetDisposal` يعيد حساب القيم من قاعدة البيانات الحيّة دومًا). أُصلح لعرض "—".

**دليل رقمي حي:** أصل `AST-1787314686084` (تكلفة 1000، بلا إهلاك سابق) → عائد تخلص 900 → ربح 100 محسوب ومعروض بشكل صحيح قبل التأكيد → `POST .../dispose` نجح، الأصل أصبح غير قابل لأي حركة مستقبلية.

## 6) إصلاح صلاحيات الأدوار — تفصيل تقني

`server.js`'s `migrateDB(db)` (يُستدعى مرة عند كل إقلاع للخادم) كان يبذر `db.roles` بالكامل فقط إن كانت غائبة تمامًا (`buildInitialDB()`) — لا آلية دمج للتغييرات على `DEFAULT_ROLES` بعد ذلك. أي تعريف صلاحية جديد (تبويب جديد أو إجراء جديد أُضيف لدور موجود) لا يصل أبدًا لقاعدة بيانات مستأجر مُهيَّأة مسبقًا.

**الإصلاح:** كتلة دمج إضافية جديدة في `migrateDB()` (نفس نمط إصلاح شجرة الحسابات الموجود مسبقًا في الدالة نفسها) — لكل دور معروف موجود فعليًا في `db.roles`، تُضاف أي علامة تبويب أو إجراء يُعرِّفه `DEFAULT_ROLES` لكن لا يمتلكه الدور المخزَّن بعد — **إضافة فقط، لا حذف أو استبدال إطلاقًا**، فلا يمكن لهذا التغيير سحب صلاحية موجودة أو تجاوز تخصيص أدمن مقصود.

**تحقق حي:** `GET /api/roles` بعد إعادة إقلاع الخادم أظهر `accountant.tabs` تتضمن الآن `vendorbills`/`patients`/`patientreceivables`، و`accountant.actions.manual` أصبحت `['view','add','edit','delete']`. مستخدم محاسب فعلي جديد أُنشئ واختُبر: إنشاء مريض → إنشاء ذمة → تحصيل — **الثلاثة نجحت (200 OK)**، بعد أن كان التحصيل سيُرفَض `403` قبل الإصلاح.

## 8) أثر البيانات الحقيقية

صفر. جميع الاختبارات نُفِّذت ضد خادم تطوير محلي (`localhost:3000`) بقاعدة بيانات ملف معزولة (`data/database.json`)، لم يُستخدَم أي اتصال Mongo إنتاجي، ولم تُلمَس أي بيانات عميل حقيقية. بيانات الاختبار (مورد/مريض/فواتير/ذمم/أصل تجريبي) بقيت في قاعدة التطوير كدليل حي قابل لإعادة الفحص.

## 9) البنود المتبقية عمدًا خارج نطاق R2 (لم تُمَس، بقرار نطاق صريح)

- P6-098, P6-099 — كما هما.
- RBAC لعملية التخلص من أصل تبقى admin-only بتصميم مسبق من P0.10 (لا تغيير).
- عدم تناظر صلاحية "موظف استقبال" (`manual.add` بلا `financials.view`) — منخفض الخطورة، آمن الاتجاه، مُلاحَظ من المراجع E، مُؤجَّل صراحة (ليس ضمن نطاق AP/AR/التخلص).
- تعميم آلية دمج صلاحيات الأدوار لتشمل مستأجرين حقيقيين مُوفَّرين مسبقًا (خارج قاعدة التطوير هذه) — الآلية المُضافة في §6 تعمل عبر نفس نقطة `migrateDB()` المُستخدَمة أصلًا لإصلاحات شجرة الحسابات عبر كل المستأجرين، لذا يُفترض انسحابها لأي مستأجر عند إعادة إقلاع الخادم — **غير مُتحقَّق منه بشكل صريح لمستأجر ثانٍ منفصل في هذا الميلستون** (يتطلب بيئة متعددة المستأجرين فعلية).
