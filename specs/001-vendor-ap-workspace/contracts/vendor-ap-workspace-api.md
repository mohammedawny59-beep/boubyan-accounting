# API Contracts: Vendor / Accounts Payable Workspace Upgrade

This is an internal server-rendered web application (no public API consumers), so contracts are documented as request/response shapes rather than a formal schema-definition-language file. Every contract below is either **reused unchanged** or has exactly **one additive field** — no contract is broken or removed.

## Reused unchanged (zero backend modification)

### `GET /api/vendors/:id/statement`
- **Auth**: `requireAuth`, `requirePermission('vendors', 'view')`
- **Response**: `{ vendor: {id, name}, rows: [...], endingBalance: number, reconciliation: {statementBalance, glBalance, difference, reconciled} }`
- **Used for**: statement rows, running balance, AND the workspace summary card's reconciliation status (Decision 1 — single shared source).
- **Async-recency guard on the caller (finding AUDIT-VBWS-2, kept and simplified this round)**: this route itself is unmodified, but its caller, `loadVendorStatement()`, can still be invoked more than once in overlapping succession — a vendor switch, or reopening the same vendor's workspace a second time before an earlier call resolves. A single request-generation counter, incremented on every call and re-checked immediately before each of the function's four user-visible outcomes (not just its writes — its error branches too), discards a response if a newer call has since started — covering both the cross-vendor and same-vendor cases with one mechanism, not a vendor-id comparison. This guard applies to workspace reads only; there is no write-triggered re-invocation of this route anymore (ninth-round simplification — see research.md Decision 4). **Tenth round (finding STALE-TOAST-1)**: this route's own pre-existing error-toast catch block is also gated by the same check — a superseded call whose request to this route subsequently fails no longer surfaces a misleading "connection error" toast over whichever vendor is now actually active. **Eleventh round (finding STALE-TOAST-1-DOC-GAP)**: this bullet, and research.md Decision 4's own operative description, now both explicitly enumerate all four guarded outcomes (statement success write, vendor-bills success write, vendor-bills failure write, statement-fetch error toast) rather than only three — the tenth round added the fourth check but had not yet updated every document's own count of them. See research.md Decision 4 for the full reasoning.
- **Failure handling — never fabricates a zero balance or a reconciled status, twelfth round (finding STMT-FETCH-FAILURE-FABRICATES-ZERO, Decision 13, spec.md FR-024) — corrected thirteenth round (findings `T011-CATCH-FALLTHROUGH-OVERWRITES-ERROR-STATE` [CRITICAL], `T011-404-CHECK-INSERTION-POINT-FICTIONAL` [HIGH], `T011-WRONG-404-TASK-REFERENCE` [MEDIUM])**: this route's own non-2xx responses (a 500, a network error, this route's own pre-existing `404`, or a `200` with an unusable body) were previously indistinguishable, client-side, from an empty-but-valid response — `d = await r.json().catch(()=>({}))` with no `r.ok` check meant `d` silently became `{}`, and the resulting `balance = 0`/`rec = null` rendered identically to "vendor owes nothing, fully reconciled." **The twelfth round's first fix attempt did not actually work**: it added the `if (!r.ok) throw ...` check and rendered an error state inside the `catch` block, but never stopped the pre-existing, unconditional success-path render code from running immediately afterward and silently overwriting that error state — a CRITICAL fall-through the required final gate check caught before implementation. It also cited "the existing, pre-existing 404 check (T012, unaffected)" as an insertion anchor that does not exist in the live code under any task number. **Corrected mechanism**: the caller now resolves this fetch to one of three mutually exclusive outcomes — `'success'` (response ok, and the body has the minimum usable shape this contract documents: `Array.isArray(rows)` and `typeof endingBalance === 'number'`), `'notfound'` (status `404`, checked *before* the general `!r.ok` branch, since this route's `404` genuinely is pre-existing at server.js:6457-6458 — only the frontend check for it was fictional), or `'error'` (any other non-2xx, a network error, or an unusable `200` body) — and gates every render (the summary/reconciliation area, and the statement's activity section) behind that outcome, reusing the same real inline empty-state convention as every other no-data state in this feature (Decision 7), mirroring the vendor-bills fetch's own failure handling above. Because the outcomes are mutually exclusive, the existing recency guard need only be checked once, immediately before the three-way branch, not once per branch. The bill-level and AP-aging sections are unaffected and still render if their own, independent fetches succeeded — this holds unconditionally now, since there is no early `return` on any of the three outcomes, only on the recency-guard staleness check.

### `GET /api/vendors`
- **Auth**: `requirePermission('vendors', 'view')`
- **Response**: full `db.vendors[]` array (name, `accountId`, `phone`, `email`, `address`, `openingBalance`, ...).
- **Used for**: workspace identity/contact fields (client-side lookup by id — no `GET /api/vendors/:id` exists or is added, Decision 5).

### `GET /api/vendor-bills?vendorId=<id>&status=<status>`
- **Auth**: `requireAuth`, `requirePermission('vendors', 'view')`
- **Response**: array of bill objects (`id`, `billNumber`, `billDate`, `dueDate`, `grossAmount`, `paidAmount`, `creditedAmount`, `outstandingAmount`, `status`, `payments[]`, `credits[]`).
- **Used for**: Open Bills total, overdue amount, and the open-items list — all filtered client-side to `status !== 'CANCELLED' && status !== 'PAID' && outstandingAmount > 0.001` (Decision 4, finding F1).
- **Called from two independent places, each with its own array (finding I1 correction; redesigned this round to remove cross-array sync)**: this route itself is completely unmodified — zero backend change — but it has **two independent frontend callers**, each storing the result in its own variable: the pre-existing `loadVendorBills()` (AP tab, unchanged, still writes `_vbBills`) and the workspace's own `loadVendorStatement()` (T007), which stores its result in a **new, workspace-local variable, `_vndWorkspaceBills`** — not `_vbBills`. `loadVendorStatement()` never called this route before this feature (finding I1), and this data was never already available in the workspace's own code path (see research.md Decision 4/11).
- **Design simplification, ninth round — no more cross-array synchronization needed (closes findings J1/K1/K2/NEW-3/NEW-4/AUDIT-VBWS-1/AUDIT-VBWS-3/AUDIT-VBWS-4/UI-1/UI-2/UI-3/AUDIT-CLOSE-1/NEW-AUDIT-1/TRACE-1)**: sixth-through-eighth-round revisions of this document required T007's fetch to also assign into the AP tab's own `_vbBills`, because the workspace used to open `openVbDetail(id)` — which reads exclusively from `_vbBills` — directly, stacked on top of itself, requiring three further rounds of fixes for a CSS-stacking defect, an unsafe write-context marker, an incomplete close-affordance enumeration, and a same-vendor write race. The product decision this round removes that entire design: an open-item click (T016) now closes the workspace and navigates to the existing "Vendor Bills (AP)" tab, where the AP tab's own `loadVendorBills()` populates `_vbBills` itself, before the existing, unmodified `openVbDetail(id)` opens the bill in its normal, single-context home. `_vndWorkspaceBills` and `_vbBills` are now two fully independent arrays with no click-through path between them — nothing to keep synchronized, and no shared-state hazard to guard against.
- **`loadVendorBills()` itself gets a request-recency guard, tenth round (findings T015-STATUS-FILTER-NOT-SYNCED, T015-DOUBLE-LOADVENDORBILLS-NO-RECENCY-GUARD)**: unlike the ninth round's description above, `loadVendorBills()` is no longer left entirely "unchanged" — a fresh-perspective audit found the ninth round's navigation function (`openVendorBillFromWorkspace`, T016) raced against `showTab('vendorbills', ...)`'s own internal, unconditional `loadVendorBills()` call (public/index.html:6149), which fired *before* T016's filter sync and could resolve *after* T016's own deliberate, correctly-filtered call — silently overwriting `_vbBills` with stale data right as `openVbDetail(id)` tried to read it. T016 also never reset the AP tab's own `#vbStatusFilt`, which — since every open item is by definition non-`PAID`/non-`CANCELLED` — could silently exclude the target bill from every fetch if the user's last AP-tab visit left it on a non-matching value. Fixed with (a) both `#vbVendorFilt` and `#vbStatusFilt` now reset *before* `showTab(...)` is called, so its internal fetch already uses the correct filters, and (b) a small, new request-generation counter (`_vbBillsReqSeq`) added to `loadVendorBills()` itself, so whichever of any two overlapping calls to it was *started* later always wins — regardless of network resolution order. This is the smallest necessary change (three lines: capture, two re-checks) — not a general request framework — and incidentally hardens the AP tab's own pre-existing behavior too (e.g. rapid filter changes), not only this feature's new caller.
- **Resetting `#vbVendorFilt` earlier exposed a DOM-population-order dependency, eleventh round (finding T016-VENDOR-FILTER-SYNC-RACE)**: moving the vendor-filter assignment to before `showTab(...)` (the fix immediately above) assumed `#vbVendorFilt` already had a real `<option>` for `currentVendorId` to select — but under this feature's own primary use case (opening a vendor's workspace directly, no prior AP-tab visit), it did not: real vendor `<option>`s are injected only by `populateVbVendorSelects()` (public/index.html:13458-13464), itself called only from inside `loadVendorBills()`/`openVendorBillModal()`, never from the Vendors-tab code path the workspace is opened from. Assigning `.value` on a `<select>` with no matching option silently no-ops. **Fix**: `openVendorBillFromWorkspace(id)` now calls the existing, unmodified `populateVbVendorSelects()` explicitly, once, as its very first step — the same function `loadVendorBills()` already calls as its own first line, just invoked one step earlier, reading from `DB.vendors`, which is guaranteed already loaded (the workspace could not have opened at all otherwise). No manual `<option>` construction, no new function.
- **The resulting AP-tab filter change is an explicit product decision, eleventh round (finding T016-FILTER-RESET-UNDOCUMENTED-UX-SIDEEFFECT)**: `openVendorBillFromWorkspace(id)` mutates the AP tab's own real, persistent, shared `#vbVendorFilt`/`#vbStatusFilt` controls — scoping them to the workspace's vendor and to all statuses is the deliberately intended outcome of this navigation (the user has just indicated, by clicking, that this vendor's AP context is what they want next), not an accidental side effect to be mitigated. No capture/restore of the AP tab's prior filter state is added — see spec.md's Assumptions section and research.md Decision 4 for the full product rationale.
- **Async-recency guard (finding AUDIT-VBWS-2, kept and simplified this round to a request-generation counter)**: same mechanism as noted on `GET /api/vendors/:id/statement` above — this fetch's response is discarded, untouched, if a newer `loadVendorStatement()` call has since started, whether due to a vendor switch or a same-vendor reopen. Workspace reads only; there is no write-triggered re-invocation of this route anymore.
- **Failure handling (finding I1, now spec-anchored per finding J2 — spec.md FR-023)**: if this fetch fails, the workspace's bill-level section (Open Bills, overdue amount, open items, next-open-item preview) shows a clear load/error state — reusing the same real inline empty-state convention as every other no-data state in this feature (Decision 7) — never a fabricated `0`/empty result, and no automatic retry or write. This failure-state write is gated by the same recency check as the success path (closing findings AUDIT-VBWS-2-GAP-1/TRACE-3, which found the prior round's guard never explicitly named this branch). The statement/reconciliation section is unaffected and still renders if its own, independent fetch to `GET /api/vendors/:id/statement` succeeded (Decision 12).
- **Deep-link reentrancy (finding T015-NO-REENTRANCY-GUARD, tenth round)**: T016's navigation function gets its own small, independent request-generation counter (`_vndDeepLinkSeq`, separate from `loadVendorBills()`'s own `_vbBillsReqSeq` above — each guards a different function's own concern) — captured when a click starts, re-checked immediately before `openVbDetail(id)` is called. If a second, newer click starts before the first's own `await loadVendorBills()` resolves, the first call's check fails and it never opens its bill — only the latest click's bill ever opens, with no visible flash of an older one.

### `POST /api/vendor-bills/:id/pay`, `POST /api/vendor-bills/:id/credit`, `POST /api/vendor-bills/:id/cancel`, `POST /api/vendor-bills/:id/payments/:paymentId/reverse`
- **Auth**: `requireAuth`; `requirePermission('vendors', 'edit')` for **pay** and **credit**; `requirePermission('vendors', 'delete')` for **cancel** and **reverse-payment** — **corrected wording, finding NEW-6**: earlier revisions of this document (and of `plan.md`'s Constitution Check) claimed all four actions share a single `requirePermission('vendors','edit')` gate. That is factually wrong: `server.js` gates cancel (line 6418) and reverse-payment (line 6260) with `requirePermission('vendors','delete')`, not `'edit'` — verified directly against the live source, and confirmed as a deliberate, pre-existing split in `lib/defaults.js`'s own role-definition comments (lines 99-106). This matters because the **accountant** role — spec.md's own named persona for this feature — has `vendors:['view','add','edit']`, with no `'delete'`; that role can pay and credit a bill but would get a 403 attempting to cancel it or reverse a payment through this feature's deep link, exactly as it would attempting the same action from the AP tab directly today.
- **This feature does not change, expand, or promise any of this (finding NEW-6, explicit correction)**: the workspace's deep link (T016) is a plain navigation to the existing "Vendor Bills (AP)" tab and its existing, unmodified bill-detail modal — it does not touch RBAC, does not grant any new permission, and does not promise that every role reaching the modal via this navigation can perform every action inside it. Existing server-side permissions remain fully authoritative, exactly as they already are for the two pre-existing AP-tab call sites this feature reuses unchanged. A user who could already perform any of pay/credit/cancel/reverse from the AP tab today can do exactly the same thing — no more, no less — after reaching the same modal via this feature's navigation; a user who could not (e.g. an accountant attempting cancel/reverse) gets exactly the same 403 they would get today.
- **Used for**: the write actions reachable from the AP tab's bill-detail modal, all reused with zero modification — not introduced or altered by this feature.

### Legacy-journal-row deep link — corrected, no API call at all (`/speckit-analyze` finding G1); not read-only (correction, finding H4)
- **This is not an HTTP contract.** The prior version of this document incorrectly named `GET /api/journal/:id` and `viewJournal(id)` here — neither is what the app actually uses for this interaction, and `viewJournal(id)` in particular opens the wrong, editable view (`#journalModal`). The corrected, verified target is: `showLedgerEntry(id)` (public/index.html:9329-9407), which opens `#ledgerEntryModal` (public/index.html:15589) — the app's existing detail view for a journal/ledger entry, already used for every other "click a journal/ledger row" affordance in the app (journal list row click, ledger tab row click, global search).
- **Not read-only (finding H4 correction)**: `#ledgerEntryModal` has its own pre-existing, unmodified Edit (`lemEditCurrent()` → `editJournal(id)`) and Delete (`lemDeleteCurrent()` → `DELETE /api/journal/:id`) actions in its footer — exactly as it already does everywhere else it's used today. Those actions remain governed by their own existing, unmodified server-side gates (`requirePermission('journal','edit')`, `requirePermission('journal','delete')` — server.js:8986, 9077), entirely independent of this feature. **This feature's own contribution is view/navigation only**: it does not create a new edit path, does not bypass any RBAC check, and does not grant any new permission. A user who could already edit/delete that entry from the ledger tab today can do exactly the same thing after clicking through from here — no more, no less.
- **No new request to open it**: `showLedgerEntry(id)` reads `id` out of `DB.journalEntries`, an array already loaded into the client at session start (via the app's existing initial data bootstrap) — opening the modal makes zero additional server call, so there is no new backend "Auth" gate to state for the act of opening it. Any Edit/Delete action taken *inside* the modal uses the pre-existing, already-gated routes named above, unaffected by this feature.
- **Used for**: legacy-journal-row deep link target (Decision 3).

## Modified (one additive query parameter)

### `GET /api/ap-aging?asOf=<date>` → `GET /api/ap-aging?asOf=<date>&vendorId=<id>`
- **Auth**: unchanged — `requirePermission('financials', 'view')` (inherited by the new parameter; no new permission introduced, Decision 6).
- **Current behavior**: returns `{ asOf, rows: [{vendor, total, buckets, count, items}, ...], grandTotal, reconciliation }` for **every** vendor, grouped by vendor name.
- **New behavior when `vendorId` is present** *(corrected, `/speckit-analyze` finding G2 — see research.md Decision 2 for the full reasoning)*: the server resolves `vendorId` → that vendor's current `name`, **explicitly null-guarded** (finding H2 correction — never a bare `.find(...).name` chain, which would throw for an unknown id):
  ```
  const matchedVendor = db.vendors.find(v => v.id === vendorId);
  const vendorName = matchedVendor ? matchedVendor.name : null;
  ```
  This is **not** "the same approach" as `GET /api/vendor-bills`'s `?vendorId=` filter (that route matches a real `b.vendorId` field directly; `rows` here is grouped by name across every source, a pre-existing characteristic of this endpoint that this feature does not change). If no vendor matches the given id, `vendorName` is `null` and the filter below naturally yields an empty `rows` — safe, matching the T005 pattern for the same endpoint's existing unknown-id case; it never throws and never fabricates a vendor.
- **Filter placement — firm-wide vs. vendor-scoped, made explicit (finding H3 correction)**: `rows`, `subledgerTotal` (→ `grandTotal`), and `reconciliation` are all still computed exactly as today, from the **full, unfiltered** `rows` array — this computation order is unchanged. The `vendorId` filter is applied only to a separate, response-only variable, built immediately before the response is sent, never to the variable those two aggregate figures were already derived from:
  ```
  const responseRows = vendorId ? rows.filter(r => r.vendor === vendorName) : rows;
  res.json({ asOf: asOfStr, rows: responseRows, grandTotal: subledgerTotal, reconciliation });
  ```
  **Confirmed scope (this was always the intent — no product decision needed, only a mechanical gap to close)**: `rows` (in the response) becomes vendor-scoped when `vendorId` is present; `grandTotal` and `reconciliation` remain firm-wide in every case. A targeted test (T002) asserts a `?vendorId=`-filtered response's `grandTotal`/`reconciliation` equal the unfiltered response's, for the same `asOf` date.
- **Known, pre-existing, documented limitation (not introduced by this feature)**: `rows` is grouped by vendor **name**, not id, for every source this endpoint already aggregates — including `accruedExpenses[]` items, which carry no `vendorId` field at all (only a free-text name/description). Two vendors sharing an exact name string already merge into one row under the endpoint's own unmodified logic, before this filter is ever applied. This feature's `vendorId` filter does not create, worsen, or attempt to silently resolve this collision — it surfaces exactly the same row the unfiltered response already shows under that name, which is the fail-safe choice: never guess which same-named vendor an ambiguous accrued-expense entry belongs to. Fixing the underlying name-based grouping architecture is explicitly out of scope for this feature (Principle X).
- **Backward compatibility**: omitting `vendorId` preserves today's exact firm-wide response — this is a strictly additive, opt-in filter, not a breaking change. The existing `/api/ap-aging`-driven aging tab (`loadAgingAP()`) is unaffected.
- **Bucket logic**: completely unchanged (`current`/`days30`/`days60`/`over90`, `<=30`/`31-60`/`61-90`/`>90` days) — only the `rows` filter is new.
