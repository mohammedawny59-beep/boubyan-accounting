# Quickstart: Vendor / Accounts Payable Workspace Upgrade

Validation-only guide — no implementation code. All steps use isolated, non-production data per constitution Principle III/IV; nothing here touches production, demo, or any real Mongo instance.

## Prerequisites

- Node.js + the project's existing `npm install` (no new dependencies added by this feature).
- The project's existing isolated test pattern: `DB_FILE_ONLY=true`, a per-run temp `DATA_FILE`/`CONFIG_FILE` under `os.tmpdir()`, and a strong `JWT_SECRET` + `ADMIN_DEFAULT_PASSWORD` — the exact bootstrap already used by `tests/p0-7-ap-lifecycle.test.js` and `tests/p3-vendor-statement-hotfix.test.js`.
- A test dataset containing at least one vendor with: an opening balance, one fully paid bill, one partially paid bill, one fully unpaid overdue bill, and at least one legacy (pre-vendorBills) journal-entry line posted directly to that vendor's payable account — the existing `tests/p3-vendor-statement-hotfix.test.js` fixtures already build exactly this shape and can be reused/extended rather than authored from scratch.

## Manual / exploratory validation scenarios

Each scenario below maps to a Success Criterion in `spec.md` and can be run against a local dev instance with test data loaded (never production).

1. **SC-001/SC-002 (owed amount, overdue amount within 30s)** — Open the workspace for the mixed-history test vendor. Confirm the current GL payable balance, statement balance, Open Bills total, and overdue amount are all visible without navigating away.
2. **SC-006 + Clarification Q1 (reconciliation agreement)** — On the same vendor, confirm the reconciliation status/difference shown on the summary card is byte-identical to the reconciliation shown at the bottom of the full statement. Compare the two numbers directly — they must always match, by construction (Decision 1), not by coincidence.
3. **Clarification Q2 (date filter doesn't move reconciliation)** — Apply a date range filter to the statement that excludes the opening balance row. Confirm the row list narrows but the reconciliation summary's numbers do not change.
4. **SC-003 (open items)** — Confirm the open-items list shows exactly the partially paid and unpaid bills, not the fully paid one, each with the correct remaining balance.
5. **SC-007/SC-008 (legacy compatibility, no double-counting)** — Confirm the legacy journal-entry row appears exactly once, is visually marked as legacy, and the statement's ending balance still matches the GL.
6. **User Story 4 (aging agreement)** — Compare the vendor's aging buckets shown in the workspace against that same vendor's row in the firm-wide `/api/ap-aging` report (or the aging tab UI) — bucket totals must match exactly.
7. **Clarification Q3 (RBAC unchanged)** — Log in as a role that currently cannot see vendor data (e.g. `receptionist`) and confirm the workspace and all its underlying requests are still denied exactly as they are today — no new access, no new restriction beyond today's behavior.
8. **Edge case — reconciliation mismatch** — Using a fixture with a deliberately introduced GL/statement difference (isolated test data only), confirm a clear warning with the exact difference is shown, and confirm no data was altered by simply viewing it.

## A note on two figures that may legitimately disagree (finding F10)

The open-items list's "overdue" flag (`dueDate < today`) and the AP aging breakdown's "current" bucket (`days <= 30` past due) are two different, both-pre-existing, both-unchanged concepts. A bill 1-30 days past its due date will correctly show as **overdue** in the open-items list while still sitting in the aging breakdown's **current** bucket in the same workspace. This is not a bug in this feature and is not something to "fix" by changing either calculation — both reuse their existing, unmodified definitions (Principle VII). If this is confusing to accountants in practice, that is a product decision for a future milestone, not a defect in this one.
