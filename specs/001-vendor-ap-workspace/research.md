# Phase 0 Research: Vendor / Accounts Payable Workspace Upgrade

All research below was performed by reading the actual current code on `chore/spec-kit-adoption` (== production baseline `b94693e` + Spec Kit tooling only) and independently re-verified line-by-line. Every "Decision" resolves an item that would otherwise be a `NEEDS CLARIFICATION` in Technical Context.

## Decision 1: Reconciliation is computed once and shared

**Decision**: The workspace summary card and the full statement both read their reconciliation status from the **same single fetch** of `GET /api/vendors/:id/statement` — its `reconciliation` object (`{statementBalance, glBalance, difference, reconciled}`) is used for both UI pieces. No second reconciliation calculation is written anywhere.

**Rationale**: This endpoint already computes reconciliation exactly once, via `buildBalanceMap(db, null, null)` (server.js:14556) — the same canonical helper used by `/api/trial-balance` and `/api/reports/balance-sheet`. This satisfies clarification Q1 (single shared check) by construction, without writing any new calculation.

**Alternatives considered**:
- A new dedicated "vendor summary" endpoint duplicating the reconciliation math — rejected: violates Principle VII (Canonical Calculations) and reintroduces exactly the risk Q1 asked about.
- Two separate fetches of the same endpoint (one for the card, one for the statement) — rejected: same backend logic either way, but wastes a network round-trip and opens a window where the two could reflect different data if fetched at different moments. One fetch, reused for both, is strictly safer.

## Decision 2: Per-vendor AP aging needs one small, precedented backend addition — with an explicitly documented, pre-existing matching limitation

**Decision**: Add an optional `?vendorId=` query filter to `GET /api/ap-aging` (server.js:8728), applied to `rows[]` before the response is built. Bucket-calculation logic (`current`/`days30`/`days60`/`over90`) is untouched.

**Corrected matching strategy (revised after `/speckit-analyze` finding G2 — do not redesign AP aging's existing name-based grouping; document its limitation instead)**: `GET /api/ap-aging`'s response already contains a genuine per-vendor breakdown (`rows[]`, one entry per vendor with `total`/`buckets`/`items[]`) — but **every** row, from **all three** of the endpoint's existing sources, is grouped by vendor **name** (`i.vendor`), not vendor id — this is a pre-existing, unmodified characteristic of the whole endpoint, not something specific to one source.

**Null-guarded resolution (revised after `/speckit-analyze` finding H2 — never chain `.name` off a possibly-missing lookup)**: the filter resolves `vendorId` explicitly, never chaining `.find(...).name` directly:
```
const matchedVendor = db.vendors.find(v => v.id === vendorId);
const vendorName = matchedVendor ? matchedVendor.name : null;
```
If `vendorId` does not resolve to an existing vendor, `vendorName` is `null` and the subsequent `rows[].filter(r => r.vendor === vendorName)` naturally yields an empty array — the exact safe, empty, non-erroring result T005 requires. This never throws and never fabricates a vendor. (The earlier draft of this Decision chained `.find(...).name` directly, which would have thrown a `TypeError` for exactly the unknown-vendor case T005 tests — corrected here.)

This is **not** "the same approach" `GET /api/vendor-bills`'s own `?vendorId=` filter uses (that route matches a real `b.vendorId` field directly, server.js:6116 — a genuinely different, ID-based mechanism). The two prior versions of this document incorrectly conflated them; corrected here.

**Filter placement — which fields stay firm-wide, which become vendor-scoped (revised after `/speckit-analyze` finding H3)**: the existing route already computes, in this order, before any response is built: (1) `rows[]` — the per-vendor breakdown; (2) `subledgerTotal` (→ the response's `grandTotal`), derived from summing across **all** of `rows[]`; (3) `reconciliation` (`subledgerTotal`/`glTotal`/`difference`/`reconciled`), also derived from the **full**, unfiltered `rows[]`. None of this computation order changes. The `vendorId` filter is applied **only** to a separate, response-only variable, built immediately before `res.json(...)` — never to the `rows` variable those two aggregate figures were already computed from:
```
const responseRows = vendorId ? rows.filter(r => r.vendor === vendorName) : rows;
res.json({ asOf: asOfStr, rows: responseRows, grandTotal: subledgerTotal, reconciliation });
```
**Explicit scope, confirmed unambiguous — no product decision needed**: `rows` (in the response) becomes vendor-scoped when `vendorId` is present. `grandTotal` and `reconciliation` remain firm-wide in every case, filtered or not — this was always this contract's stated intent (see the "Backward compatibility" line in contracts/vendor-ap-workspace-api.md, present since this Decision was first written); the gap H3 found was purely that the *implementation instruction* hadn't said *where* to apply the filter to guarantee that intent mechanically, not any ambiguity about what the intent was. Filtering `rows` before step (2) instead — the literal risk H3 flagged — would have silently turned `grandTotal`/`reconciliation` vendor-scoped too, contradicting this contract. T002 now includes an explicit assertion that a `?vendorId=`-filtered response's `grandTotal`/`reconciliation` equal the unfiltered response's, for the same `asOf` date.

**Documented limitation, not fixed by this feature**: two of the endpoint's three sources carry a true vendor id (`vendorBills[].vendorId`, vendor `openingBalance` records via `v.id`) — but the third, `accruedExpenses[]` (server.js:8737-8750), carries **no `vendorId` field at all**, only a free-text `vendor`/`description` name. If two vendors share an exact name string, their rows already merge into one under the endpoint's own current, unmodified grouping — before this filter is ever applied. This feature's `vendorId` filter does not create, worsen, or attempt to silently resolve that collision: it surfaces exactly the same row the unfiltered response already shows under that name — the deliberate fail-safe choice (never guess which same-named vendor an ambiguous accrued-expense line belongs to). Redesigning the endpoint's grouping architecture to be id-safe end-to-end is explicitly out of scope (Principle X) and is not attempted here.

**Rationale**: A near-identical structural precedent (an additive `?vendorId=` query filter on an existing list route) exists at `GET /api/vendor-bills` (server.js:6116), even though the underlying matching mechanism necessarily differs given `/api/ap-aging`'s own pre-existing name-based grouping.

**Alternatives considered**:
- Client-side filtering of the full firm-wide aging response by vendor name — rejected: pulls the entire firm-wide computation to show one vendor, for no safety benefit over the equivalent server-side filter (the same name-collision characteristic exists either way, since it is inherent to the endpoint's own data, not to where the filtering happens).
- A brand-new vendor-scoped aging endpoint with true per-source id matching (including adding a `vendorId` field to `accruedExpenses[]` records) — rejected: would require modifying the pre-existing AP-aging data model itself, violating Principle VII and Principle X (No Uncontrolled Scope Expansion) far beyond what this feature's scope allows.

## Decision 3: Deep-linking reuses the existing "Record Workspace" pattern — the *target* views are unchanged; the *access route* to reach the bill-side target from this feature's new UI is a plain navigation, not a nested modal (redesigned, ninth round — see Decision 4 for the full replan rationale)

**Decision**: Vendor-bill deep links reuse `openVbDetail(id)` / `#vbDetailModal` (public/index.html:13568-13575) unchanged as the target view — reached, as of this round, by first navigating to the existing "Vendor Bills (AP)" tab (closing the vendor workspace as part of that navigation), never by opening `#vbDetailModal` stacked on top of the still-open workspace. Legacy-journal-row deep links reuse **`showLedgerEntry(id)` / `#ledgerEntryModal`** (public/index.html:9329-9407 / 15589) unchanged as the target view, following the same pattern already established by `goToJournalSource()` (public/index.html:8322-8348, explicitly commented "Record Workspace, Part J") for fixed-asset and patient-receivable records — **entirely unaffected by this round's redesign**, since it never opened a nested modal in the first place; `#ledgerEntryModal` is reached directly from the statement row, in the workspace's own context, with no navigation step.

**Product decision, ninth round — why the bill-side access route changed**: sixth, seventh, and eighth `/speckit-analyze` rounds each found genuine new UI-state-lifecycle defects in the design of stacking `#vbDetailModal` on top of the still-open `#vendorStmtModal` (a shared CSS z-index requiring an override, a write-context marker requiring careful capture-before-write timing, close-affordance enumeration gaps, a same-vendor write race). Rather than patch a fourth time, the product decision this round is to remove the nested-modal design entirely: an open-item click now reuses the application's own pre-existing "redirect to AP" pattern (the exact same one `recordVendorPayment()` already uses, public/index.html:9802-9808) — close the workspace, navigate to the AP tab, sync its vendor filter, let its own `loadVendorBills()` populate `_vbBills`, then call the existing, unmodified `openVbDetail(id)` in its normal, single-context home. See `tasks.md` T015 for the exact function, and Decision 4 below for the full list of removed mechanisms and why each is no longer needed.

**Citation correction (finding NEW-1, documentation-only, preserved from the seventh round)**: this Decision previously cited `openVbDetail(id)` at "public/index.html:13489-13607" — verified directly against the source, `function openVbDetail(id)` actually starts at line 13568 and its body ends at line 13575; line 13489 is inside the unrelated `renderVendorBills()` table-rendering loop, and the `<div id="vbDetailModal">` markup itself is at line 4841 (neither matches the range this Decision previously cited). The corrected citation above now matches the one Decision 4 and `tasks.md` T015 already had correct.

**Correction after `/speckit-analyze` finding F2**: neither deep-link is automatically "free." The bill-side click handler is wired by a dedicated task (T015) precisely because it does not exist today. The legacy-journal-row equivalent likewise does not exist today — the statement's `<tr>` elements for `type:'legacy-journal'` rows (public/index.html:9780-9789) currently carry no `onclick` at all — so it requires its own equally small wiring task (see plan.md/tasks.md Phase 5), not an assumption that it comes for free. What genuinely is "reused unchanged" is only the *target* modal/function on both sides (`openVbDetail`/`#vbDetailModal` and `showLedgerEntry`/`#ledgerEntryModal`) — never a new detail view.

**Second correction after `/speckit-analyze` finding G1 — this is not a cosmetic naming fix, it is a correctness fix**: an earlier draft of this Decision, and of `plan.md`, `tasks.md`, `quickstart.md`, and `contracts/vendor-ap-workspace-api.md`, incorrectly named the target function as `viewJournal(id)`. That function is real (public/index.html:8510-8527) but opens a **completely different, editable** modal, `#journalModal` — the same modal used to create a brand-new journal entry, with a visible "✏️ تعديل" (Edit) affordance that repoints the form at `PUT /api/journal/:id`. `viewJournal(id)` cannot open `#ledgerEntryModal` at all — the two are unrelated functions targeting unrelated modals. The correct function, verified directly against the source, is `showLedgerEntry(id)` (public/index.html:9329), confirmed by `document.getElementById('ledgerEntryModal')` at line 9335 — the same function every other existing "click a journal/ledger row" affordance in the app already calls (the journal list's row click and view-action button, the ledger tab's row click, and global search). All five affected documents are corrected as of this revision.

**Third correction after `/speckit-analyze` finding H4 — `#ledgerEntryModal` is not read-only, and this Decision must not claim it is**: an earlier draft of this correction called `showLedgerEntry(id)`/`#ledgerEntryModal` a "read-only detail view," which is factually wrong. `#ledgerEntryModal`'s own footer (public/index.html:15589-15633) has fully-wired Edit (`lemEditCurrent()`, line 9419, which itself opens `editJournal(id)` — the exact editable path this Decision's G1 correction exists to avoid reaching *directly* from this feature) and Delete (`lemDeleteCurrent()`, line 9427, which calls `DELETE /api/journal/:id`) buttons. The accurate description: `#ledgerEntryModal` is the app's existing, unmodified **detail view**, which happens to also expose its own pre-existing Edit/Delete actions — exactly as it already does everywhere else it's used today (the journal list, the ledger tab, global search). Those actions remain governed by their own existing, unmodified server-side gates, `requirePermission('journal','edit')` and `requirePermission('journal','delete')` (server.js:8986, 9077) — independent of, and unaffected by, the `('vendors','view')` gate on the statement route this feature adds a click-through from. **This feature's own contribution is view/navigation only**: it does not create a new edit path, does not bypass any existing RBAC check, and does not grant any new permission — a user who could already edit/delete that journal entry from the ledger tab today can do exactly the same thing after clicking through from this feature's statement row, no more and no less. Per constitution Principle V, safety here correctly rests on the unmodified server-side permission checks, not on the view being non-mutating.

**Rationale**: Both target views already exist and are the app's own established deep-link precedent — no new detail view or backend route is needed for either; only a one-line `onclick` wiring is new on each side. `showLedgerEntry(id)` makes **zero additional server request** to open — it reads `id` from the already-loaded client-side `DB.journalEntries` array — so opening the deep link itself introduces no new backend contract at all (see contracts/vendor-ap-workspace-api.md's corrected entry); any subsequent Edit/Delete action a user takes from inside that modal was already possible today and remains gated exactly as it is today.

**Alternatives considered**: A new, unified "record inspector" component — rejected as an unnecessary generalization (Principle X; IMPLEMENTATION PREFERENCE's "minimal UI restructuring").

## Decision 4: Open items are derived from a genuinely new, explicit vendor-bills fetch (corrected after `/speckit-analyze` finding I1 — this data was never already available), filtered on status AND outstanding amount together

**Correction — the "already fetched" premise was false**: every earlier version of this Decision, and of `tasks.md` T007/T014, assumed `GET /api/vendor-bills?vendorId=<id>` was already being fetched somewhere in the workspace's own code path. Verified directly against the source, this is not true: `loadVendorStatement()` (the function the workspace's summary card extends) only ever calls `fetch('/api/vendors/${v.id}/statement')` — nothing else. The **only** existing caller of `GET /api/vendor-bills` anywhere in `public/index.html` is `loadVendorBills()` (line 13466), a wholly separate function belonging to the unrelated "Vendor Bills (AP)" tab, populating its own module-scoped `_vbBills` array scoped to whatever vendor its own `#vbVendorFilt` dropdown currently holds — not reliably the vendor whose workspace was just opened, and not guaranteed to have run at all before the workspace is opened. Compounding this, `db.vendorBills` has no entry in `lib/dataProjection.js`'s `COLLECTION_PERMISSION` table (grep-confirmed: zero mentions of `vendorBills` in that file), so it falls into that file's own documented "Unmapped key... fail closed, never leak" branch — meaning it is silently excluded from the global `GET /api/data` bootstrap payload for **every** role, including admin. There is no fallback global cache either. As originally planned, the workspace would have shown 0/empty Open Bills, overdue amount, and open items every time an accountant opened a vendor's workspace without having first, separately, visited the AP tab and selected that exact vendor in its own filter — directly breaking FR-004/FR-005/FR-006 and the P1/MVP success criteria SC-001–SC-003.

**Decision**: `loadVendorStatement()` (T007) performs a **second, genuinely new, explicit, additive fetch** — `GET /api/vendor-bills?vendorId=<id>` — in addition to its existing statement fetch. This reuses the existing, unmodified `GET /api/vendor-bills` route (server.js:6113, already used unchanged by the AP tab) with zero backend modification; it is a new *caller*, not a new *route*. The open-items list is derived from that response, filtering to **`status !== 'CANCELLED' && status !== 'PAID' && outstandingAmount > 0.001`** — status alone is not sufficient. "Overdue" is computed client-side as `dueDate < today && outstandingAmount > 0`. The result is stored in a **new, workspace-local variable, `_vndWorkspaceBills`** (module-scoped, declared alongside `currentVendorId`) — read by both T007's own summary-card rendering and T014's open-items list rendering (a single fetch, reused by both — the same "fetch once, reuse for both consumers" principle Decision 1 already applies to reconciliation), so the two never diverge and no second fetch is needed downstream.

**Design simplification, ninth round — the nested-modal design is removed, not patched a fourth time**: sixth, seventh, and eighth `/speckit-analyze` rounds progressively found — and each time correctly fixed, only for the audit to surface a new, adjacent gap — a chain of issues in the design of opening `#vbDetailModal` stacked on top of the still-open `#vendorStmtModal` and tracking "did this write originate from the workspace" to gate a refresh: `_vbBills` cross-contamination (I1, J1, K1), an unsafe `currentVendorId`-as-context-proxy (K2, NEW-3), a duplicate-fetch trade-off (NEW-4), a CRITICAL CSS-stacking defect that made the whole mechanism invisible (AUDIT-VBWS-1/UI-1), an async-staleness gap (AUDIT-VBWS-2), an unsafe read-after-write-completes timing bug (AUDIT-VBWS-3), an incomplete close-affordance enumeration (UI-2, AUDIT-CLOSE-1, NEW-AUDIT-1), an ordering ambiguity (AUDIT-VBWS-4), a two-distinct-strings implementation risk (UI-3), and a same-vendor write race the guard couldn't catch (TRACE-1). Each fix was individually correct; the pattern across three rounds — nested-modal-plus-context-tracking kept revealing new edge cases under deeper scrutiny — was the actual signal. The product decision this round is architectural, not another patch: **remove the nested modal**. An open-item click no longer opens `#vbDetailModal` from inside the workspace at all. Instead, `openVendorBillFromWorkspace(id)` (T015) reuses the application's own, already-established "redirect to AP" pattern — the exact same one `recordVendorPayment()` already uses (public/index.html:9802-9808) — extended by one step to also open the specific bill once there: close the workspace, navigate to the "Vendor Bills (AP)" tab, sync `#vbVendorFilt` to `currentVendorId` (K1's original one-line precedent, still valid and still used — just now as part of a real navigation rather than a same-page state sync), let the AP tab's own, completely unmodified `loadVendorBills()` populate `_vbBills`, then call the existing, unmodified `openVbDetail(id)` — which now opens in its normal, single-context home, never stacked over another modal.

**Why this closes every finding above by removing its premise, not by adding a counter-mechanism**:
- **I1/J1/K1's `_vbBills` cross-contamination** is closed because `_vbBills` and the workspace's own `_vndWorkspaceBills` are now two fully independent arrays, serving two fully independent contexts, with no click-through path between them left to synchronize. T007 no longer assigns into `_vbBills` at all.
- **K2/NEW-3's write-context tracking, NEW-4's duplicate fetch, AUDIT-VBWS-3's capture-before-write fix, AUDIT-VBWS-4's ordering fix, TRACE-1's same-vendor write race** are all closed because there is no more write-triggered workspace refresh — a write made from the AP tab's own detail modal only ever affects the AP tab's own state, exactly as it always did before this feature existed. The workspace itself is a pure read/analysis surface; nothing it displays is refreshed by a write, because nothing in this feature ever triggers a write from inside the workspace anymore.
- **AUDIT-VBWS-1/UI-1's CRITICAL modal-stacking defect** is closed because there is no longer a second modal to stack — `#vbDetailModal` is reached only after `#vendorStmtModal` has already been closed by the navigation, exactly as it always was for the two pre-existing AP-tab call sites. **Correction, owner-review remediation round (finding `VBWS-CONC-1`)**: this closure claim held only within a single vendor's own deep-link flow — it did not hold across the full asynchronous gap if the user opened a *different* vendor's workspace while an earlier vendor's deep-link chain was still in flight, since `_vndDeepLinkSeq` was previously invalidated only by a newer deep-link click, never by `openVendorStatement()` starting a new vendor context. A stale chain could still complete and call `openVbDetail()` for the earlier vendor's bill after the new vendor's workspace was already open, silently resurfacing once the new workspace was closed. Fixed by incrementing `_vndDeepLinkSeq` inside `openVendorStatement()` itself, so opening any vendor's workspace — not just clicking a deep link — invalidates any older, still-in-flight chain. Live-verified: vendor A's deep-link started, vendor B's workspace opened before A resolved, A's chain confirmed to terminate silently (`openVbDetail` never fires), and closing B's workspace afterward does not resurface A's bill detail. Latest-click-wins within one vendor's own workspace is unaffected.
- **UI-2/AUDIT-CLOSE-1/NEW-AUDIT-1's close-affordance enumeration problems** are closed because there is no more workspace-origin flag (`_vbDetailFromWorkspace`) to reset at any close affordance, anywhere.
- **UI-3's two-distinct-onclick-strings risk** is closed because T015 no longer touches either of the two pre-existing AP-tab call sites at all — they remain exactly, byte-for-byte, what they always were.

**Async request-recency guard for the workspace's own reads (finding AUDIT-VBWS-2) — kept, and simplified this round to a request-generation counter; scope made explicit and complete, eleventh round (finding STALE-TOAST-1-DOC-GAP)**: `loadVendorStatement()` still needs a staleness guard, because switching vendors (or reopening the same vendor a second time before an earlier call resolves) can still let a slower response overwrite a newer, already-rendered one — this property has nothing to do with the removed nested-modal design and remains fully in scope. The eighth round's guard (capture `currentVendorId`, re-check at each write point) correctly handled a vendor switch but — per finding TRACE-1 — never detected two overlapping calls for the *same* vendor, since the vendor id never changes between them. This round's required design, and the simpler, more robust replacement: a single monotonically-increasing counter, `let _vndStmtReqSeq = 0;`, incremented at the top of every `loadVendorStatement()` call (`const seq = ++_vndStmtReqSeq;`), re-checked (`if (seq !== _vndStmtReqSeq) return;`) immediately before **every** user-visible-state-mutating outcome the function can produce — not three, but four:
1. the statement/reconciliation success write (`vndStmtKpis`/`vndStmtBody`/the reconciliation badge),
2. the vendor-bills-derived success write (`_vndWorkspaceBills = data;` plus the Open Bills/overdue figures),
3. the vendor-bills fetch's own failure-state write (T008 — a clear load/error state, never a fabricated zero), and
4. the pre-existing statement fetch's own error-toast branch (finding STALE-TOAST-1, eleventh-round correction to this operative paragraph — the tenth round added this fourth check to `tasks.md` T007 but never mirrored it into this paragraph, leaving Decision 4's own description of "every write point" incomplete and inconsistent with the actual requirement).

A superseded request must produce **no** visible trace at all once it is no longer the active call — not stale data, not a stale empty/error state, and not a stale toast; the same single check, applied identically at all four points, guarantees this uniformly. One mechanism, one check per outcome, covers a vendor switch (the newer call increments the counter, making the earlier one stale) *and* a same-vendor double-open (the newer call still increments the counter, same effect) — no separate reasoning needed per case, and no separate reasoning needed per success-vs-failure branch either, closing AUDIT-VBWS-2-GAP-1/TRACE-3 (the prior guard's success-only scoping) as a direct side effect of using a counter instead of an identity comparison. This guard applies to workspace *reads* only, per this round's explicit scope: there is no write-triggered refresh left to guard, because there is no write-triggered refresh at all anymore.

**Gap in this guarantee found by owner-review remediation round 2 (finding `VND-STALE-DISPLAY-ON-VENDOR-SWITCH`, HIGH) — "no visible trace of a superseded *response*" is not the same as "no visible trace of the *previous* vendor"**: the `_vndStmtReqSeq` guard above correctly prevents an old vendor's *response*, once it arrives, from overwriting a newer vendor's already-rendered data — but it does nothing for the interval *before* either response arrives. A fresh, independent re-review found that clicking from an already-loaded vendor A straight into vendor B updated only the title/contact line synchronously; every other section (KPI cards, reconciliation badge, statement table, open-items table — including A's bill ids still live in their `onclick` handlers — and the aging section) kept showing vendor A's correctly-rendered data, unchanged, until vendor B's fetches resolved. This was never a stale-response bug (A's data was genuinely current for A when it was drawn) — it is a missing synchronous reset at the start of a new vendor context, a gap the counter guard was never designed to cover.

**Fix**: `loadVendorStatement()` now performs a synchronous reset of the entire workspace view — KPI cards, reconciliation badge, statement table, open-items preview/table, and aging section, plus `_vndWorkspaceBills`/`_vndStmtRows` themselves — to an explicit loading placeholder as its first action, before the `seq = ++_vndStmtReqSeq` capture and before any `fetch()` call. This is additive to the existing guard, not a replacement for it: the synchronous reset guarantees no *stale* vendor's data is ever visible while a new vendor's request is in flight; the counter guard (unchanged) continues to guarantee that whichever request resolves is the *correct* (latest-requested) one to render. Live-verified together: opening vendor A, then vendor B before A's slower response arrives, then letting A's response resolve after B's — A's data never reappears at any point, and B's own data renders once, only from B's own response.

**Alternatives considered, ninth round**: A fourth patch to the nested-modal design (e.g., fixing AUDIT-CLOSE-1's braces, adding the two missed close-affordance resets from NEW-AUDIT-1, adding a request-generation lock for TRACE-1 on top of the existing flag) — rejected: each individual fix is small, but three rounds of "small fix reveals next gap" is itself the evidence that the design's complexity is disproportionate to what it buys (a same-page detail view, when a one-navigation-step redirect to an identical, pre-existing detail experience is available at a fraction of the state-management cost). Keeping the vendor-id-comparison guard from the eighth round and adding a *second*, separate mechanism just for the same-vendor case — rejected: a single generation counter already covers both cases with less code, not more, and removes the need to reason about two guards interacting. Threading the write handler's already-fresh bill data back into the workspace via some cross-context channel to keep the "instant refresh" UX the nested-modal design offered — rejected as unnecessary complexity for a benefit (avoiding one extra navigation click) this feature's own scale does not require; the user reaches the identical, correct, existing detail experience either way.

**The simplified navigation itself needed hardening, tenth round (findings T015-STATUS-FILTER-NOT-SYNCED, T015-DOUBLE-LOADVENDORBILLS-NO-RECENCY-GUARD, T015-NO-REENTRANCY-GUARD)**: a dedicated fresh-perspective audit of the ninth round's `openVendorBillFromWorkspace(id)` — the replacement for the removed nested modal — found it was not itself reliably correct, even though it introduced no nested-modal state. Three concrete gaps, all in the navigation function itself, none related to the removed design:

- **A never-reset AP-tab status filter silently defeats the deep link (HIGH)**: `loadVendorBills()` applies `#vbStatusFilt`'s value as an AND-filter alongside the vendor (public/index.html:13469-13470), and any bill reachable through this deep link is by definition never `PAID`/`CANCELLED` (Decision 4's own open-item filter). The ninth round's function synced only `#vbVendorFilt`, never `#vbStatusFilt` — if the user's last AP-tab visit left that filter on `PAID` (or anything else), every fetch this function triggers would exclude the target bill, and `openVbDetail(id)`'s bare `.find()` + `if (!b) return;` would silently no-op, under entirely ordinary use.
- **`showTab('vendorbills', ...)`'s own internal `loadVendorBills()` call races the deliberate one (HIGH)**: `showTab()` unconditionally calls `loadVendorBills()` itself the moment the AP tab activates (public/index.html:6149) — and in the ninth round's draft, this fired *before* the function's own `filt.value = currentVendorId` sync line, using the *stale*, pre-sync vendor filter. Two overlapping fetches, no guarantee the later-started (correct) one resolves last, and `loadVendorBills()` had no recency guard of its own to arbitrate them.
- **No reentrancy guard (MEDIUM)**: rapid clicks on two different open items each scheduled an independent, uncoordinated chain, producing redundant fetches and "last-response-wins" rather than "last-click-wins."

**Fix**: two small, independent, module-scoped counters, mirroring the exact pattern this Decision already established for `loadVendorStatement()` — not a shared mechanism, not a general request framework:
1. `loadVendorBills()` itself (a *pre-existing* function, modified this round for the first time) gets its own `_vbBillsReqSeq` counter, checked before its own writes to `_vbBills` and before its own `renderVendorBills()` call — so whichever of any two overlapping calls to it was *started* later always wins, regardless of network resolution order. This benefits the AP tab's own pre-existing behavior too (e.g. rapid filter changes), not only this feature's new caller.
2. `openVendorBillFromWorkspace(id)` gets its own `_vndDeepLinkSeq` counter, captured at entry and re-checked immediately before calling `openVbDetail(id)` — so a newer click always suppresses an older, still-in-flight one's detail-open, with no visible stale-bill flash.

Both filter assignments (`#vbVendorFilt`, and now `#vbStatusFilt`) move to *before* `showTab(...)` is called, so `showTab`'s own internal fetch and the function's own explicit, awaited fetch always target the same, correct filters — the arbitrary `setTimeout(..., 150)` (a timing guess papering over the stale-filter problem, not fixing it) is removed entirely in favor of an explicit `await`.

**Moving the filter-sync earlier exposed a real, pre-existing DOM-population-order dependency, eleventh round (finding T016-VENDOR-FILTER-SYNC-RACE, HIGH)**: `#vbVendorFilt` (public/index.html:3119) is declared in the page's static markup with only a single, hardcoded empty `<option>` — every real vendor `<option>` is injected exclusively by `populateVbVendorSelects()` (public/index.html:13458-13464), which reads from the already-loaded `DB.vendors` array and is itself called only from inside `loadVendorBills()` (its own first line) or `openVendorBillModal()` — **never** from `loadVendors()`, the function backing the Vendors tab a workspace is normally opened from. Under the exact primary use case this feature targets — opening a vendor's workspace *directly*, with no prior "Vendor Bills (AP)" tab visit in the session — `#vbVendorFilt` therefore still holds only its single empty option at the moment `filt.value = currentVendorId` runs, and per standard `HTMLSelectElement` behavior, assigning a value with no matching `<option>` silently fails (`selectedIndex` stays `-1`; `.value` reads back `''`). The tenth round's fix (moving this assignment *before* `showTab(...)`, to close the double-fetch race) did not create this defect — the underlying DOM-population dependency already existed — but it did move the assignment to a point in execution where that dependency had not yet been satisfied, exposing it as a live, blocking bug rather than one that happened to already be masked.

**Fix**: call the existing, unmodified `populateVbVendorSelects()` explicitly, once, as the very first step inside `openVendorBillFromWorkspace(id)` — before either filter is set. This is the exact same function `loadVendorBills()` already calls as its own first line; reusing it here, one step earlier, requires no new function, no manual `<option>` construction, and no change to `populateVbVendorSelects()` itself. It reads from `DB.vendors`, which is guaranteed already loaded by this point — the workspace itself could not have resolved `currentVendorId` to open in the first place (`loadVendorStatement()`'s own `(DB.vendors||[]).find(...)`) without `DB.vendors` already being populated, independent of whether the AP tab has ever been visited. With the real `<option>` list already present, `filt.value = currentVendorId` now succeeds, and the subsequent `loadVendorBills()` call (both `showTab`'s own internal one and the function's own explicit, awaited one) correctly scopes to the intended vendor.

**Product decision, eleventh round, finding T016-FILTER-RESET-UNDOCUMENTED-UX-SIDEEFFECT — the filter change is intentional, not an accidental side effect**: `openVendorBillFromWorkspace(id)` sets `#vbVendorFilt` to the workspace's own vendor and resets `#vbStatusFilt` to its neutral/all-statuses value every time it runs — these are the AP tab's own real, persistent, shared filter controls, not a local copy, so this is a genuine, visible change to state the user may have set deliberately on an earlier, unrelated AP-tab visit. **Explicit product-owner decision**: this is accepted, intended navigation-context behavior, not an unwanted side effect to be mitigated. When a user deep-links from vendor A's workspace into vendor A's AP context, landing on an AP tab scoped to vendor A (and to all statuses, so the deep-linked bill is never accidentally hidden) is the *expected* result of that navigation — the user has just told the application, by clicking, that vendor A's AP context is what they want to see next. No capture/restore mechanism for the AP tab's prior filter state is introduced; the "cost" of this design (a user's independently-set AP-tab filter being replaced by the workspace's context on next use of this deep link) is accepted as the simpler, correct trade-off, consistent with treating the AP tab's filters as reflecting "what the user is currently looking at," not as durable, cross-session preferences requiring preservation. This closes the finding by making it an explicit, documented decision rather than an undiscussed side effect — see spec.md's Assumptions section and `quickstart.md` Scenario 23 for the corresponding requirement-level and acceptance-level statements of this same decision.

**Alternatives considered, eleventh round**: Manually constructing the needed `<option>` element(s) for `currentVendorId` instead of calling `populateVbVendorSelects()` — rejected: would duplicate existing, working logic (name lookup/escaping, the "all vendors" default option) the app already has a single source of truth for, and would drift from it over time. A new, dedicated "ensure vendor options are populated" helper — rejected as unnecessary generalization (Principle X) when the existing function already does exactly this, unconditionally, safely, and idempotently. Capturing and restoring the AP tab's prior filter values after the deep-linked bill's detail is closed — rejected per the explicit product decision above: the filter change is the intended outcome of this navigation, not a defect to work around.

**Alternatives considered, tenth round**: A single, shared counter for both `loadVendorBills()`'s own write-guard and the deep-link function's own open-guard — rejected: the two guard different concerns (one function's DOM/state writes; a different function's decision to call a third function), and conflating them would require `loadVendorBills()` to expose its internal sequence number to its caller, a tighter coupling than two small, independent counters using the identical, already-established pattern. Preventing `showTab()`'s own internal `loadVendorBills()` call from firing at all (e.g. by adding an "already active" early-return inside `showTab()`) — rejected: `showTab()` is a shared, heavily-used function with no such guard for any of its other tab dispatches today; adding one here would be a broader behavior change to existing, working code for every caller, not a minimal, scoped fix. A debounce/lock that disables the open-item rows themselves during an in-flight navigation — rejected as unnecessary once the sequence counter already makes rapid clicks resolve correctly without needing to prevent them.

**Rationale (revised after `/speckit-analyze` finding F1)**: The bill object already carries `dueDate`, `outstandingAmount`, and `status` (server.js:6044-6058). The bill lifecycle's documented states are `POSTED → PARTIALLY_PAID → PAID`, or `→ CANCELLED` — but that state machine is **not exhaustive of every path to a zero balance**: `postVendorBillCredit()` (server.js:6318-6364, the handler behind `POST /api/vendor-bills/:id/credit`) updates `creditedAmount` and `outstandingAmount` but **never touches `bill.status`** (unlike the payment path, server.js:6216, which does). A bill fully offset via credit notes alone therefore never reaches `status === 'PAID'` — it stays `POSTED` or `PARTIALLY_PAID` forever with `outstandingAmount ≈ 0`. A status-only filter would incorrectly keep showing it as open, directly violating FR-007 ("A fully paid **or fully credited** bill MUST NOT appear in the open-items list" — spec.md already stated this correctly; the bug was in this Decision's originally-proposed filter, not in the requirement). The corrected three-part filter is not new semantics — it is the exact existing pattern this codebase already uses correctly for the same purpose at `server.js:8754` (`GET /api/ap-aging`'s own subledger-outstanding filter: `b.status !== 'CANCELLED' && b.status !== 'PAID' && b.outstandingAmount > 0.001`). Reusing that precedent keeps this feature's "open" definition consistent with the one the firm-wide AP aging report already uses (also required by FR-013's aging-agreement requirement).

**Alternatives considered**: A server-side `?openOnly=1` convenience filter on `GET /api/vendor-bills` — a reasonable minor optimization, but not necessary for correctness at the spec's own stated "typical volume" scale (SC-009); noted as an optional future optimization, not required by this plan. Filtering on status alone (an earlier, now-corrected proposal) was considered and rejected for the reason above. Relying on `loadVendorBills()`'s existing `_vbBills` cache instead of a dedicated fetch (the original, now-corrected finding-I1 assumption) — rejected: that cache is scoped to a different, independently-selected vendor filter and is not guaranteed to exist at all when the workspace is opened directly, which is exactly the defect finding I1 identified.

## Decision 10: Vendor search (FR-016) stays a minimal inline enhancement, verified manually — reverted from a shared-module extraction (finding H1, accepting the `/speckit-analyze` recommendation; supersedes the prior version of this Decision, which proposed finding G3's extraction)

**Reversal**: The prior version of this Decision proposed extracting the `#vndSearch` matching logic into a standalone, `require()`-able shared function so Jest could unit-test it with zero DOM involvement. Re-analysis (finding H1) found this was not the small change it was framed as: making one function both `require()`-able by Jest *and* callable from `renderVendors()` inside `public/index.html`'s inline `<script>` block would have required inventing this codebase's **first-ever** browser-loadable local shared script — a genuinely new loading pattern (a dual CommonJS/global-export wrapper, plus a new `<script src>` tag), since the file currently has zero local `<script src>` precedent (its only external `<script src>` is a CDN import) and Jest's default `node` test environment has no mechanism to reach code living inside an HTML file's inline script. That is architecture, not extraction, and it directly contradicted this same plan's own Structure Decision ("no new modules"). Accepted and reverted.

**Decision**: The `#vndSearch` matching logic stays exactly where it is today — inline inside `renderVendors()` (public/index.html:9613-9668) — minimally extended in place to also match on account code, not just name. No new file, no new module, no new loading pattern, no new search framework.

**What the inline change actually is (correcting finding H7's "pure relocation" framing too)**: today's inline predicate (`if (search && !v.name.toLowerCase().includes(search)) return false;`) matches on vendor **name only** — there is no existing account-code matching anywhere in `renderVendors()` today. This is not, and was never, a pure relocation of already-existing logic: the existing name-match is preserved unchanged, and account-code matching is a small, genuinely **additive** behavior, required by FR-016 ("vendor search by name or code"), added directly to the same inline condition (e.g. `if (search && !v.name.toLowerCase().includes(search) && !String(v.accountId).toLowerCase().includes(search)) return false;`). It is a safe superset change — it can only surface additional matches, never hide previously-visible ones.

**Verification**: manual, via `quickstart.md`'s dedicated search scenario — the same class of verification already accepted for the two DOM-click cases (legacy-journal deep link, open-item deep link). A unit test was judged achievable in isolation for a pure predicate, but not without inventing new codebase architecture to reach it from Jest, which is a materially bigger and more scope-expanding change than the one-line matching enhancement itself — disproportionate for this feature.

**Rationale**: Matches the explicit instructions "no new search framework," "no new browser module architecture," "minimal inline enhancement only." The manual scenario directly verifies FR-016's actual requirement (name match, code match, non-match) without inventing infrastructure this codebase has never needed before.

**Alternatives considered**: The shared-file extraction (the prior version of this Decision) — reverted, see above. A new bundler/build step purely to make one function importable both ways — rejected as wildly disproportionate to a one-line matching enhancement (Principle X).

## Decision 12: Vendor-bills fetch failure degrades independently — never fabricates zero AP (added after `/speckit-analyze` finding I1; now anchored to spec.md FR-023 per finding J2)

**Decision**: `loadVendorStatement()`'s two fetches (statement, vendor-bills) are independent and fail independently. If the vendor-bills fetch (T007) fails: the bill-level section (Open Bills total, overdue amount, open-items list, next-open-item preview) shows a clear load/error state — reusing the same real inline-style convention as every other empty/no-data state in this feature (Decision 7) — rather than silently rendering `0`/empty as if that were a confirmed, correct answer. The statement/reconciliation portion of the workspace still renders normally if *its own* fetch succeeded — one fetch failing does not make the whole workspace unusable. **This is no longer plan-only guidance — it is a directly traceable requirement**: spec.md's FR-023 (added per finding J2) states this exact behavior as an approved MUST, including "no automatic retry, no write side effect," closing the traceability gap the second `/speckit-analyze` pass identified.

**Rationale**: Showing a fabricated `0` for Open Bills on a fetch failure would be actively misleading — indistinguishable from a vendor that genuinely has no open bills — which is worse than showing nothing, for an accounting-adjacent figure. Degrading only the affected section (not the whole modal) keeps the parts of the workspace that *did* load successfully useful, consistent with this feature's general principle of additive, non-destructive enhancement.

**Alternatives considered**: Failing the entire workspace open (showing nothing at all) if either fetch fails — rejected: the two fetches are genuinely independent pieces of information, and a statement/reconciliation-only view is still useful on its own if only the bills fetch fails. Silently treating a fetch failure as "zero open bills" — rejected: this is exactly the "do not fabricate data" risk called out for the vendor-not-found case (Decision 9), applied here to a different failure mode.

## Decision 13: The statement/reconciliation fetch's own failure must degrade the same way, never fabricating a balance or a reconciled status (added twelfth remediation round, finding STMT-FETCH-FAILURE-FABRICATES-ZERO)

**The gap**: Decision 12 gave `loadVendorStatement()`'s *vendor-bills* fetch exhaustive, careful failure treatment — but the function's other, more fundamental fetch, `GET /api/vendors/:id/statement` (the source of the workspace's own headline GL balance, statement balance, reconciliation badge, and full statement activity — T009/T010's entire summary card, and the pre-existing statement body T014/T017's own rendering sits alongside), never received the same treatment. Verified directly against the live, pre-fix source (public/index.html:9753-9790): the existing `try { const r = await fetch(...); d = await r.json().catch(()=>({})); } catch { showToast(...); }` block has no `r.ok`/status check before parsing and no `return` in its `catch` — so *any* failure other than the pre-existing, separately-handled 404 (a network error, a 500 with a JSON error body, or an unparseable response) falls through silently: `d` stays `{}`, `balance = d.endingBalance || 0` becomes `0`, and `rec = d.reconciliation || null` becomes `null` — which the reconciliation badge (T010) renders identically to "genuinely reconciled," since it only warns `if (rec && !rec.reconciled)`. A failed load is therefore visually indistinguishable from "this vendor owes nothing and is fully reconciled" — the exact fabricated-confirmed-data outcome Decision 12/FR-023 already forbids for the neighboring fetch. This is not a pre-existing, out-of-scope defect this feature merely inherits: T007 already edits this exact `catch` block (to add the `_vndStmtReqSeq` recency check, finding STALE-TOAST-1), and T009/T010 are this feature's own brand-new UI, newly and prominently displaying the fabricated result — the plan is already inside this code path and already depends on its output for a new, more consequential purpose than before.

**Decision, corrected thirteenth round**: the twelfth round's own version of this Decision described a fix that does not actually work against the live code, and cited a 404 check that does not exist — both caught by the required final gate check (findings `T011-CATCH-FALLTHROUGH-OVERWRITES-ERROR-STATE`, CRITICAL; `T011-404-CHECK-INSERTION-POINT-FICTIONAL`/`T011-WRONG-404-TASK-REFERENCE`, HIGH/MEDIUM; all three adversarially confirmed, none refuted). The corrected mechanism:

1. **Track the outcome explicitly, don't rely on a bare `return`**: a `return` in the `catch` block would also have wrongly skipped T007's independent vendor-bills fetch later in the same function — breaking the very independence guarantee this Decision requires. Instead, `loadVendorStatement()` sets a local `outcome` (`'success' | 'notfound' | 'error'`, starting pessimistic at `'error'`) as it resolves the fetch, and gates every statement-dependent render behind it — see the full code sketch in tasks.md T011.
2. **Build the 404 branch here, not "after an existing check"**: no 404/status check of any kind exists in the live `loadVendorStatement()` today — a full-file grep confirms zero matches. The twelfth round's text claimed to insert its general-failure check "after the existing, pre-existing 404 check (T012, unaffected)"; T012 is verification-only and owns no code, and the task that was actually going to add 404 handling (T013) was sequenced to run *after* this one. T011 now checks `r.status === 404` *before* its own general `!r.ok` check, building both branches itself, in the correct order, in one place — removing the false "pre-existing" framing rather than just correcting which task number it pointed to.
3. **Validate the payload shape, not just the HTTP status**: a `200` response with an unusable body (not valid JSON, or missing/wrong-typed `rows`/`endingBalance`) must not be treated as success merely because `r.ok` was true — `outcome` only becomes `'success'` when `Array.isArray(parsed.rows)` and `typeof parsed.endingBalance === 'number'` both hold, per the shape already documented in `contracts/vendor-ap-workspace-api.md` (`{ vendor, rows: [...], endingBalance: number, reconciliation: {...} }`, server.js:6523-6526). Anything short of that falls to the same `'error'` outcome as a network failure or a non-2xx status.
4. **Render a genuine load/error state, not fabricated data**: for `outcome === 'error'`, replace the summary-card/reconciliation area (`vndStmtKpis`, T009/T010) and the full statement's activity section (`vndStmtBody`) with a clear load/error state, reusing the real inline empty-message convention (Decision 7) — never `0`, never an absent-therefore-reconciled badge, never an empty-but-confirmed activity table. For `outcome === 'notfound'`, the same two elements get the vendor-not-found state (finding G4, unaffected by this correction). The existing `showToast(...)` call is retained for the `'error'` outcome only, not `'notfound'`.
5. **One recency check covers all of it**: because the three outcomes are mutually exclusive and nothing asynchronous happens between the recency check and any of the three renders, a single `if (seq !== _vndStmtReqSeq) return;` placed immediately before the three-way branch — not repeated once per branch — is sufficient and covers the success write, the not-found write, the error write, and the error toast alike (finding STALE-TOAST-1's guarantee, and Decision 4's four-outcome enumeration, both still hold).

**Independence preserved**: the bill-level (open items, T007/T014) and AP-aging (T024) sections continue to render normally if their own, independent fetches succeeded — Decision 12's independence guarantee already established this in one direction (statement failing doesn't degrade bills); this Decision confirms it holds in the other direction too (a failed, not-found, or malformed statement fetch doesn't touch the bill-level or aging sections' own, separately-guarded rendering), and — corrected this round — is now actually true in code, not just in the failure-render branch that a fall-through bug would have overwritten. One fetch failing never makes the whole workspace unusable, and no fetch's failure is ever presented as a confirmed, correct result.

**This is a directly traceable requirement**: spec.md's FR-024 states this exact behavior as an approved MUST, mirroring FR-023's own structure; its wording ("a network error, a server error, or an unusable response") already covers the malformed-payload case without needing an edit.
