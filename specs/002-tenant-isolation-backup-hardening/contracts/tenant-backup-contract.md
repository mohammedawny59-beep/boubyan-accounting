# Contract: Tenant-Scoped Backup (D)

**Revised in Design Remediation Pass 1, corrected again in a second and third pass, extended seventh, eighth, ninth, tenth, eleventh, twelfth, and thirteenth passes**: scope narrowed to exactly three categories (research.md Decision 10), idempotency exclusion made real and extended to `__restoreLock__` (Decision 8), a mandatory default-duplicate pre-flight added (Decision 16), file-mode output shape fully defined and corrected to skip genuinely-absent-or-null keys (Decision 9), category digests added with a precisely-specified canonicalization and a shared `_id`/`__v`-stripping helper reused at every digest computation point (Decision 6, third pass). Seventh pass (CRITICAL): a mandatory non-default tenant existence/active-status pre-check is added (research.md Decision 21, spec.md FR-007) — a narrow, deliberate exception to Decision 10's payload-exclusion rule, not a reversal of it. Seventh pass (MEDIUM): the tool's own operator-facing error text MUST be Arabic (research.md Decision 22), matching `scripts/restore.js`'s own existing convention. Eighth pass: the seventh pass's own file-mode fallback for the existence check (treating a missing file as "does not exist") was itself unsafe — it could reject a genuinely real, active tenant that has simply never yet triggered a durable write — and is withdrawn; file mode does not enforce this check at all. Eighth pass, HIGH: a mandatory audit-event requirement is added (research.md Decision 23, spec.md FR-037), closing a gap present, unexamined, across all seven prior passes against this project's own constitution (Principle XI, Auditability). **Ninth pass**: `auditLog` is added to `TENANT_BACKUP_ENTITY_KEYS`'s exclusion filter (research.md Decision 8, ninth-pass extension), closing a self-destruction hazard the eighth-pass audit requirement itself introduced; the audit-event metadata fields are unified with the restore contract's own; and a per-tenant backup-file retention policy is added (research.md Decision 24, spec.md FR-038), closing a previously-unexamined lifecycle gap for the backup file's own indefinite plaintext-secret exposure. **Tenth pass, HIGH (this header line itself was never updated to mention this pass — eleventh-pass correction)**: the ninth pass's own retention-matching logic was itself found unsafe — a raw string-prefix match could let one tenant's own rotation delete a hyphen-prefix-colliding different tenant's backup files (e.g. `acme` vs. `acme-corp`) — corrected to an exact-equality match on the fixed-width-stamp-stripped tenantId (research.md Decision 24's tenth-pass correction), with a new Guarantees bullet and a new collision-specific Test contract item 12a. **Eleventh pass (this parenthetical's own fix reproduced the identical omission it names — twelfth-pass correction)**: the eleventh-pass edit that added the "eleventh-pass correction" parenthetical above was itself an edit to this header line, but the opening clause's own pass-list still stopped at "tenth" until now — corrected to include "eleventh" as well. **Twelfth pass (this header's own opening clause reproduced the identical self-referential omission one level deeper, inside the very sentence naming the "eleventh" fix — thirteenth-pass correction, in the same edit that added "twelfth" and "thirteenth" to the opening clause above)**: `tasks.md`'s T026/T036 test-case numbering for this file's suite is reconciled with this contract's own canonical numbering (see `tasks.md` for the fix; no change to this contract's own Test contract items was needed, since they were already the authoritative numbering the other document now matches).

New CLI script: `scripts/tenant-backup.js`. New npm script: `backup:tenant`. Does not modify `scripts/backup.js`/`npm run backup` in any way.

## Invocation

```
node scripts/tenant-backup.js --tenant=<tenantId>
```

`--tenant=` required, no default, no positional fallback. Missing/empty → usage + exit `1`, nothing written. `--tenant=default` is valid and is the primary way to back up the current production clinic under the new, safer format.

## Pre-flight (default tenant only) — MUST run and pass before anything else

For `--tenant=default`: scan every logical identity matched by `_defaultTenantFilter` (a `User.id`, an `EntityChunk`/`AppConfig` `key`) and count distinct physical documents per identity. **Any identity with more than one document → hard-fail**, printing the exact category + identity + both documents' `_id`s, and write **no** backup file (research.md Decision 16, spec.md FR-026). This is a detection gate, not a repair — the tool never merges or guesses.

## Pre-flight (non-default tenant only, Mongo mode) — NEW, seventh pass, CRITICAL, MUST run and pass before anything else

For any `--tenant=` other than `default`, and only when `MONGO_URI` is set (Mongo mode): `const tenant = await Tenant.findOne({tenantId}).lean(); if (!tenant || tenant.status !== 'active') { <hard-fail> }` — reusing `lib/tenantMiddleware.js:72-73`'s existing pattern verbatim (research.md Decision 21, spec.md FR-007). On failure, print `❌ المستأجر "<tenantId>" غير موجود أو غير نشط — رُفض النسخ الاحتياطي، لم يُكتب أي ملف.` and write **no** backup file. This is a single, discarded, read-only existence/status read — it never becomes part of the backup payload, and does not reverse research.md Decision 10's payload-exclusion rule for `Tenant`/`Subscription` (see that decision's own seventh-pass narrowing note). **In file mode, this check does not run at all (research.md Decision 21, corrected eighth pass)** — file mode has no `Tenant` registry to query, and file-existence is not a safe substitute (a genuinely real, active tenant that has never yet triggered a durable write has no file on disk either, which the withdrawn seventh-pass file-mode heuristic would have wrongly rejected); a file-mode backup for a non-`default` tenant proceeds unconditionally and simply produces zero records for a tenant that has never persisted anything, consistent with spec.md's own "brand-new signup" Edge Case.

## Output file format

See `data-model.md` → "New logical file format 1". `{scope:'tenant', schemaVersion:1, tenantId, createdAt, source, recordCounts:{users,entityChunks,appConfigs}, categoryDigests:{users,entityChunks,appConfigs}, collections:{users,entityChunks,appConfigs}}`. **No `tenants`/`subscriptions` field of any kind** — `Tenant`/`Subscription` are out of scope for this tool entirely (research.md Decision 10); this backup is never described as a "full tenant backup," only as covering users, accounting data, and configuration. Written to `backups/tenant-<tenantId>-<stamp>.json` + `.sha256` sidecar.

## Source selection

- `MONGO_URI` set → Mongo mode.
- Else → file mode: `default` reads `data/database.json`/`data/config.json` (unchanged paths); any other tenant reads exactly `data/tenants/<sanitized-tenantId>.json` and `data/tenants/<sanitized-tenantId>.config.json` (the new per-tenant config file, research.md Decision 2) via the exported `_tenantFilePath()`/`_tenantConfigFilePath()` helpers.

## Mongo-mode collection queries

| Category | Filter |
|---|---|
| `users` | `_defaultTenantFilter` if `tenantId==='default'`, else `{tenantId}` |
| `entityChunks` | same tenant filter, plus `key: {$in: TENANT_BACKUP_ENTITY_KEYS}` — **never raw `ENTITY_KEYS`** (research.md Decision 8; `TENANT_BACKUP_ENTITY_KEYS` is `ENTITY_KEYS` minus `'idempotencyRecords'` and, as of the ninth pass, minus `'auditLog'` too, exported from `lib/database.js`) |
| `appConfigs` | same tenant filter, `key:'config'` |

`IdempotencyRecord` (the dedicated model) is never queried. `Tenant`/`Subscription` **data** is never queried as part of this table — the sole exception is the Pre-flight step above's single existence/status read, which returns nothing that ever reaches this table's queries or the output payload (research.md Decision 10's payload-exclusion rule, narrowed seventh pass by Decision 21). Mongo mode naturally returns only chunks that actually exist for the tenant — no undefined-data risk here (that risk is specific to the file-mode transform below).

## File-mode transform (unified shape, research.md Decision 9)

`collections.users = blob.users`; `collections.appConfigs = [{tenantId, key:'config', data: <that tenant's config file content>, updatedAt: backupCreatedAt}]` if it exists, else `[]`.

**`collections.entityChunks` — corrected, second `/speckit-analyze` pass, tightened third pass**: `TENANT_BACKUP_ENTITY_KEYS.filter(key => blob[key] != null).map(key => ({tenantId, key, data: blob[key], updatedAt: backupCreatedAt}))` — **filtering out keys absent-or-null in the blob (`!= null` catches both `undefined` and an explicit `null`, matching Mongoose's own `required:true` validator), not mapping every key unconditionally** (Pass 1's bug). `passwordResets`/`errorLog` are real `ENTITY_KEYS` members absent from `emptyDBShape()`, so they are `undefined` for any tenant that never triggered a password reset or a logged error — mapping them unconditionally would insert a schema-invalid, `data`-less `EntityChunk` record and (absent `{ordered:false}`, see below) abort the whole category's insert on restore. `updatedAt` is the backup run's own `createdAt` (file storage tracks no per-key write time) — never meaningful per-record provenance for a file-mode-sourced backup.

The output shape is otherwise identical to Mongo mode's — a restore never needs to know which backend produced the file.

## Category digests

For each of `users`/`entityChunks`/`appConfigs`: `recordCounts.<cat> = collections.<cat>.length`; `categoryDigests.<cat> = computeCategoryDigest(collections.<cat>)`. `computeCategoryDigest()` (new, exported from `lib/backupValidation.js` alongside `computeChecksum()`) is `computeChecksum(canonicalJson(records.map(stripMongoMeta)))`, where `stripMongoMeta` strips `_id`/`__v` and `canonicalJson()` sorts each array by its stable identity field (`id` for `users`, `key` for `entityChunks`/`appConfigs`) **before** recursively sorting object keys at every depth.

**Critical, third pass**: the `_id`/`__v`-stripping is **mandatory here**, at backup-write time, even though `collections.<cat>` itself (the array actually written into the file) is **not** stripped for Mongo-sourced records — `collections.<cat>` keeps `_id` on each record, matching the existing, unmodified whole-instance `scripts/backup.js:41` precedent (`_id` is stripped only at restore time, `scripts/restore.js:40`). Without stripping *before hashing* at this backup-write step specifically, `categoryDigests` would be computed over `_id`-bearing records while restore's own recompute (over the already-`_id`-stripped staged records) and restore's live apply-time re-check (over a fresh, `_id`-bearing Mongo query, likewise stripped by the same helper) would never match it — permanently failing every Mongo-sourced tenant backup's own digest-integrity check and defeating the resume-skip mechanism entirely (research.md Decision 6). Using the single shared `computeCategoryDigest()` helper at all three computation points — this one, restore-staging's recompute, and restore-apply's live re-check — is what keeps them consistent; the array-sort half of `canonicalJson()` matters separately, because a later live-database re-query (during restore) carries no implicit stable order, and without it two logically-identical record sets could hash differently purely from ordering. Computed from the same in-memory arrays just written — never a second query.

## Audit trail (NEW eighth pass, HIGH; self-destruction hazard closed and metadata unified ninth pass — research.md Decision 23, spec.md FR-037, per this project's own constitution Principle XI)

On any terminal outcome — a written backup file, or a hard-fail from the default-duplicate pre-flight or the non-default existence/active-status pre-flight — call the canonical `appendAuditEvent()` (`lib/auditLog.js`) exactly once, never a hand-rolled event object, written to `default`'s own `auditLog` — the purpose mirrors `lib/tenantMiddleware.js`'s own existing precedent for cross-tenant accountability logging (not the target tenant's own log), though the actual write mechanism (a direct `EntityChunk` read-modify-write) is new to this codebase, not itself reused from that precedent; see research.md Decision 23 for the full distinction. `action:'tenant.backup'`, `resourceType:'tenant'`, `resourceId:<--tenant= value>`, `outcome:'success'|'failure'`, `metadata:{backupFingerprint, createdAt, recordCounts, categoryDigests}` on success (`backupFingerprint`/`createdAt` unified ninth pass with the restore contract's own shared minimum; `recordCounts`/`categoryDigests` are this tool's own extra context). **Ninth-pass addition**: the event's own `tenantId` field requires a synthetic `req:{tenantId:<--tenant= value>}` passed as `opts.req` — `buildAuditEvent()` has no other way to learn the target tenant from a bare CLI invocation; omitting this silently defaults every event's `tenantId` to `'default'`. **Ninth-pass, CRITICAL, closed at the root in research.md Decision 8**: `auditLog` is now excluded from `TENANT_BACKUP_ENTITY_KEYS`, so this centralized log — and every tenant's own `auditLog` — is never itself part of any tenant-scoped backup/restore payload, closing the hazard where a `default` restore would otherwise have silently reverted every tenant's accountability trail recorded here. Mongo-mode mechanics: same direct `EntityChunk{tenantId:'default',key:'auditLog'}` read-modify-write the restore contract's own audit-event section uses — see that contract for the exact sequence, including its own acknowledged, deliberately-deferred non-atomicity under concurrent invocations. No audit event is written for a plain early exit with no attempted action (e.g. missing `--tenant=`).

## Backup-file retention (NEW, ninth pass, MEDIUM; matching logic corrected tenth pass, HIGH — research.md Decision 24, spec.md FR-038)

On every successful invocation, after the backup file and its `.sha256` sidecar are written: list `backups/` for files matching `tenant-*.json`, then for each candidate extract its own embedded tenantId by stripping the fixed `tenant-` prefix, the fixed `.json` suffix, and the trailing 20 characters (the always-19-character `YYYY-MM-DDTHH-mm-ss` stamp plus its own separating hyphen), and keep only candidates whose extracted tenantId is **exactly equal** (`===`) to the target `tenantId` — never a `startsWith()`/prefix test, since real tenantIds may themselves contain hyphens (`server.js:1252-1254`'s own `<slug-derived-base>-<base36-timestamp>` generation, unsanitized by `_tenantFilePath()`'s hyphen-preserving filter), which would let rotating tenant `acme`'s own backups also match and delete tenant `acme-corp`'s (**tenth-pass correction — see research.md Decision 24 for the full defect and fix**); sort (the ISO-stamp naming already sorts chronologically); delete every file beyond the newest `TENANT_BACKUP_KEEP` (`process.env.TENANT_BACKUP_KEEP || 30`, mirroring `scripts/backup.js`'s own `BACKUP_KEEP` default), plus each deleted file's `.sha256` sidecar — never touching files belonging to any *other* tenant, or the whole-instance `backup-*.json` files `scripts/backup.js` already rotates separately. This is the same, already-proven rotation mechanism `scripts/backup.js:91-98` already runs for whole-instance backups — whose own filter structurally never matches this tool's `tenant-<tenantId>-...json` naming, so tenant-scoped backups were previously excluded from any rotation at all — applied here with a tenant-scoped, delimiter-safe filter and its own independent env-var override. A rotation failure (e.g. permissions) is logged as a warning, not escalated to a non-zero exit — the backup itself already succeeded.

## Guarantees

- No document belonging to any tenant other than `--tenant=` may appear anywhere in the output.
- `recordCounts`/`categoryDigests` are always computed from the exact arrays written, never re-derived later.
- Missing `--tenant=` fails before any Mongo connection or file read.
- A `default`-tenant backup with an undetected duplicate identity is impossible — the pre-flight above blocks it structurally.
- **A backup for a nonexistent or inactive non-default tenant is impossible, in Mongo mode (NEW, seventh pass; scope narrowed eighth pass)** — the existence/active-status pre-flight above blocks it structurally, before any entity-data read. File mode does not enforce this guarantee (see the Pre-flight section's own eighth-pass correction above).
- **A tenant's own `auditLog` history is never part of any backup, and the centralized accountability log this tool writes to is never reverted by any tenant-scoped restore, including of `default` (NEW, ninth pass)** — `auditLog` is excluded from `TENANT_BACKUP_ENTITY_KEYS`, structurally.
- **Tenant-scoped backup files do not accumulate indefinitely (NEW, ninth pass)** — the retention policy above bounds how many any single tenant's backups can reach on disk.
- **A tenant whose identifier is itself a hyphenated prefix of another tenant's identifier (e.g. `acme` and `acme-corp`) never has its retention rotation touch the other's files (NEW, tenth pass, HIGH)** — the exact-equality, fixed-width-stamp-stripping match above is structurally immune to the prefix-collision class of bug; see research.md Decision 24's tenth-pass correction.

## Test contract

1. Cross-tenant leakage (unchanged from original pass): seed A/B with a colliding `id`/`key`, back up A, assert zero B-owned documents.
2. Legacy inclusion: seed a legacy no-`tenantId`-field `default` user via the **raw driver** (spec.md FR-027 — not `Model.create()`), back up `default`, assert included.
3. Missing `--tenant=` exits non-zero, writes nothing.
4. Idempotency exclusion (NEW): seed a real `IdempotencyRecord` document and an `EntityChunk` with `key:'idempotencyRecords'` for the target tenant; back it up; assert neither appears anywhere in the output, and `TENANT_BACKUP_ENTITY_KEYS` (not `ENTITY_KEYS`) is confirmed (by import, not by re-implementing the filter in the test) to be the query source.
5. Default-duplicate pre-flight (NEW): seed a genuine duplicate identity for `default` (a legacy no-`tenantId` user and an explicit `tenantId:'default'` user sharing the same `id`, both via the raw driver); attempt a `default` backup; assert hard failure, exact identity named, zero file written.
6. `Tenant`/`Subscription` absence (NEW): confirm the output file has no `tenants`/`subscriptions` key at all, for both `default` (which has no such rows) and a real tenant (which does, but they must not appear).
7. **File-mode undefined-key handling (NEW, second pass)**: under `DB_FILE_ONLY=true`, back up an ordinary tenant that has never triggered a password reset or a logged error; assert the output's `collections.entityChunks` contains no `passwordResets`/`errorLog` entry at all (not an entry with `data:undefined`), and that `recordCounts.entityChunks` matches the actual filtered array length.
8. **`__restoreLock__` exclusion (NEW, second pass)**: seed an `EntityChunk` with `key:'__restoreLock__'` for the target tenant (simulating a leftover/stuck lock); back it up; assert it does not appear anywhere in the output, mirroring test 4's `idempotencyRecords` case.
8a. **`auditLog` exclusion (NEW, ninth pass)**: seed an `EntityChunk` with `key:'auditLog'` for the target tenant (real audit history); back it up; assert it does not appear anywhere in the output, mirroring test 4/8's cases — the exclusion is now enforced for a third key, not just the original two.
9. **Non-default existence/active-status pre-check, Mongo mode (NEW, seventh pass, MANDATORY)**: a `--tenant=` with no matching `Tenant` document hard-fails with an Arabic error naming the tenant identifier, before any file is written; a `Tenant` document with `status:'suspended'` or `status:'cancelled'` hard-fails identically; `--tenant=default` succeeds regardless of whether any `Tenant` row exists for it.
10. **File-mode existence check is deliberately not enforced (NEW, eighth pass, MANDATORY — closes a real defect in the seventh-pass file-mode design)**: under `DB_FILE_ONLY=true`, back up a non-`default` tenant identifier that has genuinely never persisted any data (no file exists at `_tenantFilePath(tenantId)`); assert the backup succeeds with zero records — **not** a hard failure — confirming the withdrawn "missing file means nonexistent" heuristic is not present anywhere in the implementation.
11. **Audit event (NEW eighth pass, MANDATORY; event `tenantId` and self-destruction assertions added ninth pass)**: a successful backup appends exactly one event to `default`'s own `auditLog` with `action:'tenant.backup'`, `resourceId` equal to the target tenantId, `outcome:'success'`, **and the event's own `tenantId` field equal to the real target (not `'default'`) — confirming the synthetic-`req` requirement is actually implemented** — and confirm the event is absent from the *target* tenant's own `auditLog` if the target is non-`default`. A hard-failed backup (e.g. the existence/active-status pre-flight) appends exactly one event with `outcome:'failure'` to the same log instead. **Ninth pass**: run a `default`-target restore afterward (or, more directly, a `default`-target backup then restore cycle) and confirm `default`'s own `auditLog` — including the events this test just appended — survives byte-for-byte except for whatever new event that restore itself appends, proving the `TENANT_BACKUP_ENTITY_KEYS` exclusion actually protects it.
12. **Backup-file retention (NEW, ninth pass, MANDATORY)**: with `TENANT_BACKUP_KEEP=3`, back up the same tenant 5 times; assert exactly 3 `tenant-<tenantId>-*.json` files (+ matching `.sha256` sidecars) remain, the 3 newest by timestamp; assert a *different* tenant's own backup files, and any whole-instance `backup-*.json` file, are completely unaffected by this tenant's own rotation.
12a. **Backup-file retention, hyphen-prefix collision (NEW, tenth pass, MANDATORY — closes the defect corrected in research.md Decision 24)**: create two real tenants with colliding hyphenated identifiers, one a literal string-prefix of the other (e.g. `acme` and `acme-corp`); with `TENANT_BACKUP_KEEP=3`, back up `acme-corp` 5 times, then back up `acme` once; assert `acme-corp` still has exactly 3 files (its own rotation) and `acme` has exactly 1 (its own single backup, untouched by `acme-corp`'s rotation) — a `startsWith()`-based match would fail this test by deleting `acme-corp` files during `acme`'s own rotation pass or vice versa.
