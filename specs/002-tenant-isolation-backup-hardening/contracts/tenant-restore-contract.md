# Contract: Tenant-Scoped Restore (E) + Offline Staging (F) + Restore Lock + Digest-Based Resume (G/H) + Whole-Instance Separation (H)

**Substantially redesigned in Design Remediation Pass 1, corrected through Passes 2, 3, 4, 5, 6, 7, 8, 9, 10, and 11.** The original `__restage__<tenant>__<runId>` live-Mongo synthetic-tenant staging design is **rejected outright** (research.md Decision 6) — it collided with `Tenant.slug`'s global uniqueness, with live-tenant `_id`s, and created a reachable authentication identity during staging. ## Invocation

```
node scripts/tenant-restore.js <backup-file> --tenant=<tenantId> --target=<label> [--yes] [--force-unlock]
```

`<backup-file>`, `--tenant=`, `--target=` all required, no defaults, no fallback to whole-instance behavior. `--force-unlock` is a distinct, explicit, logged flag — see "Restore Lock" below — never implied by `--yes`.

## Step -1 — Pre-Restore Quiesce Warning (printed unconditionally, before anything else, CRITICAL, fifth pass — research.md Decision 19)

Before argument parsing completes into any action, print a loud, unconditional warning (every invocation, not gated behind a flag): the target tenant's live application traffic should be quiesced — the server process serving it stopped, or that tenant otherwise prevented from accepting writes — **before** this restore begins, not only restarted after. A write accepted by a still-running server during Step 5's apply window can recreate a document the restore just deleted (colliding with the restore's own insert) or re-persist an already-applied category's stale, pre-restore state from that server's own in-memory cache — corrupting the restore while it runs, not merely reverting it afterward (research.md Decision 19, fifth-pass extension). This is a printed warning, not an enforced block — no write-blocking mechanism is built this phase (see Decision 19's own "considered and rejected" note); the operator's own judgment and process are what quiesce traffic, exactly as they already are for the existing whole-instance `scripts/restore.js`. **In Arabic (research.md Decision 22, seventh pass)**, e.g.: `⚠️ تحذير قبل البدء: أوقف حركة الطلبات الحية للمستأجر "<tenantId>" الآن (أو أوقف السيرفر الذي يخدمه) قبل متابعة هذه الاستعادة. أي كتابة تصل أثناء التطبيق قد تُفسد الاستعادة نفسها، لا أن تُلغيها لاحقاً فقط.`

## Step 0 — Restore Lock (acquire first, before anything else touches the backup file)

Research.md Decision 11. Reuses the existing `EntityChunk` compound unique index `{tenantId,key}` — no new model.

- **Acquire**: `EntityChunk.create({tenantId: target, key: '__restoreLock__', data: {runId, pid: process.pid, acquiredAt}})`. A concurrent second invocation for the same `target` hits a duplicate-key error (Mongo error `11000`) on the existing unique index and is rejected immediately, before opening or even reading the `<backup-file>` argument, printing the existing lock's `runId`/`pid`/age.
- File mode: `fs.writeFileSync(backups/.restore-checkpoints/<target>.lock, {...}, {flag:'wx'})`, same fail-fast semantics.
- **Release**: on any clean terminal outcome (`completed` or a caught `failed`), `EntityChunk.deleteOne({tenantId:target, key:'__restoreLock__', 'data.runId':runId})` (file mode: `fs.unlinkSync`) — conditioned on this run's own `runId`, so a stale release can never remove a different, newer lock.
- **Stale lock (process killed, not a clean failure) — no exception, ever (second pass correction)**: the lock is never automatically released, age-expired, or reclaimed via a process-liveness/`pid` check (unreliable across independent hosts — the lock must hold across independent machines pointed at the same database, where a local `pid` check is meaningless, and `pid`s can be reused across hosts/time anyway). A second invocation is rejected until an operator passes `--force-unlock` explicitly (logged, deliberate) — **including when the "second invocation" is simply resuming the very same restore after the very same crash**; there is exactly one lock policy, with no carve-out for the resume-after-crash case (Pass 1 left this inconsistent between documents — some implied a plain re-run would succeed after a kill; it does not).
- **`--force-unlock` is one atomic compare-and-delete-then-create, never a bare unconditional delete-then-create (second pass correction)**: (1) attempt `create()`; (2) on failure, **read** the existing lock document and delete it conditioned on **that specific lock's own `runId`** (`EntityChunk.deleteOne({tenantId:target, key:'__restoreLock__', 'data.runId': <the runId just read>})`); (3) attempt `create()` exactly once more; (4) if that also fails, exit non-zero reporting contention against whichever lock now exists. **No retry loop** — an unconditional delete-then-create pair would let two operators force-unlocking near-simultaneously both believe they hold the lock.
- `__restoreLock__` is deliberately **not** in `TENANT_BACKUP_ENTITY_KEYS`, so it is never itself swept into a tenant backup — and a backup file that illegitimately contains one is rejected by validation (Step 1.6 below), so it can never be planted via restore either. **(Third pass)** A dedicated unit test asserts `!ENTITY_KEYS.includes('__restoreLock__')` directly against the exported constant, independent of any backup/restore fixture — guarding against a future milestone ever hand-adding a real entity key with this exact name.

## Step 1 — Validation gate (reject BEFORE any file write, any Mongo write, or any local staging)

Extends `lib/backupValidation.js` with `validateTenantBackupObject(backup, targetTenantId)` — additive; `validateBackupObject()` (whole-instance) unchanged except for the one guard in "Whole-Instance Separation" below.

1. **Structural**: file exists, non-empty, valid JSON, checksum sidecar matches (existing `validateBackupFile()` machinery, unchanged).
2. **Format/scope**: `backup.scope === 'tenant'` and `backup.schemaVersion` known/supported. A whole-instance file (no `scope`, or any `scope` other than `'tenant'`) is rejected here.
3. **Tenant-identity ambiguity**: `backup.tenantId` is a single, unambiguous string.
4. **Tenant match**: `backup.tenantId === targetTenantId` exactly.
5. **Category shape**: `backup.collections` contains exactly `users`/`entityChunks`/`appConfigs` — **a `tenants` or `subscriptions` key present at all is itself a rejection** (a leftover shape from an incompatible producer; research.md Decision 10).
6. **Idempotency-, lock-, and audit-log-exclusion enforcement**: reject if `collections.entityChunks` contains any entry with `key==='idempotencyRecords'`, `key==='__restoreLock__'` (extended, second pass — the first pass only named `idempotencyRecords`), **or `key==='auditLog'` (extended, ninth pass — research.md Decision 8's ninth-pass extension)**, or any top-level `idempotencyRecords` field exists at all (research.md Decision 8, spec.md FR-024) — defense in depth against a malformed/hand-edited/future-version file, independent of whether the backup tool itself behaved correctly. Without the `__restoreLock__` half, a planted record at that reserved key could permanently block every future restore for the tenant, since its `data.runId` would never match a real run's own runId and so could never be released by the normal path. Without the `auditLog` half, a malformed file could reintroduce exactly the self-destruction hazard the exclusion itself exists to prevent.
7. **Record-count / digest integrity**: `recordCounts.<cat>` matches `collections.<cat>.length` for each category, and `categoryDigests.<cat>` matches a freshly-computed digest of `collections.<cat>` via the shared `computeCategoryDigest()` helper (research.md Decision 6, third pass — strips `_id`/`__v` before hashing even though `collections.<cat>` itself keeps `_id` on Mongo-sourced records) — a backup file that was hand-edited after being written is caught here, not silently trusted.
8. **Backup-fingerprint match on resume (research.md Decision 13)**: if an existing, non-`completed` checkpoint is found for `targetTenantId` (Decision 15 — a direct, tenant-keyed path, not a search), compute this invocation's backup file's sha256 (reusing the hash already computed in step 1's checksum verification) and compare it against that checkpoint's recorded `backupFingerprint`. Mismatch → hard reject, naming both files, before any further step. This is the check that replaces the original design's unenforced "resume with the same backup file" assumption, and it runs **last** in the validation gate, deliberately — see research.md Decision 13's "Ordering, corrected" note.

Any failure at any step: print every problem, exit non-zero, release the Step-0 lock, write no checkpoint, touch no real data. **NEW, ninth pass**: append exactly one `outcome:'failure'` audit event before exiting (research.md Decision 23, spec.md FR-037 — **tenth-pass citation correction: was wrongly also cited to Decision 25, the unrelated confirmation-gate decision**) — this is a terminal outcome of an already-lock-holding, privileged invocation, and MUST NOT go unaudited merely because it happens before Step 5.

## Step 2 — Default-tenant duplicate pre-flight (target `default` only)

Identical check to the backup contract's pre-flight (research.md Decision 16), run here against the **live database** (not the backup file) before staging begins: any `default`-owned logical identity (User `id`, EntityChunk/AppConfig `key`) with more than one physical document → hard-fail, name the exact identity, release the lock, write no checkpoint, touch no data. **NEW, ninth pass**: append exactly one `outcome:'failure'` audit event before exiting, identically to Step 1's own new requirement above.

## Step 3 — Offline/logical staging (NEW — no live-Mongo write of any kind)

Research.md Decision 6. Runs unconditionally on every invocation — fresh or resumed after a `--force-unlock` — never skipped based on a prior checkpoint or an existing staging file (research.md Decision 14, sixth-pass note); a stale staging file left over from a prior failed attempt is simply overwritten fresh here, not read back. Reads the already-validated backup's `collections` into memory:

1. **Sanitize**: strip `_id`/`__v` from every record in every category (confirmed, by re-reading `models/User.js`/`EntityChunk.js`/`AppConfig.js`, that neither field is ever used as application identity anywhere in this codebase — `id`/`key`/`tenantId` are the only identity fields any query uses).
2. **Recompute count + digest per category** using the shared `computeCategoryDigest()` helper (records sorted by identity key, then by recursive object-key order, `_id`/`__v` stripped before hashing — research.md Decision 6, third pass) and confirm they match the backup file's own `recordCounts`/`categoryDigests` (a second, independent check beyond Step 1's file-level one, now against the actually-sanitized, actually-staged data — this recompute is a no-op re-strip on already-sanitized records, so it matches the backup file's own digest exactly, computed via the identical helper at backup-write time).
3. **Ownership check**: every sanitized record's own `tenantId` (or, for `default`, a shape `_defaultTenantFilter` would match) is consistent with `targetTenantId`.
4. **Write the staged, sanitized representation to a local, tenant-keyed file** — `backups/.restore-staging/<targetTenantId>.json` (second pass — was `<runId>.json`; see Step 4 for why) — never to any live collection. **No `Tenant` document, real or synthetic, is ever created anywhere by this step** — closing the reachable-fake-identity hazard the original design had, by construction. `fs.mkdirSync` for this directory runs before the first write here, exactly as it does for the checkpoint directory (research.md Decision 14).
5. **Write the checkpoint** (Step 4 below) with `stage:'staged'`, `expected:{users:{count,digest}, entityChunks:{...}, appConfigs:{...}}` copied from this step's own recomputed values.

**Guarantee**: at the end of Step 3, the real target tenant's live data is byte-for-byte unchanged from before the restore began — nothing in staging ever writes to it.

## Step 4 — Checkpoint (atomic writes, tenant-keyed path, research.md Decisions 14–15)

**`backups/.restore-checkpoints/<targetTenantId>.json`** (second pass — was `<runId>.json`; keying by `runId` made "find the existing checkpoint for this tenant," required by Step 1.8's fingerprint check and Step 5's resume logic, undefined on a resumed invocation with a fresh `runId`. One live checkpoint per tenant, matching the one-lock-per-tenant invariant). Written via the existing, exported `_atomicWriteJsonSync` (tmp-file + `fs.renameSync`) — never a plain `fs.writeFileSync`. `fs.mkdirSync(path.dirname(...), {recursive:true})` runs before the first write. `runId` is a field inside the document, not part of its path. Format: see `data-model.md` → "New logical file format 2". A checkpoint that fails to `JSON.parse` on a later resume attempt is treated as "no reliable prior record, proceed as fresh" (safe — see Step 5's digest re-check, which never trusts the checkpoint blindly anyway).

## Step 4a — Explicit typed confirmation, MUST NOT be defaulted or bypassed (NEW, ninth pass, CRITICAL — research.md Decision 25, spec.md FR-039, per this project's own constitution Principle IV)

After the checkpoint is written (Step 4) and before Step 5's first destructive write — the latest point still before any data is touched — require the operator to type `نعم`, exactly mirroring `scripts/restore.js:104-107`'s own existing typed-confirmation gate, unless `--yes` is passed or `RESTORE_YES=1` is set (the same escape hatch `scripts/restore.js:104` already uses, needed here for this contract's own mandatory automated tests, e.g. T057/T058, which cannot pause for interactive input). The prompt MUST echo the target tenant identifier and the operator-supplied `--target=` label before asking, mirroring `scripts/restore.js:98-99`'s own echo, e.g. `🎯 الوجهة المُعلَنة: acme (staging) — اكتب "نعم" للتأكيد.` A negative or empty response cancels cleanly: release the lock, leave the checkpoint at `stage:'staged'` (Step 3/4 already completed, nothing destructive attempted), append one `outcome:'cancelled'` audit event (**eleventh-pass addition** — see the Mandatory audit event section below, research.md Decision 23's own eleventh-pass widening), print an Arabic cancellation message (research.md Decision 22) mirroring `scripts/restore.js:106`'s own `أُلغيت الاستعادة.`, and exit `0` — not a failure, since nothing was attempted. This gate applies identically to every target tenant, `default` included, and MUST NOT be weakened, defaulted, or silently bypassed by any flag or environment condition other than the one explicit escape hatch named above, per the constitution's own unconditional text.

**Acknowledged residual risks, tenth pass, not architecturally solved (research.md Decision 25's own tenth-pass addenda)**: (1) SIGINT/SIGTERM while this prompt awaits input is unhandled — the `readline` mechanics here mirror `scripts/restore.js:21-24`'s own equally signal-handler-free `ask()` verbatim (**eleventh-pass citation correction** — previously `:20-23`), so an interrupt falls through to Node's default immediate exit with the restore lock still held; recovery is the existing `--force-unlock` escape hatch, the same path any other pre-apply crash already requires. (2) this prompt's own wait is unbounded, extending the already-quiesced (Step -1), already-locked (Step 0) window by an arbitrary, human-response-dependent amount, with no timeout specified anywhere across all ten passes; `--yes`/`RESTORE_YES=1` is the intended mechanism for any unattended/scripted invocation that must avoid this. See research.md Decision 25 for the full reasoning on why neither is closed in this pass.

## Step 5 — Apply (the only step that writes to the real target tenant)

For each category, in the fixed order `users → entityChunks → appConfigs`:

1. **Digest re-check (research.md Decision 12)**: compute the category's *current, actual* count+digest for `targetTenantId` in the live database, via `computeCategoryDigest()` (research.md Decision 6, third pass — strips `_id`/`__v` from the freshly-queried, `_id`-bearing Mongo documents before hashing, so this matches `expected.<cat>`'s own already-sanitized-basis digest) — for `entityChunks`, this query is `{tenantId:target, key:{$in:TENANT_BACKUP_ENTITY_KEYS}}` (**second pass correction** — see point 2 below for why); for `default`, **every** category's query uses `_defaultTenantFilter` in place of plain `{tenantId:target}` (**third-pass correction** — this was previously stated only for the point-2 delete, not for this digest re-check itself; without it, a `default` restore's first-ever digest check always undercounts legacy no-`tenantId`-field records and reports a spurious mismatch — safe-direction, since it only ever triggers an unnecessary-but-correct delete+insert rather than an incorrect skip, but not the intended behavior). If it already matches `expected.<cat>` exactly, mark this category `categoriesApplied` and move to the next — **no destructive operation is performed on an already-correct category**, regardless of what the checkpoint's own prior `categoriesApplied` list said (it might be stale or absent from a crash — this re-derivation is authoritative, not the checkpoint alone).
2. If it does not match: **delete** the real target tenant's current documents in this category — `{tenantId:target}` for `users`/`appConfigs` (or `_defaultTenantFilter` for `default`), and **`{tenantId:target, key:{$in:TENANT_BACKUP_ENTITY_KEYS}}` for `entityChunks` specifically (second pass correction — a bare `{tenantId:target}` would also delete the Step-0 restore lock and the tenant's live `idempotencyRecords` document, both of which live in this same collection under this same tenantId)** — **never** a bare `deleteMany({})` — then **insert** the staged, sanitized records from Step 3's local file directly with `tenantId` set to the *real* target (no synthetic identity of any kind — there is nothing to "repoint" anymore), with `{ordered:false}` on the `entityChunks` insert specifically (mirroring `scripts/restore.js:41`'s own precedent) so one unexpected record can never abort unrelated ones in the same batch.
3. Append the category to `categoriesApplied`, rewrite the checkpoint (atomically, Step 4's mechanism).
4. On any error: catch it, set `stage:'failed'`, record `error`, rewrite the checkpoint, release the lock (clean failure — not a crash), exit non-zero, print the recovery-model reminder (below).

## Step 6 — Finalize

Once every category is confirmed in `categoriesApplied`: `stage:'completed'`, release the lock, print success — **explicitly naming the target tenant and stating a tenant-scoped restore path was used** (research.md Decision 18 *(third-pass correction: was cited as Decision 17, the raw-driver test-fixture decision, through the second pass)*, spec.md's operator-honesty requirement), **in Arabic (research.md Decision 22, seventh pass — was English)** — e.g. `✅ اكتملت استعادة المستأجر "acme" فقط، عبر فلاتر مخصّصة لهذا المستأجر — لم تُكتب بيانات أي مستأجر آخر في هذه العملية.` This is a claim about the tool's own design guarantee (every write in Step 5 is filtered to `target` by construction), not an empirically runtime-checked claim about every other tenant — the tool does not, and is not required to, scan other tenants' data to "verify" this.

**Mandatory addition to the success message (research.md Decision 19, CRITICAL)**: the same output MUST also state that the target tenant's live application server process(es) — if still running (the normal case if the Step -1 quiesce warning above was not followed) — hold an in-memory cache that this restore never invalidates, and MUST be restarted before any further write to that tenant is accepted, **in Arabic (Decision 22, seventh pass)** — e.g. appended to the message above: `⚠️ مهم: أي عملية سيرفر تخدم هذا المستأجر حالياً تحتفظ بذاكرة مؤقتة (cache) قديمة ويجب إعادة تشغيلها الآن، قبل أي كتابة أخرى لهذا المستأجر، وإلا فقد تُلغى هذه الاستعادة صمتاً.` Without this, a completed, correctly-scoped restore can be silently undone by the very next unrelated write the live server accepts for that tenant.

**Mandatory idempotency-staleness count (research.md Decision 20, fifth-pass extension, representation specified sixth pass)**: still within Step 6, before printing final success, run one cheap, read-only query for `targetTenantId`: count documents with `status:'COMPLETED'` AND `completedAt > backup.createdAt`. **In Mongo mode this queries the dedicated `IdempotencyRecord` collection specifically** — `IdempotencyRecord.countDocuments({tenantId:target, status:'COMPLETED', completedAt:{$gt: backup.createdAt}})` — **never** the `EntityChunk{key:'idempotencyRecords'}`-embedded array (`db.idempotencyRecords[]`), which a request marks `COMPLETED` in-memory strictly before its own durable save, while the dedicated collection's own record is written only after that save succeeds — the two can briefly disagree, and the dedicated collection is the one whose `completedAt` this comparison is well-defined against (research.md Decision 20, sixth pass). **In `DB_FILE_ONLY` mode**, where no dedicated `IdempotencyRecord` collection exists, the equivalent count is computed by loading the target tenant's own file-mode data and counting matching entries in its `idempotencyRecords[]` array — the only representation that mode has. Print this count as part of the same success output, **in Arabic (Decision 22, seventh pass)** — e.g. `ℹ️ ملاحظة: يوجد 3 سجل(ات) idempotency لهذا المستأجر اكتملت بعد وقت أخذ النسخة المستعادة. أي طلب متكرر يطابق أحدها سيُعاد له نفس النتيجة المخزّنة (عبر sourceId أو journalId) حتى لو لم يعد الكيان الأصلي موجوداً بعد الاستعادة. هذا خطر متبقٍّ معروف ومُبلَّغ عنه فقط (بدون إصلاح تلقائي) — راجع docs/PRODUCTION_RUNBOOK.md.` If the count is zero, state that explicitly — `ℹ️ لا يوجد أي سجل idempotency معرّض للخطر (0).` — rather than omitting the line — a silent line is easy to misread as "not checked."

**Mandatory staging-file cleanup (fifth pass, HIGH; rationale corrected sixth pass)**: on this same successful `stage:'completed'` path only, delete the local staging file written in Step 3 (`backups/.restore-staging/<targetTenantId>.json`). It holds the same sanitized-but-otherwise-complete tenant records the backup file itself does — including any plaintext secret an `AppConfig` document may carry (e.g. `smtpPass`, per `server.js:5544`'s own destructuring of it as a real, sensitive field) — and has no further purpose once the apply step it fed has succeeded. On a `failed` exit (Step 5, point 4) the staging file is deliberately left in place — **not**, as a Pass 5 draft of this contract stated, because a `--force-unlock` resume "re-reads it rather than re-running Step 3." Step 3 runs unconditionally on every invocation, resumed or not (see Step 3 above and research.md Decision 14's own opening sentence), and would simply overwrite the file fresh regardless of whether the prior copy survived — there is no skip-staging-on-resume branch in this design. The file is preserved after a failure purely as a forensic/diagnostic artifact, so an operator investigating the failure — before deciding whether to retry with `--force-unlock` — can inspect exactly what was staged (research.md Decision 14, sixth-pass addition). A delete failure (e.g. permissions) is logged as a warning, not escalated to a non-zero exit — the restore itself already succeeded.

**Mandatory audit event (NEW eighth pass, HIGH; scope and mechanics corrected ninth pass, widened eleventh pass — research.md Decision 23, spec.md FR-037, per this project's own constitution Principle XI)**: on the **first terminal outcome the invocation reaches** — a Step 1 validation-gate rejection, a Step 2 default-duplicate rejection, **Step 4a's own decline (eleventh-pass addition, HIGH — see below)**, or Step 5/6's own success-or-apply-failure exit — call the canonical `appendAuditEvent()` (`lib/auditLog.js`) exactly once, never a hand-rolled event object. **Ninth-pass correction**: this requirement previously said "still within Step 6," which both misdescribed Step 5's own error handling (which already fully owns and exits a failed apply *within Step 5 itself* — it never separately reaches "Step 6") and, more substantively, left Step 1/Step 2 rejections with no audit event at all despite being genuine terminal outcomes of an already-lock-holding, privileged invocation — an asymmetry with `scripts/tenant-backup.js`'s own broader pre-flight audit coverage. **Eleventh-pass correction**: this scope statement was itself left stale after Decision 25's Step 4a confirmation gate was introduced in the same ninth pass elsewhere in this document — an operator declining at Step 4a is a fourth genuine terminal outcome (ordinary, non-crash, lock released, exit 0) that the "Step 1, Step 2, or Step 5/6" enumeration omitted, silently leaving a privileged invocation's own deliberate cancellation unaudited. Now four terminal-outcome families are covered; only one is ever reached per invocation, so exactly one event is still guaranteed **for every terminal outcome that is not a raw SIGINT/SIGTERM kill during the Step 4a prompt itself** (the acknowledged, deliberately-unclosed residual risk above — the process dies before any write can occur, so no event fires for that one specific case, and this is the sole exception to "exactly one event guaranteed"). Written to `default`'s own `auditLog` (an `EntityChunk{tenantId:'default', key:'auditLog'}` document in Mongo mode, `blob.auditLog` in file mode), **never the target tenant's own log**, since Step 5's own apply is precisely what could destroy a record stored inside the tenant it documents — and, since research.md Decision 8's ninth-pass extension excludes `auditLog` from `TENANT_BACKUP_ENTITY_KEYS` entirely, `default`'s own `auditLog` is itself never touched by any tenant-scoped restore's Step 5 apply either, closing the self-destruction hazard the eighth-pass version of this requirement did not consider (a restore *of* `default` would otherwise have reverted this same centralized log). `action:'tenant.restore'`, `resourceType:'tenant'`, `resourceId:target`, `outcome:'completed'===stage?'success':'failure'` (or `'failure'` for a Step 1/Step 2 rejection, or **`'cancelled'` for Step 4a's own decline — eleventh-pass addition, distinct from `'failure'` since a deliberate operator decline is not itself an error**), `metadata:{backupFingerprint, createdAt:backup.createdAt, categoriesApplied}` (unified ninth pass with the backup contract's own shared minimum, plus `categoriesApplied` as this tool's own extra context — `categoriesApplied` is `[]` for a Step 1/Step 2/Step 4a outcome, since none has begun applying anything). **Ninth-pass addition, closing a silent-default gap**: `buildAuditEvent()` derives its own `tenantId` field from `req.tenantId || user.tenantId || 'default'` — a CLI script has no real `req`, so the caller MUST construct and pass a synthetic `req:{tenantId:target}` as `opts.req`; without this explicit construction, every event's own `tenantId` field would silently read `'default'` regardless of the real target, defeating this requirement's own "self-describing" purpose. Mongo-mode mechanics: read the current `auditLog` `EntityChunk` (or `{data:[]}` if absent), pass its `data` array to `appendAuditEvent()` as the `db.auditLog` it mutates, then `EntityChunk.findOneAndUpdate({tenantId:'default',key:'auditLog'}, {$set:{data:<mutated array>}}, {upsert:true})` — a direct read-modify-write via the same `EntityChunk` primitive the restore lock already uses, not the full `loadDB()`/`saveDB()` cache machinery (see research.md Decision 23's own "known residual risk" note for this write's acknowledged, deliberately-deferred non-atomicity under concurrent invocations). A write failure here is logged as a warning, not escalated to change the restore's own already-determined exit code.

## Recovery model — stated explicitly (research.md Decision 18)

- **Resume: supported, always via `--force-unlock` after any non-clean prior exit (second pass — tightened, no exception)**: re-run the identical command with the identical backup file. If the prior attempt exited cleanly (a caught `failed`), the lock is already released and a plain re-run suffices. If the prior attempt was killed (a real crash — including the mandatory crash-window test scenario itself), the lock is still held and `--force-unlock` is **required**, with no exception, because the tool cannot safely distinguish "genuinely dead" from "merely slow" without operator judgment, and cannot rely on a `pid` check across independent hosts. Step 1.8's fingerprint check confirms it's the same backup; Step 5's digest re-check skips whatever is already correctly applied and only redoes what isn't.
- **Rollback: NOT supported.** There is no automatic mechanism to revert an already-applied category back to its pre-restore state. Reverting requires an explicit, deliberate restore again, using a backup taken *before* the unwanted one.
- On any `failed` exit, the tool prints, **in Arabic (research.md Decision 22, seventh pass — was English)**: *"↻ الاستئناف: أعد تشغيل نفس الأمر بنفس ملف النسخة. إذا كانت هذه العملية أُوقفت قسراً لا بخطأ عادي، فقفل الاستعادة لهذا المستأجر لا يزال محجوزاً — إعادة التشغيل تتطلب --force-unlock، ولا تستخدمه إلا بعد التأكد أن لا استعادة أخرى لهذا المستأجر تعمل فعلياً الآن. لا يوجد تراجع تلقائي (rollback) عن فئة سبق تطبيقها — أعد الاستعادة من نسخة أقدم عند الحاجة."*

## Whole-Instance Separation (H)

`lib/backupValidation.js`'s existing `validateBackupObject()` (whole-instance, used by the **unmodified** `scripts/restore.js`) gains one new, additive, first check: `if (backup.scope === 'tenant') return {ok:false, problems:['tenant-scoped backup file — use scripts/tenant-restore.js']}`. An absent `scope` (every existing whole-instance file) is unaffected — zero regression. This replaces the original design's incorrect claim that the existing `collections`-presence check already handled this (research.md Decision 7) with a deliberate, tested guard.

## Test contract

**NEW, tenth pass, blanket requirement — closes a gap Pass 9 itself introduced**: every test below that expects the tool to reach Step 5/6 (i.e. every test except one specifically exercising Step 4a's own prompt behavior) MUST invoke `tenant-restore.js` with `--yes` or `RESTORE_YES=1` set, exactly as `scripts/restore.js`'s own existing tests already do for its equivalent gate. Pass 9 added Step 4a (the typed-`نعم` confirmation gate, research.md Decision 25) without updating any test below individually — a blanket requirement here, rather than an edit to each test's own line, is deliberate: enumerating every affected test by number invites exactly the "some updated, some silently missed" gap this fix itself exists to close, and any *future* test added to this list inherits the requirement automatically without needing its own reminder.

1. Restoring Tenant A never changes Tenant B (unchanged from original pass, re-verified: byte-identical before/after, across all three categories).
2. A whole-instance file fed to `tenant-restore.js` is rejected at Step 1.2. A tenant-scoped file fed to `scripts/restore.js` is rejected by the new `validateBackupObject()` guard above — both tests call the real, exported validators, not a reimplementation.
3. A tenant-scoped file with a `tenants`/`subscriptions` key is rejected at Step 1.5.
4. A backup containing an `idempotencyRecords` entity chunk, a `__restoreLock__` entity chunk (extended, second pass), **or an `auditLog` entity chunk (extended, ninth pass)**, is rejected at Step 1.6.
5. **Concurrent restore (mandatory)**: start two `tenant-restore.js` processes against the same tenant; assert exactly one acquires the lock and proceeds, the other is rejected at Step 0 before reading the backup file at all.
6. **Digest-based resume (mandatory, corrected second pass — must include `--force-unlock`)**: apply `users` successfully, then kill the process before `entityChunks`'s checkpoint entry is written (simulating the crash window, not just a thrown JS exception) — re-run **with `--force-unlock`** (a plain re-run without it MUST be rejected at Step 0 per the tightened lock policy — assert this rejection as part of the same test, before demonstrating the `--force-unlock` re-run succeeds); assert `users` is **not** re-deleted/re-inserted (verify via a marker field or write-count instrumentation) because its digest already matches, while `entityChunks`/`appConfigs` proceed normally.
7. **Failure-injection mid-apply (mandatory, unchanged intent, updated mechanism)**: force a failure after `users` applies but before `entityChunks` begins; assert Tenant B untouched, `entityChunks`/`appConfigs` untouched (pre-restore state), `users` matches the backup, checkpoint shows `stage:'failed'`, `categoriesApplied:['users']`, non-zero exit, no false success claim.
8. **Backup-fingerprint mismatch on resume (mandatory)**: after a partial failure, re-invoke (with `--force-unlock`, per test 6's policy) with a *different* backup file for the same tenant; assert hard rejection at Step 1.8, zero additional writes.
9. **`default` duplicate pre-flight (mandatory)**: seed a genuine duplicate `default` identity (raw-driver-seeded, per spec.md FR-027); attempt a `default` restore; assert hard failure at Step 2, exact identity named, zero writes.
10. **No live synthetic identity at any point (mandatory)**: throughout a full staging run, assert (via a live query) that no `Tenant`/`User`/`EntityChunk`/`AppConfig` document with any placeholder/synthetic `tenantId` ever exists in the database — staging never touches Mongo at all.
11. `default` restore uses `_defaultTenantFilter` for the delete half of Step 5.2, correctly clearing legacy no-`tenantId`-field documents being replaced (unchanged intent from the original pass, re-verified: legacy record seeded via raw driver per FR-027, restored exactly once, no duplicate pair remains).
12. **`entityChunks` delete scoping (NEW, mandatory, second pass)**: before a restore that changes `entityChunks`, seed the target tenant's own live `idempotencyRecords` document and acquire the Step-0 lock; after Step 5's `entityChunks` apply completes, assert **both** the lock document and the `idempotencyRecords` document still exist, byte-unchanged, under the real target tenantId — proving the delete was scoped by `key` as well as `tenantId`.
13. **Tenant-keyed checkpoint lookup (NEW, mandatory, second pass)**: fail a restore partway, note its `runId`; start a **new** invocation (a fresh `runId`) with the same backup and `--force-unlock`; assert it correctly locates and compares against the *prior* run's checkpoint (via the tenant-keyed path) despite the different `runId`, and that the fingerprint/digest checks behave as if resuming, not as a from-scratch first run.
14. **File-mode `entityChunks` undefined-key handling (NEW, second pass)**: restoring a file-mode backup of an ordinary tenant (no `passwordResets`/`errorLog` history) completes without a Mongoose validation error, and the `entityChunks` category's `{ordered:false}` insert is confirmed present (e.g. via a test that also includes one deliberately-invalid record among otherwise-valid ones and asserts the valid ones still land).

16. **Typed confirmation gate (NEW, ninth pass, MANDATORY — research.md Decision 25; tenth-pass correction to this test's own claim; eleventh-pass audit-event assertion added)**: without `--yes`/`RESTORE_YES=1`, the restore pauses at Step 4a and performs no write until `نعم` is typed; typing anything else cancels cleanly (lock released, `stage` left at `'staged'`, exit `0`, **and — eleventh pass — exactly one `outcome:'cancelled'` audit event appended to `default`'s own `auditLog`, with the event's own `tenantId` equal to the real target, per test 15's fourth case above**); with `--yes` or `RESTORE_YES=1`, Step 4a is skipped non-interactively and no `'cancelled'` event is appended (the run proceeds to whatever event Step 5/6 itself produces instead).
