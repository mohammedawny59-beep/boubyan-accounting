## Decision 2 — Tenant config: synchronous cache, asynchronous warm, fail-closed on cold miss, with file-fallback parity (REVISED)

**What was wrong**: the original design had `loadConfig()`'s non-default branch perform an inline `AppConfig.findOne(...).lean()` — a Mongo round-trip — inside a function that is, and per this remediation must remain, synchronous, with ~18 unguarded synchronous callers in `server.js`. It also never defined a `_useFileFallback` branch at all, unlike the sibling `_tenantCaches` mechanism it claimed to mirror "exactly."

**Decision**: mirror `warmTenantCache()`/`loadDB()`'s existing two-part design precisely — an async warming step, then a synchronous read of an already-warm cache:

- **New function `warmTenantConfigCache(tenantId)`** (async), directly analogous to the existing `warmTenantCache(tenantId)` (`lib/database.js:794-799`): no-op for `tenantId==='default'` or when the process has no per-tenant concept to warm; for a non-default tenant, if `_tenantConfigCaches` does not yet have an entry, resolve one — under Mongo mode via `AppConfig.findOne({tenantId,key:'config'}).lean()`, merged over `_defaultConfig`; under `_useFileFallback` via the new per-tenant config file (below) — and cache it.
- **`lib/tenantMiddleware.js:94`** gains one line: `await warmTenantConfigCache(tenantId);` immediately alongside the existing `await warmTenantCache(tenantId);` — both awaited before `next()`, so by the time any route handler runs, both caches are warm.
- **`loadConfig()` stays synchronous** and gains exactly one new branch: for a non-default tenant, if `_tenantConfigCaches.has(tid)`, return the cached, already-merged value; if not — this is a bug, not a legitimate cold path, because `tenantMiddleware` always warms it first — **throw** (`Tenant config not warmed for "<tid>" — warmTenantConfigCache() must run before loadConfig()`), exactly mirroring `loadDB()`'s own existing fail-closed pattern for an uninitialized default cache (`lib/database.js:687`, `if (!_dbCache) throw ...`). This satisfies "fail closed rather than silently return global/default tenant config" without touching any of the ~18 existing synchronous callers — Express's own error handling turns an uncaught synchronous throw inside a route into a 500, which is the correct fail-closed outcome for a genuine bug (a route touching tenant config outside `tenantMiddleware`'s normal flow).
- **Default tenant's own AppConfig calls MUST be scoped too — correction, second `/speckit-analyze` pass**: the statement below ("default tenant is unaffected... no change needed there") was **wrong** in the first remediation pass and is retracted. It described the *cache/warming* mechanism correctly (default's config is populated synchronously at boot, no change to that timing) but incorrectly implied the *Mongo query scoping* was already correct too. It was not: `initConfig()`'s read (`lib/database.js:612`, `AppConfig.findOne({key:'config'})`) and its two legacy-migration writes (`:621-625`, `:633-637`, both `AppConfig.updateOne({key:'config'},...)`), plus `flushToMongo()`'s default-tenant config write (`:490-494`, `AppConfig.updateOne({key:'config'},{$set:{data:_configCache,...}},{upsert:true})`) all filter by `{key:'config'}` alone, with **zero tenant scoping** — exactly the same class of bug Decision 1 fixes for `persistUsers()`/`persistEntityKey()`, left unfixed here because the original remediation rewrite of Phase B replaced the *entire* config task list and dropped the default-tenant scoping task that existed before that rewrite. Once any non-default tenant has its own `AppConfig` document (`{tenantId:'acme',key:'config',...}` — the compound unique index `{tenantId,key}` on `models/AppConfig.js:10` permits this to coexist with `{tenantId:'default',key:'config'}`), these three unscoped call sites can read or overwrite the wrong tenant's config document, since Mongo gives no ordering guarantee for a `{key:'config'}`-only filter matching multiple documents. **Fix, restored from the pre-remediation design**: all three call sites get the identical `_defaultTenantFilter` + normalize-forward treatment as `persistUsers()`/`persistEntityKey()` — `AppConfig.findOne({..._defaultTenantFilter, key:'config'})` for the read, `AppConfig.updateOne({..._defaultTenantFilter, key:'config'}, {$set:{tenantId:'default', ...}}, {upsert:true})` for every write. This is not new scope creep — it is restoring a fix that was correctly specified once already (`contracts/tenant-backup-contract.md`'s own `default`-tenant backup query already independently arrived at the same correct pattern, which is what exposed the runtime-code gap during re-verification) and must not be dropped again.
- **Default tenant's config *warming/caching* is otherwise unaffected**: its config is already synchronously populated by `initConfig()` during `initDB()`, before the server accepts any request — no change to that timing.
- **File-fallback (`DB_FILE_ONLY`) parity**: add a new per-tenant config file path, `_tenantConfigFilePath(tid)` (derived from the same sanitization `_tenantFilePath()` already uses, at a sibling path — `data/tenants/<sanitized-tid>.config.json`, distinct from that tenant's `<tid>.json` data file). `warmTenantConfigCache()` under `_useFileFallback` reads that file if it exists (`fs.readJsonSync`), else caches a fresh copy of `_defaultConfig` (matching `loadDB()`'s own "new tenant starts from sane defaults" behavior). `saveConfig()`'s non-default branch, under `_useFileFallback`, writes to that same path using the existing `_atomicWriteJsonSync` — no Mongo call is ever attempted in file mode, closing the original design's silent gap outright. Default tenant's file-mode config path (`_configFile`/`data/config.json`) is unchanged.
- **Persistence flush (Mongo mode)**: reuse the *same* per-tenant debounce timer `_flushTenantToMongo()` already schedules for entity/user data (`lib/database.js:38-65`) — one added branch checking `_tenantConfigDirty.has(tenantId)` — not a second, parallel timer. `saveConfig()`'s non-default branch marks `_tenantConfigDirty` and calls the existing `_scheduleTenantPersist(tenantId)`. **Correction (second `/speckit-analyze` pass)**: `_flushTenantToMongo()`'s existing early-return guard, `if (!db || dirty.size === 0) return;` (`lib/database.js:41`), checks only the entity-dirty set — a tenant whose *only* pending Mongo-mode change is a `saveConfig()` call (no `saveDB()` in the same debounce window) would hit this guard and return before ever reaching the new config branch, silently dropping the config write and never clearing `_tenantConfigDirty`. The guard MUST change to `if ((!db || dirty.size === 0) && !_tenantConfigDirty.has(tenantId)) return;` — skip only when there is truly nothing to do on either axis.
- **Persistence flush (file mode) — new timer map and shutdown wiring required (second `/speckit-analyze` pass, corrected fourth pass)**: the new `_scheduleTenantConfigFilePersist(tid)` needs its own debounce-timer bookkeeping, exactly mirroring the existing `_tenantFileTimers`/`_scheduleTenantFilePersist` pair (`lib/database.js:691-712`) that already exists for entity-data file persistence — a new `_tenantConfigFileTimers = new Map()`. This new map MUST be added to the P0.11 cross-backend reset block (alongside `_tenantConfigCaches`/`_tenantConfigDirty`, with the `clearTimeout`-first treatment its own live-handle nature requires — third pass). **Shutdown wiring, corrected fourth pass**: the second pass's own instruction to "flush any *pending* tenant config-file timer" on shutdown was wrong — it does not actually mirror the real sibling code. `_flushAllTenantsOnShutdown()`'s real, current file-mode branch (`lib/database.js:831-841`) does **not** iterate `_tenantFileTimers` to decide what to flush at all; it unconditionally writes **every** tenant present in `_tenantCaches.keys()`, full stop — and the Mongo-mode half of the same function states the reasoning explicitly in its own comment (`:845-847`): "flush every tenant with any cached state, not just ones still listed in `_tenantDirty`... being conservative here costs a few redundant upserts at worst, never a lost write." This matters because a tenant's file-write retry (after a transient failure, `:703-709`) reschedules via a **bare, untracked** `setTimeout` whose handle is never stored back into `_tenantFileTimers` — so during that backoff window, a tenant has *no* entry in `_tenantFileTimers` at all even though its data is not yet durable, and a "flush only pending timer entries" shutdown step would miss it entirely. **The corrected instruction**: the config-file shutdown extension MUST unconditionally iterate `_tenantConfigCaches.keys()` (not `_tenantConfigFileTimers.keys()`) and write every entry via `_atomicWriteJsonSync`, exactly matching lines `:831-841`'s real pattern — `_tenantConfigFileTimers` is used only to *cancel* pending debounce timers first (as the reset block already does), never as the source of which tenants to flush. Omitting durable-flush-on-shutdown entirely would reintroduce the exact SIGTERM data-loss bug class this codebase's own P0.5 milestone already closed for entity data (`lib/database.js:817-822`'s own comment); the second pass's narrower "pending only" version would have reintroduced a smaller version of the identical bug for a tenant caught mid-retry.

**Why this satisfies "do not make the ~18 callers async"**: every existing `loadConfig()` call site keeps its exact current signature and calling convention. The only new failure mode (a throw on an unwarmed cache) can only actually occur if a code path reaches `loadConfig()` for a non-default tenant *without* having gone through `tenantMiddleware` first — which every existing route already does (the global `app.use('/api', requireAuth, tenantMiddleware)` mount predates this feature) — so in the entire currently-existing call graph, the throw branch is unreachable in normal operation; it exists purely as a fail-closed guard against a *future* code path that forgets to run through the middleware, exactly the kind of defense FR-002 already requires elsewhere.

## Decision 6 — Restore staging: offline/logical, never live-Mongo synthetic tenants (MAJOR REVISION)

**What was wrong, adversarially confirmed**: the original `__restage__<tenant>__<runId>` design inserted a real, synthetic-tenantId copy of the entire backup directly into the live `User`/`EntityChunk`/`AppConfig`/`Tenant`/`Subscription` collections *before* the real tenant's old data was deleted. Three independent, fatal problems followed directly from this one choice: (a) `Tenant.slug`'s standalone unique index (`models/Tenant.js:7`, not compound with `tenantId`) collided with the still-live real tenant's own slug on every restore of an already-registered tenant — the *normal* case; (b) staged documents kept their original Mongo `_id`, colliding with a still-live target tenant's own current documents sharing that `_id` whenever the target's data had been edited since the backup was taken — quickstart.md's own canonical worked example; (c) a staged `Tenant` document with `status:'active'` became a real, reachable authentication identity for the entire staging window, with its exact synthetic tenantId sitting in plaintext in the checkpoint file.

**Decision**: staging is now **entirely offline** — no live-database write of any kind occurs before the final apply step for the real target tenant.

1. **Validate** (unchanged from the original design's Phase E: structural, scope, schema-version, tenant-identity-match, record-count checks — see Decision 7/8 revisions below for what's new inside this step).
2. **Sanitize, in memory**: for every record in every included category (users, accounting entities — see Decision 10 for what "category" now means), strip Mongo-only persistence metadata (`_id`, `__v`). Confirmed by re-reading every relevant schema (`models/User.js`, `models/EntityChunk.js`, `models/AppConfig.js`) that `_id`/`__v` are never used as application-level identity anywhere in this codebase — `id` (User), `key` (EntityChunk/AppConfig), and `tenantId` are the only identity fields any code path queries by — so stripping them is lossless, exactly matching what the existing `scripts/restore.js:40` already does for the whole-instance path.
3. **Compute per-category count + digest**: for each category, `count = array.length`; `digest = computeChecksum(canonicalJson(sanitizedArray))` — reusing the *existing*, unmodified `computeChecksum()` from `lib/backupValidation.js`. **`canonicalJson()` is a new, exported function, defined precisely (second `/speckit-analyze` pass — the first pass left it as an undefined name in prose)**, added alongside `computeChecksum()` in `lib/backupValidation.js`: it (a) sorts every record in the array by its stable identity field first — `id` for `users`, `key` for `entityChunks`/`appConfigs` — **before** serializing, and (b) recursively sorts object keys at every depth within each record. Both halves matter: without (a), two logically-identical record sets returned by MongoDB in a different physical order (no query has an implicit stable order) would hash differently, causing Decision 12's resume-skip check to falsely report "does not match" and trigger an avoidable destructive re-apply — silently degrading the mechanism's purpose without ever producing a wrong end state, but undermining the "closes the crash window" claim. This pair becomes each category's "expected" state for Decision 12's resume logic, and is written into the local staging artifact and the checkpoint (Decisions 14 and 15 *(fourth-pass correction: was "Decision 18," the runbook/success-output decision, unrelated to the checkpoint mechanism itself)*).

   **`_id`/`__v`-stripping MUST happen before every digest computation, at all three points it occurs — not only during restore staging (third-pass correction, CRITICAL)**: the paragraph above computes the staging-side digest over `sanitizedArray` (already `_id`/`__v`-stripped by step 2). But `categoryDigests` is *also* computed once at backup-write time (`tenant-backup.js`, Decision 8/9) and *again* at restore apply-time as a fresh live re-check (Decision 12) — and neither of those two other computation points was previously specified to strip `_id`/`__v` first. Mongo-mode backup queries (`Model.find().lean()`, matching the existing, unmodified `scripts/backup.js:41` precedent) return documents *with* `_id`, and the stored `collections.<cat>` array in the backup file **keeps** `_id` on each record (this does not change — it matches the existing whole-instance convention of stripping `_id` only at restore time, `scripts/restore.js:40`). Left as originally worded, this means the backup file's own `categoryDigests` would be hashed over `_id`-bearing records while the restore-staging recompute (this step) hashes the *same* records *after* `_id` is stripped — two structurally different representations of identical data that can never hash equal, making every Mongo-sourced tenant backup fail its own digest-integrity check on the very first restore, and making Decision 12's live re-check (which queries fresh, `_id`-bearing documents from Mongo) never match `expected` either, permanently defeating the resume-skip mechanism. **Fix**: introduce one shared, exported helper — `computeCategoryDigest(records) = computeChecksum(canonicalJson(records.map(stripMongoMeta)))`, where `stripMongoMeta` strips `_id`/`__v` (a harmless no-op on a record that is already sanitized) — and use *only* this helper at all three computation points: backup-write time (over the raw, `_id`-bearing `collections.<cat>` array, even though that array itself is stored unsanitized in the file, matching precedent), restore-staging recompute (over the already-sanitized staged array — the helper's strip step is a no-op here), and restore apply-time live re-check (over a fresh Mongo query's `_id`-bearing results). All three now hash the same logical content the same way, regardless of which literal representation each one started from. File mode is unaffected (its synthesized records never had `_id` to begin with).
   **Timestamp-field dependency, stated explicitly (second pass)**: sanitization strips only `_id`/`__v`, never `updatedAt`/`createdAt` — this is safe today because `User`/`EntityChunk`/`AppConfig` all declare `{versionKey:false}` with no schema-level `{timestamps:true}` option (confirmed by re-reading all three schemas), so Mongoose never overwrites an explicitly-provided `updatedAt`/`createdAt` value on insert — the digest computed from a backup's records and the digest recomputed after those same records are inserted live will match. **This is a load-bearing assumption**: if any future, unrelated change adds `{timestamps:true}` to any of these three schemas, Decision 12's resume-skip check would silently stop matching (degrading to "always re-apply," never to a wrong result) and this note must be re-verified against the changed schema.
4. **Validate ownership**: confirm every sanitized record's own `tenantId` (or, for `default`, a value `_defaultTenantFilter` would match) is consistent with the declared target tenant — defense in depth beyond the top-level backup-file `tenantId` check, catching an internally-inconsistent or tampered file.
5. **Persist the staged, sanitized, digested representation to a local file** (`backups/.restore-staging/<targetTenantId>.json` — **third-pass correction**: this line still said `<runId>.json` after Decision 15 introduced tenant-keying for exactly this file; every downstream document already said `<targetTenantId>.json` — this was the one place in this document where the correction was missed) — not a database write. Nothing under the real target `tenantId`, and no placeholder/synthetic identity of any kind, exists in Mongo at the end of this step.
6. Only the **apply** step (Decision 12, which spells out the fixed-order, digest-gated delete+insert mechanic this bullet summarizes) ever writes to the live target tenant's collections, directly with the *real* `tenantId` already set on each sanitized record — there is no more "insert under a fake identity, then repoint" two-hop mechanic. This eliminates findings C4, C5, and H4 by construction, not by patching around them. *(Fourth-pass correction: the second-pass "corrected to 18" footnote here was itself wrong — Decision 18 is the runbook/success-output decision, which only reports on this guarantee, it does not define it. The correct target, confirmed by cross-checking every citation in this document, is Decision 12.)*

## Decision 7 — Backup format separation: explicit, not accidental (REVISED)

**What was wrong**: the original design's own safety proof (research.md, the contract, plan.md's Plan Consistency Review) all claimed a tenant-scoped file fails the whole-instance `validateBackupObject()`'s `collections`-presence check (`lib/backupValidation.js:33-42`) — but a tenant-scoped file's `collections` object *does* carry all the keys that check requires (even as empty arrays), so it actually passes that check. The real, accidental reason rejection happened to occur was a missing `version` field.

**Decision**: make the rejection deliberate on both sides, in `lib/backupValidation.js` (the one shared validation module both restore paths already import from):
- `validateBackupObject()` (whole-instance, existing, otherwise **unmodified**) gains exactly one new, additive check at its top: `if (backup.scope === 'tenant') return {ok:false, problems:['this is a tenant-scoped backup file — use scripts/tenant-restore.js']}`. An absent `scope` field (every existing whole-instance backup file, past and future) is unaffected — this is purely additive, zero regression to the legacy format.
- `validateTenantBackupObject()` (new, tenant-scoped) requires `backup.scope === 'tenant'` as its first structural check (unchanged from the original design — this half was already correct).
- Both cross-feed tests (Decision from the original Phase J) must call these *real*, exported functions — not a hand-rolled reimplementation — closing the class of test-quality gap Decision 17 addresses more broadly. *(third-pass correction: was cited as Decision 16 through the second pass — Decision 16 is the default-tenant duplicate pre-flight, unrelated to test-fixture quality.)*

## Decision 8 — Idempotency exclusion: a real filtered key list, not raw `ENTITY_KEYS` (REVISED)

**What was wrong**: the original design said "reuse `ENTITY_KEYS`" for the `entityChunks` backup query *and*, in the same documents, claimed idempotency records were excluded — but `ENTITY_KEYS` (`lib/database.js:111-172`) literally contains the string `'idempotencyRecords'` at line 171, so the two claims directly contradicted each other; following the tasks as written would have captured and later restored stale idempotency claims.

**Decision**: export a new, derived constant from `lib/database.js`: `TENANT_BACKUP_ENTITY_KEYS = ENTITY_KEYS.filter(k => k !== 'idempotencyRecords')`, and use *that* — never raw `ENTITY_KEYS` — as the single authoritative source for every tenant-backup/restore entity-category query and for record-count computation. The dedicated `IdempotencyRecord` Mongoose model remains, as originally designed, never queried by backup/restore's own capture-or-apply mechanism — it is never read during backup, never staged, and never a target of any restore-apply write, exactly as this decision intends. **Sixth-pass narrowing, to keep this claim accurate rather than merely aspirational**: the one deliberate exception is Decision 20's fifth-pass extension, where `scripts/tenant-restore.js`'s Step 6 runs a single, read-only diagnostic query against this same collection purely to report an operator-facing idempotency-staleness count, strictly after the restore's own destructive apply work is already complete — a read for reporting, not a capture-or-apply operation, and not a contradiction of this decision's actual purpose (keeping the restore's own *write* path from ever touching this collection, which remains true). **New, additive validation**: `validateTenantBackupObject()` gains a check that rejects a backup file whose `collections.entityChunks` array contains any entry with `key==='idempotencyRecords'` — a defensive check against a malformed, hand-edited, or future-version file, not just a promise about how the backup tool itself behaves — satisfying "restore must reject an unexpected idempotency-record payload rather than recreate stale duplicate-posting claims." **Extended, second `/speckit-analyze` pass**: the identical rejection applies to `key==='__restoreLock__'` (Decision 11's reserved lock key) — a backup file that illegitimately carries a planted lock-shaped record must be rejected for exactly the same reason (a malformed file should never be able to inject a document at a key this feature's own tooling treats as reserved/special), not merely excluded from *legitimate* backups by `TENANT_BACKUP_ENTITY_KEYS`.
**Delete-side scoping, stated explicitly (second pass, citation corrected fourth pass — was wrongly "Decision 17," the test-fixture decision, unrelated to this)**: the corresponding restore-apply delete for the `entityChunks` category (Decision 12) MUST be scoped by `key:{$in:TENANT_BACKUP_ENTITY_KEYS}` in addition to `tenantId` — **not** a bare `{tenantId:target}` — because the restore lock (Decision 11) and the tenant's live `idempotencyRecords` document both live in the same collection, under the same real target `tenantId`, as the records restore is replacing. An unscoped-by-key delete would destroy the lock the restore is currently running under (reopening the exact concurrent-restore race Decision 11 exists to close) and permanently discard the tenant's live idempotency-claim store. The insert side was already correctly scoped this way (`TENANT_BACKUP_ENTITY_KEYS`); the delete side must match it exactly.

## Decision 9 — One unambiguous backup schema for both Mongo and file sources (REVISED)

Restore's apply logic (Decision 12) never needs to know or care which backend the original backup came from — it always consumes the same `collections` shape. *(Fourth-pass correction: cited as Decision 17 through the second pass, then wrongly "corrected" to 18 in the third pass — the actually-correct target, confirmed this pass, is Decision 12, the decision that defines the apply mechanic itself.)*

## Decision 10 — `Tenant`/`Subscription` registry rows are out of scope for tenant-scoped backup/restore (NEW)

**The question, posed directly by the remediation instruction**: are `Tenant`/`Subscription` truly part of "the recoverable tenant state," or operational metadata that lives outside it?

**Decision, and why**: **outside it.** Three independent reasons converge on the same answer: (1) `Tenant.slug`'s global uniqueness (Decision 6) makes any live-Mongo staging of it actively dangerous, and even an offline-staged version would need cross-tenant uniqueness validation *before* apply — real complexity for data this feature's own spec already lists billing/subscription work as a non-goal for; (2) `Subscription.stripeCustomerId`/`stripeSubscriptionId` are foreign references into Stripe, whose actual state is the source of truth — silently reverting them via a tenant-data restore (e.g. an operator restoring a corrupted set of journal entries) would surprise-revert billing state that has nothing to do with what the operator was trying to fix; (3) `default` — today's only real tenant — has *no* `Tenant`/`Subscription` row at all (Decision 5), so any design that treats these as required tenant state would need an awkward "except for `default`" carve-out throughout. **Consequence**: tenant-scoped backup/restore now covers exactly three categories — `users`, `entityChunks` (via `TENANT_BACKUP_ENTITY_KEYS`), `appConfigs` — never `tenants`/`subscriptions`. This is stated as a firm scope boundary in `spec.md`'s Out of Scope section, not left implicit.

**Seventh-pass narrowing, to keep "never queried" accurate rather than accidentally over-broad**: "out of scope" here means `Tenant`/`Subscription` **data** is never captured, staged, counted, digested, or restored as part of any backup/restore payload — that guarantee is unchanged and remains absolute. It does **not** mean, and was never intended to mean, that `scripts/tenant-backup.js` may never issue a `Tenant` *existence/status* read for any other purpose. Decision 21 (seventh pass) introduces exactly one such read — a pre-flight check that the target tenant exists and is active, required by spec.md's own original FR-007 — as a narrow, deliberate, explicitly-carved-out exception to this decision's payload-exclusion rule, not a reversal of it.

## Decision 11 — Restore lock: reuse `EntityChunk`'s existing compound unique index, not a new model (NEW)

**The question**: how to make "two restores for the same tenant can't run concurrently" hold across independent OS processes (a bare in-memory flag does not), preferring an existing atomic primitive over new infrastructure.

**Rejected alternative — a new dedicated `RestoreLock` Mongoose model**: works, but is a new schema/index/migration surface for a concern this codebase already has a structurally identical, reusable primitive for.

**Decision**: reuse `EntityChunk`'s existing `{tenantId,key}` compound unique index (`models/EntityChunk.js:12`) as the atomic acquire primitive, under a reserved key that is deliberately *outside* `TENANT_BACKUP_ENTITY_KEYS` (so it is never itself captured by a tenant backup, with no separate exclusion rule needed — it simply isn't in the list a backup query filters by): `key: '__restoreLock__'`.
- **Acquire**: `EntityChunk.create({tenantId: target, key: '__restoreLock__', data: {runId, pid: process.pid, acquiredAt}})` — a plain insert, not an upsert. A concurrent second attempt for the same tenant hits the *existing* unique index and throws a duplicate-key error (Mongo error code `11000`), which is standard, well-defined MongoDB/Mongoose behavior for a unique-index violation on `insertOne`/`create` — always catchable, never a process crash; the restore script catches it, reads the existing lock document, and reports its `runId`/`pid`/age in a clear rejection message before doing anything else — satisfying "acquire atomically before apply/recovery" by acquiring it as the first *state-changing* action after argument parsing, before even validation, which is simplest to reason about and test (validation/staging are read-only/local anyway, so acquiring earlier than strictly necessary costs nothing). **Sixth-pass note**: since Decision 19's fifth-pass extension, the lock is no longer the literal first action of any kind taken after argument parsing — the unconditional pre-restore quiesce warning (Decision 19's new Step -1) now prints before it. This is not a contradiction, only a clarification: the warning is a print with no side effect on database or filesystem state, while this bullet's "very first action" language is, and always was, about the first state-changing/exclusion action specifically. No document anywhere describes the lock as acquired before the Step -1 warning prints.
- **Release**: `EntityChunk.deleteOne({tenantId: target, key: '__restoreLock__', 'data.runId': runId})` — conditioned on the *same* `runId`, so a stale release can never delete a different, newer lock. Released in a `finally` covering both clean success and clean (caught) failure.
- **Stale-lock handling — explicit, no silent auto-expiry, and no automatic liveness detection (second `/speckit-analyze` pass: this section is tightened, not merely restated)**: if the process is killed (not a clean failure), the lock document is never released and blocks all future restores for that tenant by design — this is the safe default. Recovery requires an explicit, deliberate `--force-unlock` flag in **every** case where the prior run did not exit cleanly, with **no exception** — including the "resume after a crash" scenario itself (see the correction below). Two mechanisms that might look like reasonable alternatives are explicitly rejected: an automatic age-based expiry (could race a restore that is merely slow, not dead) and a process-liveness/`pid`-existence check (unreliable across independent hosts — FR-029 requires the lock to hold across independent OS processes, which in a real deployment may mean independent machines entirely, where a local `pid` check is meaningless, and even same-host `pid`s can be reused by an unrelated process after the original exits).
  **Correction, second `/speckit-analyze` pass — the "plain resume after a kill" scenario was inconsistent between documents and is now resolved in favor of the stricter policy**: the mandatory crash-window/digest-resume test (research.md Decision 12, `tasks.md` T058 *(third-pass correction: previously mis-cited as T055, which is the Step-5 apply implementation task, not the test)*, `quickstart.md` step 8) involves a *real* process kill, which by the rule above always leaves the lock held. **The resolution is that this scenario's re-run MUST also pass `--force-unlock`** — every document describing this test/scenario is corrected to include it explicitly. "Resume is supported" therefore means: an operator (or their own orchestration, which knows for certain the prior process is dead because it is the thing that killed it or observed its exit) re-runs the identical command with the identical backup file **and** `--force-unlock` after any non-clean prior exit. This keeps exactly one lock policy, with no hidden second path, and matches this feature's own "no silent auto-expiry" principle applied consistently rather than carved around for the one scenario that happened to be inconvenient to test.
- **Force-unlock is a single, non-looping, conditioned operation — not a bare delete-then-create (second pass correction)**: `--force-unlock` MUST NOT simply `deleteOne()` unconditionally followed by a separate `create()` — that pair is not atomic, and two operators invoking `--force-unlock` at nearly the same moment could otherwise both believe they hold the lock (one deletes the stale lock, creates its own; the second, mid-flight, deletes what it still believes is the stale lock — which may by then be the *first* operator's live one — and creates its own on top). The specified sequence is exactly: (1) attempt `create()`; (2) on failure, **read** the existing lock document and delete it conditioned on **its own specific `runId`** (`EntityChunk.deleteOne({tenantId:target, key:'__restoreLock__', 'data.runId': <the runId just read>})` — a compare-and-delete, not an unconditional one); (3) attempt `create()` exactly once more; (4) if that second attempt also fails, exit non-zero reporting contention against whichever lock now exists. No retry loop — a second failure is reported as genuine contention, never retried automatically. **Third-pass clarification**: correctness here comes from the *second* `create()`'s own unique-index atomicity, not from inspecting the delete's own matched/deleted count — two processes racing this sequence each issue the same runId-conditioned delete (at most one can ever match a given stale lock), but regardless of which one's delete actually matched, exactly one of the two subsequent `create()` calls succeeds and the other hits the duplicate-key error and correctly reports contention. No `deletedCount` check is needed or should be added.
- **File mode**: an equivalent lock **file** at a fixed, per-tenant path (`backups/.restore-checkpoints/<tenantId>.lock`), created with Node's exclusive `{flag:'wx'}` (fails `EEXIST` if held), released via `fs.unlinkSync` in the same `finally`, with the identical explicit-`--force-unlock`-only recovery policy — no atomicity concern equivalent to the Mongo compare-and-delete above, since a lock-file's content is only ever read by an operator/diagnostic, not compared-and-conditionally-deleted the way the Mongo path requires.

## Decision 12 — Resume derives truth from checkpoint AND actual state, never checkpoint alone (NEW)

**The question**: the checkpoint file's own "ground truth" claim is falsifiable by a real crash window (a category's DB write succeeds, then the process dies before that category's checkpoint entry is written) — how to close this without assuming atomicity the architecture doesn't have.

**Decision**: for each category, in the fixed apply order, *before* performing its destructive delete+insert: compute the category's **current actual** count+digest for the target tenant (the same canonicalization used in Decision 6, step 3 — including the identity-key sort that makes the comparison order-independent) and compare it against the category's **expected** count+digest (computed once during staging, carried in the checkpoint). If they already match exactly, the category is treated as complete — *regardless of what `categoriesApplied` in the checkpoint says* — and is not re-applied. If they don't match, the normal tenant-scoped delete+insert proceeds. This makes the checkpoint file a *hint* that lets a normal resume skip already-verified work quickly, not the *sole* source of truth a lying checkpoint could corrupt — a category that was actually swapped just before a crash (but never got its checkpoint entry written) is correctly detected as already-done by its digest matching, and is never redundantly re-deleted-and-reinserted. This closes the crash window completely, using only a count+hash comparison this codebase already has the primitive for (`computeChecksum()`) — no new infrastructure.

**Delete-side scoping for `entityChunks` (second `/speckit-analyze` pass — cross-referenced from Decision 8)**: both the live-digest re-check query and the destructive delete for the `entityChunks` category MUST be `{tenantId:target, key:{$in:TENANT_BACKUP_ENTITY_KEYS}}`, never a bare `{tenantId:target}` — see Decision 8's "Delete-side scoping" note for why (the restore lock and the tenant's live idempotency store share this same collection and tenantId).

**Default-tenant scoping for the live-digest re-check itself (added fifth pass — this was previously stated only in data-model.md, the restore contract, and tasks.md, never here in the decision meant to be their common source)**: for `default`, the live-digest re-check query for *every* category — not only the `entityChunks` delete — MUST substitute `_defaultTenantFilter` for plain `{tenantId:target}`, exactly like the delete side already does (Decision 1's pattern). Without this, a `default` restore's digest check under-counts live legacy no-`tenantId`-field records and reports a spurious mismatch on the tenant's first restore — safe-direction (it only ever triggers an unnecessary-but-correct delete+insert rather than an incorrect skip), but not the intended behavior.

## Decision 13 — Backup fingerprint on resume: content hash, not filename (NEW)

**The question**: nothing previously compared a resumed run's backup file against the one that partially applied — an operator resuming with the *wrong* file (an old backup, a same-named-but-different file from another operator) would silently apply mismatched data with no warning.

**Decision**: the checkpoint records a `backupFingerprint` — the backup file's own sha256 (the *same* value already computed for its `.sha256` sidecar during `tenant-backup.js`, not a separately-invented hash) — alongside `targetTenantId` and `schemaVersion`. **Ordering, corrected (second `/speckit-analyze` pass — the first pass left this contradicted between documents: research.md said "before validation," the contract/data-model/tasks all said "step 1.8, last." The contract's placement is correct and is what this document now states too)**: the fingerprint check runs as the **last** step of the validation gate (Step 1.8), after structural/format/tenant-match/category-shape/idempotency-exclusion/record-count checks — reusing the file hash already computed during Step 1.1's checksum verification rather than hashing the file a second time. If an existing checkpoint is found for the target tenant (Decision 15 makes this lookup a direct, predictable path, not a search) that is not yet `stage:'completed'`, the tool compares the new file's fingerprint against the checkpoint's recorded one. A mismatch is a hard rejection, naming both files, before any further write — "filename alone is not identity" is satisfied because a renamed-but-byte-identical file is correctly treated as the *same* backup (its fingerprint matches), while a different file at the same path is correctly caught.

## Decision 14 — Atomic writes and directory creation for both the checkpoint and the local staging file (NEW, extended second pass, extended sixth pass)

**Decision**: every checkpoint write in `scripts/tenant-restore.js` uses the *existing*, exported `_atomicWriteJsonSync` from `lib/database.js` (tmp-file + `fs.renameSync`) — the same crash-safety primitive this codebase already trusts for `data/database.json` and every per-tenant file — rather than a plain `fs.writeFileSync`. **The same requirement applies to the local staging file (second pass correction — the first pass scoped this decision to the checkpoint only, leaving the staging file, written one step earlier in the sequence, with no equivalent guarantee)**: `_atomicWriteJsonSync` for both, and `fs.mkdirSync(path.dirname(...), {recursive:true})` runs before the *first* write to **each** of `backups/.restore-checkpoints/` and `backups/.restore-staging/` — mirroring `scripts/backup.js:59`/`scripts/restore.js:55,60`'s own established convention for a freshly-provisioned target, for both directories, not just one. A checkpoint read that fails to `JSON.parse` (corrupt/truncated) is treated as "no reliable prior record" — logged as a clear warning, and the tool proceeds as a fresh run (safe, because staging is always freshly recomputed from the backup file regardless, and Decision 12's real-state digest check means a fresh run never blindly re-destroys already-correct data even without a readable checkpoint).

**Sixth-pass addition — the staging file's own lifecycle across success and failure, and a correction to a wrong rationale a Pass 5 document round introduced for it**: on a successful restore (`stage:'completed'`), the local staging file is deleted automatically — it holds the same sanitized tenant records the backup file itself does, including any plaintext secret an `AppConfig` document may carry (e.g. `smtpPass`, `server.js:5544`), and has no further purpose once the apply step it fed has succeeded. On a `failed` exit, the file is deliberately left in place — **not**, as the restore contract's Step 6, `data-model.md`'s `staged`/`failed` bullets, `tasks.md` T056c, and `quickstart.md`'s step 6c all stated in Pass 5, because a `--force-unlock` resume "reads it rather than re-running Step 3." That rationale directly contradicts this very decision's own opening sentence above ("staging is always freshly recomputed from the backup file regardless") and the unconditional `Lock → Validate → Duplicate-pre-flight → Stage → Checkpoint → Apply` run sequence stated in `tasks.md`'s "Dependencies & Execution Order" section: Step 3 runs on *every* invocation, resumed or not, and would simply overwrite the file fresh regardless of whether the prior copy survived — there is no skip-staging-on-resume branch anywhere in this design, and adding one is not proposed here either. The **correct** rationale, recorded here as authoritative: the file is preserved after a failure purely as a forensic/diagnostic artifact, so an operator investigating why a restore failed — before deciding whether to retry with `--force-unlock` — can inspect exactly what was staged; deleting a file that might still be useful for that inspection, when the run did not complete successfully, is an unforced, purposeless risk with no corresponding benefit. The restore contract, `data-model.md`, `tasks.md` T056c, and `quickstart.md` step 6c are all corrected to state this rationale instead.

## Decision 15 — Checkpoint and staging files are keyed by tenant identity, not by a random run id (NEW, second `/speckit-analyze` pass)

**What was wrong**: the first remediation pass keyed both the checkpoint (`backups/.restore-checkpoints/<runId>.json`) and the local staging file (`backups/.restore-staging/<runId>.json`) by a freshly-generated, per-invocation `runId` — but Decisions 12 and 13 both require locating "the existing checkpoint for this tenant" on a resumed invocation, and a resumed invocation generates a *new*, different `runId` than the failed run's, with no directory-scan or index mechanism specified anywhere to bridge the two. As written, every invocation would look like a fresh run with no prior checkpoint to compare against — silently defeating the fingerprint-mismatch protection (Decision 13) entirely. This also created an unnecessary collision risk between two different tenants' concurrent restores if `runId` generation were ever less than fully collision-resistant.

**Decision**: key both files by `tenantId`, exactly like the restore lock already is — `backups/.restore-checkpoints/<tenantId>.json` and `backups/.restore-staging/<tenantId>.json`, one live file of each per tenant. This is not merely consistent with the lock's own naming; it is *implied* by the lock's own guarantee — since only one restore can ever be in-flight per tenant at a time (Decision 11), there is never a reason for more than one live checkpoint or staging file to exist per tenant either. `runId` remains a field *inside* the checkpoint document (for logging/diagnostic correlation with the lock's own `runId`), it simply no longer appears in either file's path. This also resolves the cross-tenant collision concern without needing to specify a particular entropy source for `runId` beyond "unique enough to correlate one run's own lock/checkpoint/log lines," since two different tenants' files can never collide on path (they're keyed by the different tenant ids) and two same-tenant runs can never coexist (the lock prevents it).

## Decision 16 — Default-tenant duplicate detection: a mandatory pre-flight, not a repair (NEW)

**The question**: research.md's original Decision 1 already flagged pre-existing default-tenant duplicate records (legacy no-`tenantId` copy + explicit `tenantId:'default'` copy of the same identity) as a real, deferred risk — analysis sharpened this into a specific, more severe conclusion: such a duplicate makes tenant-scoped *restore* of `default` provably fail outright during staging's digest computation (both copies rewritten to the same identity would violate uniqueness once inserted), and an *untargeted* `_defaultTenantFilter` delete during apply could silently collapse two live duplicates into one, discarding whichever wasn't in the backup, with no operator-visible warning.

**Decision**: add a mandatory pre-flight check, run automatically (not as an opt-in separate script) before a `default`-tenant backup writes its output file, and again before a `default`-tenant restore performs any apply write: for each logical identity (a `User.id`, an `EntityChunk`/`AppConfig` `key`) matched by `_defaultTenantFilter`, count how many *distinct* physical documents exist for it. If any identity has more than one, **hard-fail** — print the exact identity and category, and both conflicting documents' `_id`s for operator reference — and produce no backup file / apply no restore write. This is explicitly a **detection gate**, not a repair: the tool never guesses which copy is canonical, never merges, never silently discards. Resolving a real conflict, if one is ever found, is a separate, deliberate, operator-reviewed action outside this feature (unchanged from the original Decision 1's framing) — the difference this pass makes is that the *tool itself* now refuses to proceed past an undetected conflict, rather than silently producing a corrupted backup or a restore that fails opaquely mid-apply.

## Decision 17 — Legacy no-`tenantId` test fixtures must bypass Mongoose's own schema default (NEW)

**The question**: `User`/`EntityChunk`/`AppConfig` all declare `tenantId: {..., default: 'default'}`. Mongoose applies a field's `default` at document construction for `new Model()`, `Model.create()`, and `Model.insertMany()` alike — the only seeding pattern used anywhere in this codebase's existing Mongo-backed tests. A test that seeds a "legacy, no-`tenantId`-field" fixture through that normal API silently persists an *explicit* `tenantId:'default'`, never a genuinely missing field — meaning every planned legacy-compatibility test would pass even if the fix regressed to the exact naive-equality-filter bug Decision 1 exists to prevent.

**Decision**: every task that seeds a "legacy, no-`tenantId`-field" fixture MUST do so via the raw MongoDB driver collection object — `User.collection.insertOne({...})` / `EntityChunk.collection.insertOne({...})` / `AppConfig.collection.insertOne({...})` (or `mongoose.connection.db.collection(name).insertOne(...)`) — which bypasses Mongoose's schema-default/casting layer entirely, and MUST immediately read the seeded document back (`.findOne(...).lean()` or equivalent) and assert `!('tenantId' in doc)` **before** exercising the behavior under test. This is a proof-of-fixture-validity check, not just a proof-of-behavior check, and is now a binding requirement (spec.md FR-027), not merely a task-writing convention.

## Decision 18 — Operator-facing honesty: runbook update and precise success output (NEW)

**Decision**: `docs/PRODUCTION_RUNBOOK.md` (the actual operational document this codebase's incident response already points to — confirmed to exist and already document the whole-instance `backup.js`/`restore.js` flow at lines 78/153) gains a new section covering: the tenant backup/restore commands, the explicit distinction from the whole-instance commands, full-tenant-replace-only semantics, resume support (yes, same-backup re-invocation, **always requiring `--force-unlock` after any non-clean prior exit — Decision 11's tightened policy**) versus rollback (**not** supported — reverting an already-applied category requires restoring again from an earlier backup, not an automatic undo), the `default`-duplicate hard-block, and the Telegram/scheduler default-only limitation. `scripts/tenant-restore.js`'s own success output explicitly states the target tenant name and that a **tenant-scoped** restore path was used — a claim about the tool's own design guarantee (every write is filtered to that one tenant, by construction, per Decisions 8 and 12 *(fourth-pass correction: was "8/17" — Decision 17 is the test-fixture decision and does not define this guarantee)*), not an empirically-checked claim about every other tenant's state, which the tool does not and should not spend time verifying at runtime.

**Critical caveat, added fourth pass — this design guarantee covers only the *target* tenant's own collections, not the *live application server's* view of them**: see the new Decision 19 below.

## Decision 19 — A tenant restore MUST require the target tenant's live traffic to be quiesced BEFORE it begins and the server process(es) restarted AFTER it completes, because the running server's in-memory cache is never invalidated by an out-of-process Mongo write and can race the restore itself, not just follow it (NEW fourth pass, EXTENDED fifth `/speckit-analyze` pass, CRITICAL)

**The question, found by re-verification, never previously considered in any of the first three passes**: `scripts/tenant-restore.js` is a separate CLI process that writes directly to Mongo. The live application server process, if it is still running (the normal, expected deployment topology — nothing in this design tells an operator to stop it), holds its own long-lived, per-tenant in-memory cache (`_tenantCaches`/`_dbCache`, `lib/database.js:17-22` and `:176`) that is populated once — **eagerly, at process boot, for `default`** (`initDB()`, `lib/database.js:987-995`) **and lazily, on first request, for every other tenant** (`warmTenantCache()`/`_loadTenantDB()`, `lib/tenantMiddleware.js:93-94`) — and is **never** re-read from Mongo after that either way. `loadDB()`'s default-tenant branch (`:686-688`, the tail of the function spanning `:657-689`) unconditionally returns the already-cached `_dbCache`. Every ordinary write for that tenant flows `saveDB()` → dirty-key marking → the existing debounced (or, for `{durable:true}` callers — the majority of this codebase's financial routes — *immediate, synchronous*) `_flushTenantToMongo()`/`flushToMongo()` → `_persistEntityKeyTenant()`/`persistEntityKey()`, all of which read the value to persist **from that same stale in-memory object**, never from a fresh Mongo query. Critically, `saveDB()` marks **every** top-level key of the in-memory object dirty on every call (`lib/database.js:753,779` — `Object.keys(db).forEach(...)`), not only the key that actually changed — so *any* unrelated write for that tenant re-persists the *entire* stale snapshot, including whatever the restore just changed.

**Fifth-pass extension — this is not only a "the next write after the restore finishes" risk, as the fourth-pass version of this decision framed it**: because dozens of this codebase's financial routes call `saveDB(db, {durable:true})` (a *synchronous*, immediate flush, not the debounced path), a live write for the target tenant arriving **during** the restore's own Step 5 apply window can itself race the restore's delete+insert for a category — recreating a document the restore just deleted (via the live write's own upsert), which the restore's subsequent `insertMany` then collides with on `EntityChunk`'s compound unique index, or silently re-persisting a category the restore had already correctly applied earlier in the same run, using the stale whole-tenant snapshot. This is strictly worse than a post-completion overwrite: it can corrupt the restore *while it is still running*, and the restore lock (Decision 11) does nothing to prevent it, since the lock is checked only by `tenant-restore.js` itself — the live server's normal request/write path has no knowledge of it.

**Decision**: this is a hard operational prerequisite on **both ends**, not an edge case to design around with new invalidation or write-blocking infrastructure. Consistent with this codebase's own established pattern (`docs/PRODUCTION_RUNBOOK.md`'s existing table of settings that "require a restart" to take effect, and this codebase's identical, pre-existing, previously-undocumented exposure to this same staleness mechanism for the *whole-instance* `scripts/restore.js`, which has never quiesced live traffic either) and this feature's own "no unnecessary new infrastructure" constraint, the fix is **explicit, loud, and operational on both sides of the restore, not architectural**:
- **Before** any restore begins (printed unconditionally, before Step 0's lock acquisition, on every invocation — not gated behind a flag): `scripts/tenant-restore.js` MUST print a loud warning that the target tenant's live traffic should be quiesced (the server stopped, or that tenant otherwise prevented from accepting writes) before proceeding, because a write arriving during the restore can corrupt it, not merely follow it.
- **After** a restore completes: Step 6 (Finalize)'s success output MUST state, as part of the same success message, that the target tenant's live application server process(es) MUST be restarted before any further write to that tenant is accepted — e.g. *"✅ اكتملت استعادة المستأجر "acme" فقط، عبر فلاتر مخصّصة لهذا المستأجر — لم تُكتب بيانات أي مستأجر آخر. ⚠️ مهم: أي عملية سيرفر تخدم هذا المستأجر حالياً تحتفظ بذاكرة مؤقتة (cache) قديمة ويجب إعادة تشغيلها الآن، قبل أي كتابة أخرى لهذا المستأجر، وإلا فقد تُلغى هذه الاستعادة صمتاً."* (Arabic, seventh pass — see Decision 22 for why every new operator-facing message this feature introduces must be Arabic, matching `scripts/restore.js`'s own existing convention).
- `docs/PRODUCTION_RUNBOOK.md`'s new tenant-restore section (research.md Decision 18, `tasks.md` T064) MUST state both the pre-restore quiesce step and the post-restore restart step as mandatory, numbered steps in the restore procedure itself, not a footnote.
- This applies identically to `default` and to every other tenant — `default`'s cache (`_dbCache`) is exposed to exactly the same staleness mechanism as any other tenant's `_tenantCaches` entry, just populated at a different moment (boot vs. first request).
- This is **not** a new mechanism to build (no admin endpoint, no IPC signal, no cache-invalidation pub/sub, no per-tenant write-blocking middleware) — it is the same "requires a restart"/"run deliberately, manually, with the operator's full attention" operational discipline this codebase and its own runbook already use for other out-of-band state changes and for the existing whole-instance restore, applied here for the first time to a tenant-scoped write path, and extended for the first time to explicitly cover the *pre*-restore window as well as the post-restore one. Building an automatic write-blocking/quiescing mechanism (e.g. a restore-lock-aware `tenantMiddleware` check that rejects writes for a locked tenant) was considered and explicitly rejected as disproportionate for this phase: it would require touching the live request path itself (`tenantMiddleware.js`/`saveDB()`), a materially larger surface than this phase's own backup/restore tooling, for a risk this codebase's existing whole-instance restore has always carried, undocumented, without incident severe enough to have prompted it before. Recorded as a follow-on hardening candidate for a later phase, not silently dropped.
- **Explicitly out of scope, not silently dropped**: multi-instance/horizontal-scaling deployments, where "restart the server"/"quiesce traffic" would mean coordinating across an unknown number of instances or a load balancer, are already outside this codebase's current architecture (Constitution Principle VI) and this feature's own non-goals — this decision does not attempt to solve that harder problem, only to stop the current, real, single-instance case from silently failing or being corrupted mid-restore.

## Decision 20 — Idempotency-claim survival across a restore is a real, acknowledged residual risk, not silently assumed safe (NEW fourth pass, EXTENDED fifth `/speckit-analyze` pass with a restore-time count, HIGH)

**The question, found by re-verification**: Decision 8 correctly excludes `idempotencyRecords` from every tenant-scoped backup/restore, so a restore never touches them — they survive, byte-unchanged, across a restore that otherwise fully replaces the tenant's `users`/`entityChunks`/`appConfigs`. Every prior mention of this exclusion (this document, both contracts, `tasks.md`) frames it purely as a safety win (the delete-scoping fix, Decision 12, exists specifically to make sure of it). None of them consider the other side: `lib/idempotency.js`'s real, already-implemented claim mechanism treats a `COMPLETED` idempotency record as a permanent, unconditional short-circuit for any future retry of the same `(tenantId, operationScope, key)` — it replays the stored `resultReference`/`journalId` snapshot rather than re-executing, with **no check that the referenced entity still exists** in the tenant's current data. A tenant restore that reverts `journalEntries`/similar data to an earlier point can leave a `COMPLETED` idempotency record referencing a journal entry that the restored data no longer contains — and any legitimate retry of that original operation (a webhook redelivery, a client's own retry logic) will be silently told "already done" and replay a now-dangling reference, never re-creating the entry.

**Decision**: this is a genuine, real limitation of restoring `users`/`entityChunks`/`appConfigs` while deliberately leaving `idempotencyRecords` untouched (Decision 8) — not a defect in Decision 8's own exclusion logic, which remains correct (restoring idempotency claims *would* reintroduce the stale-duplicate-posting risk Decision 8 was written to prevent in the *other* direction). Rather than silently accepting this residual risk unacknowledged, it MUST be documented explicitly: `spec.md` gains a new Edge Case entry, and `docs/PRODUCTION_RUNBOOK.md`'s new tenant-restore section (`tasks.md` T064) MUST state plainly that a tenant restore does not roll back idempotency claims — with the documented remedy being operator inspection of `idempotencyRecords`, not an automatic mechanism (which would reintroduce exactly the kind of "restore auto-repairs a discrepancy it notices" behavior spec.md's own FR-012 already forbids). **The remedy's own inspection guidance must name both `sourceId` and `journalId`, not only `journalId` (fifth-pass correction)**: at least one real, already-wired operation scope (`vendor:create`, `server.js:5898`) completes its claim with `journalId:null` and identifies the created entity only via `sourceId` — an operator checking only `journalId` would miss this class of claim entirely.

**Fifth-pass extension — a cheap, restore-time signal, not just a static paragraph**: unlike a general "go audit everything" instruction, a precise, restore-time-computable count is available at negligible cost and MUST be surfaced by the tool itself, not left entirely to a runbook paragraph an operator might never open. Because a tenant-scoped restore is a full replace and the backup file's own `createdAt` timestamp is already loaded and validated before Step 6 runs, `scripts/tenant-restore.js`'s Step 6 (Finalize) success output MUST also print a count of the target tenant's `idempotencyRecords` with `status:'COMPLETED'` and a `completedAt` later than the backup's own `createdAt` — every such record is, by construction, guaranteed not to be reflected in the just-restored data. This is read-only reporting (a `countDocuments()`-class query, no write, no repair), consistent with FR-012, and mirrors the precedent Decision 19 already set for surfacing an operational caveat directly in the tool's own output rather than only in the runbook. If the count is `0`, the success output MUST print that explicitly (`0 idempotency records at risk`) rather than omit the line — an omitted line reads as "not checked," not "checked and clean."

**Sixth-pass clarification — which physical representation this count actually queries**: `lib/idempotency.js` maintains idempotency state in two genuinely divergent physical forms in Mongo mode, confirmed by direct re-reading. (1) The dedicated `IdempotencyRecord` Mongoose collection (`models/IdempotencyRecord.js`), with its own queryable `status`/`completedAt` fields, populated only by `finalizeIdempotencyClaimMongo()` — which every caller invokes *after* that same request's `saveDB(db,{durable:true})` has already succeeded. (2) The `EntityChunk{key:'idempotencyRecords'}`-embedded array (`db.idempotencyRecords[]`, itself deliberately excluded from tenant backup/restore by this very decision's key-filter above), which `completeIdempotencyClaim()` marks `COMPLETED` synchronously and in-memory *before* that same `saveDB` call. Between those two points in a single request's lifecycle, the two representations can briefly disagree. This count MUST query representation (1), the dedicated `IdempotencyRecord` collection — `IdempotencyRecord.countDocuments({tenantId:target, status:'COMPLETED', completedAt:{$gt: backup.createdAt}})` — since it is the representation with its own indexed, queryable `completedAt` field this count's comparison depends on, and the one whose write is already ordered strictly after the durable save the idempotency guarantee itself depends on. In `DB_FILE_ONLY` mode there is no dedicated `IdempotencyRecord` collection at all — the equivalent count there is computed by loading the target tenant's own file-mode data (exactly as Step 6 already must, to report anything about that tenant) and counting entries in its `idempotencyRecords[]` array whose `status==='COMPLETED'` and `completedAt` postdates `backup.createdAt`; no representation-choice ambiguity exists in file mode, since the array is the only representation that backend has.

## Decision 21 — Tenant-scoped backup MUST reject a nonexistent or inactive target tenant, via a narrow, deliberate exception to Decision 10's payload-exclusion rule (NEW seventh pass, CRITICAL)

**The question, found by the seventh re-verification's open-ended sweep, closing a gap present since before any remediation pass began**: `spec.md`'s FR-007 — an original requirement, not introduced by any remediation pass — requires: "Requesting a tenant-scoped backup for a tenant identifier that does not exist, or is not active, MUST fail with a clear error and produce no artifact." Decision 10 (Pass 1, above) excludes `Tenant`/`Subscription` from tenant-scoped backup/restore's *payload*, describing them as "never queried" — a policy correctly aimed at keeping billing/registry data out of the backup file itself. No decision, contract, or task anywhere in this document set ever actually implemented FR-007's own, separate requirement: a lightweight existence/active-status *check* against the `Tenant` registry, not a data capture, for a non-`default` target tenant. Left as originally scoped, Decision 10's "never queried" language technically forecloses even this single read, leaving FR-007 unimplementable as written and directly contradicted by User Story 2's own Acceptance Scenario 3, which restates FR-007 almost verbatim. (Decision 5's own text already alluded to "skipping any `Tenant.findOne()` active-status check that might otherwise gate a `default` restore" — implying such a check exists for *other* tenants elsewhere in this design; it never did, anywhere, until now.)

**Decision**: for any `--tenant=` other than `default`, and **only when running in Mongo mode** (`MONGO_URI` set — see the file-mode note below), `scripts/tenant-backup.js` MUST perform exactly one additional read as its very first substantive step, before any entity-data query and before the default-duplicate pre-flight's non-default equivalent (there is none — this check is what stands in that place for non-default tenants): `const tenant = await Tenant.findOne({tenantId}).lean(); if (!tenant || tenant.status !== 'active') { <hard-fail, write nothing> }` — reusing `lib/tenantMiddleware.js:72-73`'s own existing, already-proven pattern verbatim, not inventing a new one. This is a narrow, explicit, deliberate exception to Decision 10's payload-exclusion rule, not a reversal of it: Decision 10 remains fully correct and unchanged about backup/restore *payload* content — `Tenant`/`Subscription` data is still never captured, staged, counted, digested, or restored — this is a single existence-check read, discarded immediately after the pass/fail decision, that never becomes part of any backup artifact. For `--tenant=default`: this check is skipped entirely and unconditionally — `default` has no `Tenant` registry row at all (Decision 5), and is always treated as existing and active, consistent with every other place in this design `default` is exempted from registry-dependent logic (e.g. FR-021's restore-side carve-out).

**File mode, explicitly scoped out and why, not silently dropped**: file-mode backup (`DB_FILE_ONLY`, no `MONGO_URI`) has no `Tenant`/`Subscription` registry to query at all — these are Mongo-only concepts in this codebase's current architecture. FR-007's intent is still honored using the only signal file mode actually has: `_tenantFilePath(tenantId)` not existing on disk is treated as "does not exist" (hard-fail, same error family as the Mongo-mode check); file mode has no equivalent of an "active"/"suspended" status stored anywhere per-tenant, so an existing tenant file is always treated as active — a deliberate, narrower interpretation of FR-007 for this backend, not an oversight. Building a parallel status-tracking mechanism for file mode — a backend this codebase already treats as a local/offline fallback rather than the primary multi-tenant deployment target — is out of scope for this phase.

## Decision 22 — Every new operator-facing message this feature introduces MUST be Arabic, matching this codebase's own existing convention (NEW seventh pass, MEDIUM)

**The question, found by the seventh re-verification's open-ended sweep**: every illustrative example message drafted across this document, both restore/backup contracts, and `tasks.md` for `scripts/tenant-backup.js`/`scripts/tenant-restore.js`, across all six prior remediation passes, was written in English. This directly conflicts with the already-shipped sibling script `scripts/restore.js`, whose every operator-facing `console.log`/`console.error` string is Arabic (confirmed by direct re-reading, e.g. `"❌ يجب تحديد الوجهة صراحة: --target=<اسم> ..."`, `"✅ اكتملت الاستعادة إلى..."`), and with this same feature's own Telegram/monitor 403 boundary (`telegram-scheduler-boundary-contract.md`'s error body is specified in Arabic).

**Decision**: every new operator-facing string `scripts/tenant-backup.js`/`scripts/tenant-restore.js` print — errors, warnings, progress, and success messages alike — MUST be Arabic, in the same register and convention `scripts/restore.js` already established: a leading emoji (❌ hard failure, ⚠️ a warning that does not itself stop execution, ✅ success, ℹ️ informational/reporting-only text, ↻ resume/recovery guidance, 🎯/🗄️ target/source echoes), concise imperative Arabic sentences, and English kept only for identifiers that are not natural to translate (`tenantId`, `MONGO_URI`, `IdempotencyRecord`, `--force-unlock`, file paths) — mirroring `scripts/restore.js`'s own existing mixed-language convention exactly, not a full English-free translation that would make technical identifiers unrecognizable to an operator already familiar with this codebase's other scripts. Every illustrative example message in this document, both contracts, and `tasks.md` is corrected to this Arabic convention as part of this same pass. A dedicated test requirement (extending T040a's/T056a's existing content-assertion pattern) asserts the actual Arabic substring for every safety-critical message this decision covers, not merely "some warning printed."

**Why this was missed for six passes**: every one of Passes 1-6 focused on the *mechanics* of tenant isolation and backup/restore safety (the live-Mongo staging hazard, cache staleness, digest correctness, lock atomicity) — none included a linguistic/message-convention consistency check against this codebase's own established operator-facing text. The discovery of `scripts/restore.js`'s and the Telegram contract's own concrete, in-repository Arabic precedent settles this independently of any broader question about what CLAUDE.md's own reporting-language instruction was intended to cover.
