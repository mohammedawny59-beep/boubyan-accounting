# Research: Tenant Isolation + Safe Backup/Restore Hardening (P4)

**Feature**: `002-tenant-isolation-backup-hardening` | **Phase**: 0 (research, `/speckit-plan`)
**Inputs**: `spec.md` (Clarified), the P4 read-only architecture audit (5-area, prior turn), direct re-verification of `lib/database.js`, `lib/tenantMiddleware.js`, `lib/backupValidation.js`, `scripts/backup.js`, `scripts/restore.js`, `models/*.js`, `server.js` (Telegram/monitor routes), and `.specify/memory/constitution.md`.

Every decision below is grounded in a specific, re-read line range — not the prior audit's summary alone — because a plan that gets any of these filters wrong would either (a) leave a CRITICAL bug half-fixed, or (b) silently drop the `default` tenant's real production data from its own "safety" backup.

---

## Decision 1 — `persistUsers()`/`persistEntityKey()` fix: reuse `_defaultTenantFilter`, don't just add `tenantId:'default'` equality

**What was considered**: the obvious first instinct is to make the default-tenant write path look like the already-correct non-default path (`_persistUsersTenant`/`_persistEntityKeyTenant`, `lib/database.js:67-92`), i.e. add `tenantId: 'default'` to every filter.

**Why that's wrong on its own**: `_defaultTenantFilter` (`lib/database.js:404-406`) exists specifically because `default`'s legacy records — every user/entity-chunk document written before multi-tenancy existed — have **no `tenantId` field at all**, not `tenantId: 'default'`. A plain equality filter `{tenantId: 'default', id: {$nin: ids}}` does not match a document missing the field, so:
- `User.deleteMany({tenantId:'default', id:{$nin:ids}})` would silently stop deleting a legacy user removed from the in-memory array — it would resurrect on every restart (read side still finds it via `_defaultTenantFilter`, write side never cleans it up).
- `User.bulkWrite([{updateOne:{filter:{tenantId:'default', id:u.id}, upsert:true}}])` would not find the existing legacy document (no match on an equality filter against a missing field) and would **insert a second, duplicate document** with an explicit `tenantId:'default'` — because the compound unique index `{tenantId:1, id:1}` (`models/User.js:17`) indexes a missing field as its own distinct key value, so no unique-constraint violation stops the duplicate from being created.

**Decision**: reuse `_defaultTenantFilter` on the **write side too** (it is currently read-only, used only by `loadUsersArray()`, `hydrateFromMongo()`, `ensureAdminUser()`) as the *match* filter, and always `$set: {tenantId: 'default', ...}` explicitly (the *update* payload) so every document a default-tenant write touches is normalized forward to an explicit `tenantId:'default'` — legacy ambiguity shrinks with every save cycle instead of accumulating. This exact "spread `_defaultTenantFilter` into a richer query" pattern is already precedented in the same file (`User.findOne({..._defaultTenantFilter, role:'admin'})`, `lib/database.js:575`), so this is not a new idiom.

**Residual risk, documented rather than silently ignored**: if a duplicate pair (one legacy no-`tenantId`-field doc, one already-normalized `tenantId:'default'` doc) already exists for the same `id`/`key` *before* this fix ships — plausible given the current code's inconsistent write behavior — `updateOne`'s single-match semantics mean the fix will keep only one of them synchronized going forward; the other becomes a silent orphan. This is a **pre-existing data-quality risk**, not something this fix introduces or can retroactively repair from application code alone. Scope: a one-time, read-only detection script (`scripts/detect-duplicate-default-records.js`, reports only — see Out of Scope in data-model.md) is recommended as an operational follow-up, not part of this phase's application code change.

## Decision 2 — Tenant-safe config: extend the existing `_tenantCaches` pattern, don't invent a new mechanism

**Current state (re-verified)**: `_configCache`/`_defaultConfig` (`lib/database.js:177-178`) are bare module-level variables with **no tenant keying of any kind** — there is no `_tenantConfigCaches` analog to `_tenantCaches` (`lib/database.js:18`). `initConfig()` (`:609-646`) runs exactly once per process, outside any `runAsTenant()` context, and its own Mongo read (`AppConfig.findOne({key:'config'})`, `:612`) is unscoped — it can hydrate from **any** tenant's config document, arbitrarily, depending on Mongo's match order. `loadConfig()`/`saveConfig()` (`:801-815`) consult this single global pair regardless of `_currentTenantId()`. This is a materially worse gap than the entity/user write bugs: those bugs corrupt data during a write race; this one means **every tenant currently shares one process's config state outright** in a real multi-tenant Mongo deployment.

**Decision**: mirror the already-proven `_tenantCaches`/`_flushTenantToMongo` design exactly, rather than a bespoke mechanism:
- Add `_tenantConfigCaches = new Map()` (tenantId → resolved config object) and `_tenantConfigDirty = new Set()` (tenantIds with an unpersisted config change).
- `loadConfig()` branches on `_currentTenantId()`: `'default'` keeps today's exact behavior (`deepMerge(_defaultConfig, _configCache)`); any other tenant lazily loads (and caches) `AppConfig.findOne({tenantId, key:'config'})` — a plain equality filter is correct here because a real tenant's config document always carries an explicit `tenantId` set at creation (Decision 5) — merged over the same `_defaultConfig` baseline so a brand-new tenant gets sane defaults on first read, not `{}`.
- `saveConfig(cfg)` branches the same way; the non-default path writes into `_tenantConfigCaches` and marks `_tenantConfigDirty`, flushed on the **same** per-tenant debounce timer `_flushTenantToMongo()` already uses (`:57-65`) — one extra `if (_tenantConfigDirty.has(tenantId))` branch inside the existing function, not a second parallel timer.
- The default-tenant Mongo read/write (`initConfig()`'s `AppConfig.findOne(...)`, `flushToMongo()`'s `AppConfig.updateOne({key:'config'},...)`, `:488-496`) gets the identical `_defaultTenantFilter` + normalize-forward treatment as Decision 1, for the identical legacy-no-`tenantId`-field reason.

**Boundary explicitly not touched**: whether an authenticated request is *allowed* to reach `loadConfig()`/`saveConfig()` without a resolved tenant context at all is `tenantMiddleware`'s concern (already covered by the existing FR-002 fail-closed requirement, verified in Phase 1 audit), not this function's. `loadConfig()`/`saveConfig()` simply honor whatever `_currentTenantId()` already resolved to — adding a second, redundant fail-closed check here would duplicate — and could silently drift from — the middleware's own gate.

## Decision 3 — Telegram/scheduler: gate the entry points, not every downstream handler

**Root-cause finding (new this pass, not in the original 5-area audit)**: the Telegram subsystem is not merely "three routes with a process-global side effect" — `bot`/`global._tgBot` (`server.js:2636`) is a **single package-wide singleton** used directly by dozens of inbound-message handlers inside `setupBot(bot)` (`server.js:2700-3735`, `bot.sendMessage(...)` at ~50 call sites). Those handlers fire from Telegram's own polling loop, **not from an Express request** — so they run with no `AsyncLocalStorage` tenant context at all, meaning `loadDB()`/`loadConfig()` inside them always resolve to the **default tenant**, regardless of which tenant's token happens to currently be loaded into `bot`. If a non-default tenant were ever allowed to call `POST /api/telegram/start` (`server.js:2678`, currently gated only by `requirePermission('telegram','edit')` — no tenant check), a real inbound message on *their* bot would silently read and write the *default* tenant's accounting data (expense logging, invoice OCR posting, voice-journal posting — all real write paths inside `setupBot()`) — a materially worse hazard than "wrong bot sends a message," and not fixable by patching each of the ~50 handlers individually.

**Decision**: enforce default-tenant-only at every entry point that could cause a non-default tenant to influence the singleton `bot`/its config, rather than downstream. Four routes identified by direct grep (not just the three the audit's summary listed):
1. `POST /api/telegram/start` (`server.js:2678`) — the root cause; if this is blocked for non-default tenants, `bot` can never be instantiated on a non-default tenant's behalf in the first place, which transitively makes every inbound-handler hazard above unreachable.
2. `POST /api/monitor/inventory` (`server.js:9822`)
3. `POST /api/monitor/monthly-report` (`server.js:9826`)
4. `POST /api/reports/send-telegram` (`server.js:15987`) — not in the original audit list; found via a targeted grep for `bot.sendMessage`/route handlers this pass.

Each gets one explicit, honest check — `if (req.tenantId && req.tenantId !== 'default') return res.status(403).json({error: '...', code: 'TELEGRAM_DEFAULT_TENANT_ONLY'})` — placed after `requireAuth`/`tenantMiddleware`/the route's own `requirePermission`, before any Telegram/scheduler side effect. This is a **documented P4 limitation** (FR-016), not silent default-fallback and not a completed multi-tenant capability.

**Already safe, verified rather than assumed**: the *automatic* hourly/daily/monthly schedulers (`runScheduledTasks()` `server.js:4072`, `runInventoryCheck`/`runMonthlyReport`'s own timer-driven invocations wired in `startMonitorSchedule()`) are started once at process boot, outside any `runAsTenant()` call — so `_currentTenantId()` already defaults to `'default'` for them today, with no code change needed. This was confirmed by reading the scheduler wiring, not assumed from the manual-trigger routes' behavior.

## Decision 4 — No Mongo multi-document transactions; constitution already documents this as a known, accepted limit

`.specify/memory/constitution.md:186-188` (Principle VI's "Known Architectural Risks") already states: *"Multi-document Mongo ACID transactions (`session.withTransaction`) are not generally used; consistency instead relies on idempotency unique-indexes and durable-flush writes."* A repo-wide grep for `startSession`/`withTransaction`/`replicaSet` this pass found **zero matches** in application code — only `.specify/memory/constitution.md` itself mentions the term. `mongoose.connect()` (`lib/database.js:957-960`) passes no replica-set options. **Decision confirmed, not re-litigated**: the restore design (Decision 6) must not assume transactions exist, matching both the constitution and the empirical absence of any transaction infrastructure.

## Decision 5 — `default` tenant has no `Tenant`/`Subscription` registry row; tenant-scoped backup/restore must not require one

Re-verified this pass: `Tenant.create(...)` is called from exactly one place in the entire codebase (self-service tenant registration), and `default` predates that flow entirely — it has no row in `Tenant` or `Subscription` at all. A tenant-scoped backup of `default` will therefore legitimately produce an **empty** `tenants`/`subscriptions` array — this must be documented as expected output, not misclassified as a validation failure. Any tenant-registry "is this an active tenant" check the backup/restore tooling performs must special-case `tenantId==='default'` to always pass, exactly like `tenantMiddleware.js:59-64` already does for live requests.

## Decision 6 — Staged tenant-scoped restore, no transactions: reuse existing primitives, one small new file-based checkpoint

**Constraint**: Decision 4 rules out wrapping the whole restore in a transaction. The existing whole-instance `scripts/restore.js:38` (`await Model.deleteMany({})` per collection, then `insertMany`) is not transactional either — it already accepts "some collections written, others not" as its failure mode; this phase does the same but bounds the blast radius to one tenant and makes the boundary observable.

**Rejected alternative — in-place update of the target tenant's own documents**: updating existing docs field-by-field to match the backup avoids ever deleting real data, but requires computing a diff (added/changed/removed records per collection) against arbitrary historical schema shapes stored in `EntityChunk.data` (a `Mixed` blob per `models/EntityChunk.js:7`) — this is materially more complex than delete+insert and reintroduces exactly the kind of parallel, non-canonical logic Constitution Principle VII warns against. Rejected as over-engineering for what is fundamentally a full-tenant-replace operation (clarified scope, Decision E below).

**Rejected alternative — a second, temporary MongoDB database/cluster for staging**: unnecessary new infrastructure for a feature whose own explicit instruction is "no unnecessary new infrastructure" (spec.md design constraint). Rejected.

**Chosen design**: stage into the **same** collections, under a synthetic, run-scoped `tenantId` value (`__restage__<targetTenantId>`) that can never collide with a real tenant identity (real tenant ids come only from the registration flow or the literal string `default`) — this reuses the exact same `insertMany`/query mechanics `scripts/restore.js` already uses, with one substituted field, rather than a new code path. See `data-model.md` and `contracts/tenant-restore-contract.md` for the full six-step sequence (validate → stage → verify staged counts → checkpoint → swap-per-collection → finalize) and the explicit "what is/isn't atomic" statement required by spec.md FR-013.

**Checkpoint storage — a plain JSON file, not a new Mongo collection**: the checkpoint is operator-facing CLI bookkeeping (which collection did a `tenant-restore` run reach), not accounting or tenant business data. Adding a new Mongo model for it would mean a new schema/index/migration surface for a concern that's naturally file-scoped and already matches this codebase's own convention for operational state living outside the tenant data model (e.g. `backups/*.sha256` sidecars). Written to `backups/.restore-checkpoints/<runId>.json`.

## Decision 7 — Tenant-scoped backup format needs its own discriminator, not a bumped shared `version`

The existing whole-instance format (`scripts/backup.js:75`) is `{createdAt, version: 2, tenantIds, source, collections|database}` — no `scope` field. A new tenant-scoped backup uses `{scope: 'tenant', schemaVersion: 1, tenantId, createdAt, source, recordCounts, collections}` — a **different field name** (`scope`) as the primary discriminator, and its own independently-numbered `schemaVersion` rather than reusing/bumping the whole-instance file's `version` counter. This means `lib/backupValidation.js`'s existing `validateBackupObject()` (whole-instance) and a new `validateTenantBackupObject()` can never be confused by a version-number collision, and `scripts/restore.js` (whole-instance) fed a tenant-scoped file fails immediately on `!backup.collections && !backup.database` (existing check, `lib/backupValidation.js:33-42`) since a tenant-scoped file's top-level shape is deliberately different enough to not accidentally satisfy either legacy branch.

## Decision 8 — Idempotency records are deliberately excluded from tenant-scoped backup/restore

`IdempotencyRecord` (`lib/idempotency.js`, `models/IdempotencyRecord.js`) exists to prevent duplicate financial postings via a unique `(tenantId, operationScope, key)` claim. It is operational safety state describing *in-flight or completed* claims **as of the moment of backup**, not accounting history. Restoring a stale idempotency claim after real operations have continued past the backup's timestamp could either (a) wrongly block a legitimate new operation that happens to reuse a since-expired key, or (b) — worse — fail to block a genuine duplicate the backup predates. Both are silent-correctness risks disproportionate to what this collection is for. **Decision**: tenant-scoped backup/restore covers `users`, `entityChunks` (i.e. every `ENTITY_KEYS` field — the actual accounting data), `appConfigs`, and (for non-`default` targets) `tenants`/`subscriptions`. `idempotencyRecords` is explicitly out of scope, documented here rather than silently omitted.

## Decision 9 — File-mode tenant backup reuses the existing per-tenant file path convention

`lib/database.js:651-655` (`_tenantFilePath(tid)`) already defines `data/tenants/<sanitized-tid>.json` as the on-disk location for a non-default tenant's file-fallback cache, and `saveDB()`'s non-default branch already writes there (`:740-751`). This is currently a private, unexported helper. **Decision**: export it (or an identical pure re-implementation of its sanitization regex) for `scripts/tenant-backup.js`/`scripts/tenant-restore.js` to reuse directly — file-mode tenant backup reads exactly that one file, matching the "file mode reads exactly the selected tenant's file" requirement without duplicating the sanitization logic in a second place where it could drift.

## Alternatives considered and rejected for the overall approach

- **A generic multi-tenant backup/restore framework covering arbitrary future collections automatically**: rejected — explicit non-goal ("no generic distributed system"); `ENTITY_KEYS` already enumerates every real collection, and a framework generalizing over it would be premature abstraction for a fixed, known list.
- **Partial/per-collection tenant restore**: rejected per clarified scope (spec.md FR-020) — full-tenant-replace only in this phase.
- **Making the default-tenant backup/restore paths a special case of the whole-instance script instead of the new tenant-scoped one**: rejected — `default` is backed up/restored through the *same* new tenant-scoped tooling as any other tenant (with the `_defaultTenantFilter`/no-registry-row special-casing from Decisions 1 and 5), keeping exactly two tools (whole-instance, tenant-scoped) instead of three.
