**Revision note (Design Remediation Pass 5)**: A fifth `/speckit-analyze` re-verified Pass 4 and found 1 CRITICAL, 5 HIGH, 3 MEDIUM further defects. The headline finding: Pass 4's live-server-cache fix only closed the *after*-restore window — the same in-memory cache can also race and corrupt a restore *while it is running*, requiring a genuinely new pre-restore quiesce warning (T040a) in addition to, not instead of, the existing post-restore restart message (T056). Two further HIGH findings extend rather than replace Pass 4 decisions: the idempotency-staleness acknowledgment gains a restore-time-computable count printed in Step 6's own output (T056b), and the offline staging file is now deleted automatically on a successful restore since it carries the same plaintext-secret exposure as the backup file itself (T056c). A MEDIUM finding closed a documentation gap: three downstream documents required `default`'s live-digest re-check (not just its delete) to use `_defaultTenantFilter` and attributed this to research.md Decision 12, but Decision 12 itself never stated it (research.md fixed directly; T067's own citation was already correct and needed no task-level change). The runbook (T064) is extended again for all three operator-facing additions, and a pre-existing (not introduced by this feature) factual bug in `docs/PRODUCTION_RUNBOOK.md` §5.1 — a false claim that no live scheduled job exists in this repository, when `startBackupSchedule()` (`server.js:9942`) demonstrably runs one automatically in production — is corrected in the same task. Task count is now 79 (T001-T075 plus T040a, T056a, T056b, T056c) — no other renumbering required.

**Revision note (Design Remediation Pass 4)**: A fourth `/speckit-analyze` re-verified Pass 3 and found 1 CRITICAL, 6 HIGH, 4 MEDIUM further defects. The headline finding, previously unconsidered across all three prior passes: a completed tenant restore is invisible to the target tenant's own live application server process, whose in-memory per-tenant cache is never invalidated by an out-of-process Mongo write — closed by requiring the tool's own success output (T056, extended) to instruct an immediate server restart, with a new dedicated test (T056a) and a runbook update (T064, extended). A second acknowledged-but-previously-unconsidered risk: idempotency-claim survival across a restore, now documented (T064, extended) rather than silently unaddressed. Also fixed: a corrected shutdown-flush design for `_tenantConfigFileTimers` (T015 — Pass 3's version did not actually match the real sibling code it claimed to mirror), and several stale decision-number cross-references left by Pass 3 itself, including two citation "corrections" Pass 3 got wrong. **Revision note (Design Remediation Pass 3)**: A third `/speckit-analyze` re-verified Pass 2 and found 3 CRITICAL, 2 HIGH, 4 MEDIUM further defects — a missing `clearTimeout` step for the new `_tenantConfigFileTimers` map (T008), a `categoryDigests` computed over structurally inconsistent `_id`-bearing vs. `_id`-stripped representations at different pipeline points (T029/T034/T048/T055 — closed via a new shared `computeCategoryDigest()` helper), a stale `<runId>.json` staging-path reference left in research.md Decision 6 after Decision 15 corrected it everywhere else, and several stale decision-number/task-ID cross-references.
